# 任务：IOTLB 失效策略造成的跨设备翻译干扰（来源核查 + 仿真测量）

## 先读这段：本任务的工作方式

本任务为一篇刻画类短论文收集核心证据。研究问题只有一个：

> 在多个 DMA 设备共享 RISC-V IOMMU 时，一个设备做流式 DMA（每次 I/O 都 map/unmap）所触发的 IOTLB 失效，会给另一个使用持久映射的设备造成多大的翻译干扰？失效粒度（整个上下文、按 PSCID、按地址、延迟批量）能把这种干扰降低多少？

- 本提示优先于仓库中旧的流程习惯。不写"合同""裁决""证据包""next-decision-contract"之类文档，不重新评估研究方向，不开新分支方向。
- 不恢复 MIG、FPGA 板测、综合布线，不重跑无关旧实验。不修改生产 RTL 和生产 Linux 代码，所有改动放在独立测试副本中。
- **使用原版 IOTLB 配置**：不启用 P/PN 分区、不使用 `policy_mask_i` 的分区扩展、不使用命中提前旁路。替换策略与上游一致（即 V0 去掉分区 mask 后的行为，所有 way 均可分配）。上一轮已证明分区 mask 会自行制造替换偏置，本任务必须排除它。
- 报告用普通中文和具体数字，让没读过本仓库的体系结构研究者能直接看懂。必须使用的内部术语在报告开头给出一行定义。
- 所有输出放在一个新目录：`iommu-platform/out/invalidation-interference-<日期>/`。

背景：上一轮 `iommu-platform/out/plru-ablation-20261017/generality/README.md` 第 2 节第 5 点指出，平台 Linux 在 strict 模式下每次 unmap 同步失效；RISC-V 驱动未声明 DEFERRED_FLUSH，DMA_FQ 被降为 DMA；`riscv/iommu.c` 中按 PSCID 和按地址的失效被注释，实际执行一阶段宽失效。

## 第二步：仿真测量

### 1. 场景

在现有 Verilator 平台和测试驱动（参照 `plru-ablation-20261017/runner/` 的结构）上构造：

- **设备 A（流式）**：模拟内核驱动的流式 DMA。每次 COPY 前建立映射（写 PTE），完成后撤销（清 PTE，然后经命令队列发出失效命令和 IOFENCE，等待完成）。每次 I/O 使用新的 IOVA 页，按第一步发现的 Linux IOVA 分配规律选取（例如自上向下的连续页号）；如果不确定，说明你的选择。
- **设备 B（持久）**：使用持久映射，循环访问固定的一组页，全程不 unmap。
- A 和 B 的上下文配置要与第一步问题 3 的结论一致。如果 Linux 下两种情况都可能（同域或不同域），两种都跑。

### 2. 变量

失效模式（主变量）：
- **M0 无失效**：A 也使用持久映射，作为无干扰基线。
- **M1 宽失效**：复现平台驱动当前发出的命令粒度。
- **M2 按 PSCID 失效**。
- **M3 按地址失效**：只失效 A 刚撤销的页。
- **M4 延迟批量**：每 N 次 unmap 才发一次失效（N 取 16 和 64），近似 flush queue 的行为。

次要变量（保持矩阵小）：
- B 的足迹：4 页和 8 页（均小于 IOTLB 容量，确保 B 自身不会因容量不足 miss）。
- A 的 I/O 大小：4KiB 一种即可。如果时间允许，加 64KiB 一种。

仿真是确定性的，每个配置跑一次；若发现非确定性，重复至稳定并报告波动。

### 3. 每个配置需要的数据

- B 的 IOTLB 命中、miss、页表遍历次数，以及其中**由失效导致**的 miss（失效后第一次访问该页的 miss）
- B 的完整完成时间，A 的完整完成时间，两者合计
- A 每次失效命令从提交到 IOFENCE 完成的周期数，以及命令队列总占用
- 页表遍历对内存带宽的占用（如可测）

### 4. 停止条件

- 如果测试驱动无法经命令队列发出 IOTINVAL/IOFENCE，或者需要超过约一天的改动才能实现，停止，报告卡在哪里。
- 如果发现 B 在 M1 下几乎没有额外 miss（例如因为 A 和 B 处于不同 GSCID、命令实际不会影响 B），不要硬造干扰，直接报告这个结论及原因。这本身就是重要结果。
