L6: The Xilinx UHD SDI Rx Subsystem consists of UHD SDI Rx IP core, an SDI to native video bridge followed by a Native to AXI-4 S bridge. It is capable of detecting the SD, HD, 3GA, 3GB, 6G and 12G (upto 8 data streams) type SDI streams. The maximum resolution it supports is 4096x2160p60 in 12G mode. The SDI Rx IP allows the configuration of the modes to be detected at run time or a fixed mode. It also allows the Framer to be enabled.
L7: A video lock event is generated when the incoming SDI mode and transport stream is detected and is stable for a configurable number of video clocks as programmed in the Video Lockout Window. When the input video stream is stopped or the type changed, a video unlock event is generated. The IP gives out the CRC and EDH error status. When the bridges are enabled, then the AXI-4 Stream of YUV 422 10 bit per component and 2 pixels per clock is sent out.
L8: cite1†Image L9: The SDI Rx Subsystem driver (cite2†xilinx-sdirxss.c†github.com ) is based on the V4L2 framework.
L10: It creates a subdev node(/dev/v4l-subdev*) which can be used to query and configure the UHD SDI Rx Subsystem IP.
L11: The SDI Rx IP would be the first node in the video capture pipeline.
L12: It exposes various cite3†V4L controls†github.com which can be used to configure the subsystem like auto detection of SDI modes, Framer enable, etc and query the status like CRC status, EDH errors, etc.
L13: It also exposes certain cite4†V4L events†github.com like video unlock, bridge overflow/underflow, video source change, etc which can be used by application to trigger certain actions.
L14: The general description of V4L2 framework is documented here, cite5†v4l2-framework.txt.†www.kernel.org L15: # IP/Driver Features

L50: ### Missing Features / Known Issues / Limitations in Driver
L51:   * In case of a HD stream without payload, a progressive segmented frame (pSF) will be reported incorrectly as Interlaced as the driver relies on the IP's transport scan locked bit.
L52:   * *Multiple instances capability not tested
L53:   * *Tested with only 12G 8DS configuration
L54:   * HD 1280x720p24 and HD 1280x720p23.98 - Incorrect colors are captured
L55:   * In some 3GB 1080 modes, the colors in color bars are swapped.
L56:   * Tested with Phabrix SDI generator and Omnitek Ultra4K
L57:   * Doesn't support to YUV444 in 2019.2

L96: The SDI Rx subsystem locks on to the incoming video stream.
L97: Using VIDIOC_SUBDEV_G_FMT ioctl, the width, height and field type (interlaced or progressive) can be determined.
L98: 
L99: The resolution info can be sent across to video capture application like YAVTA to capture the stream frames into the DDR using a simple design
L100: SDI Rx SS ==> VDMA S2MM OR Framebuffer Write ==> Memory
L101: For example, to capture a 1920x1080 stream the following command is used
L102: 
L103:     yavta -n 3 -c10 -f YUYV -s 1920x1080 --skip 7 -F /dev/video0
L104: 
L105: The captured .bin files can then be viewed in yuvplayer.exe application.
L106: ## Debug capability
L107: 
L108: The driver debug messages can be enabled by adding "#define DEBUG" at the top of the file.
L109: All debug prints are sent to serial console and can be viewed in kernel dmesg buffer.
L110: 
L111: Some tips to help you debug are as below -
L112: 
L113:   1. The SDI source connected to SDI Rx port and should be running.
L114:   2. The driver should have been loaded successfully during kernel bootup.
L115:   3. Running media-ctl should show resolution.
L116:     1. E.g. “media-ctl –d /dev/media0 –p”
L117:   4. Always check if the lock has occurred or not.
L118:   5. If the lock is occurred, is the current mode (SD, HD, 3GA, 3GB, 6G, 12GI or 12GF) same as source?
L119:   6. What is the ST352 payload in RX_ST352_DATA_DS1 register? Decode it to get resolution and size and color format.
L120:      * Refer to driver code how to decode.
L121:   7. Compact GT Reset - There are 2 signals connected to compact_gt which need to be toggled to have a clean reset of the GT.
L122:     1. The SI5324_LOL should be toggled to high and then made low. (Default low)
L123:     2. The fmc_init_done line should be toggled to low and then high (Default high).
L124: 
L125:     3. cite7†Image: AMD Adaptive Computing Wiki > Xilinx V4L2 SDI Rx driver > compact-gt-design.png cite8†Image: AMD Adaptive Computing Wiki > Xilinx V4L2 SDI Rx driver > debug-design.png L126: ## FAQ
L127: 
L128: Q1 - While running yavta for resolution AxB with our source box, we see "Unable to start streaming: Invalid argument (22)." Why is this happening?
L129: 
L130: Ans - One possible reason is that the resolution that the SDI source is generating and what is being passed to yavta don't match.
L131: 
L132: Run media-ctl to find out the resolution currently being identified by the SDI Rx IP driver.
L133: 
L134: Read your SDI source documentation to know how to manipulate the resolutions.
L135: Q2 - The frame rate reported by yavta is significantly lesser than expected.
L136: 
L137: Ans - Depending on your design and system load, there may be a case where there may be frame drops.
L138: 
L139: But double check the ST352 payload in SDI Rx to verify if the SDI source connected is correctly generating the required frame rate (fps).
L140: 
L141: You may have to refer to cite9†PG205†www.xilinx.com to decode the RX FAMILY to get the resolution and RX Frame Rate (in case of zero payload in 2017.3/4)

L171: Q3 - After boot up, even though there is valid SDI source connected, the IP is unable to detect the source and video is not locked. Why could this happen?
L172: Ans - Check if the IP's registers are not default values after kernel boots up. E.g. MODULE_CTRL register should be 0x3F30. If the registers are in default state, it may mean the clocking to the IP is not correct. Please check device tree to set the correct clock source.
