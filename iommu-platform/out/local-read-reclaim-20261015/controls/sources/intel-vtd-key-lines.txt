  6787  6.5.2.3              IOTLB Invalidate
  6788  The IOTLB Invalidate Descriptor (iotlb_inv_dsc) allows software to invalidate the IOTLB and paging-
  6789  structure-caches. This descriptor is expected to be used when software has changed second-stage
  6790  tables and wants to invalidate affected cache entries. The IOTLB invalidate descriptor is a 128-bit
  6791  descriptor. It must be padded with 128-bits of 0s in the upper bytes to create a 256-bit descriptor
  6792  when the invalidation queue is configured for 256-bit descriptors (IQA_REG.DW=1). If a 128-bit
  6793  version of this descriptor is submitted into an IQ that is setup to provide hardware with 256-bit
  6794  descriptors or vice-versa it will result in an invalid descriptor error.

  8130  Requests from devices that are already processed by the remapping hardware, but queued within the
  8131  Root-Complex to be completed to memory are referred as non-committed requests. Draining refers to
  8132  hardware pushing (committing) these requests to the global ordering point. Hardware
  8133  implementations report support for draining through the Capability Registers.
  8134  
  8135  A write request to system memory is considered drained when the effects of the write are visible to
  8136  processor accesses to addresses targeted by the write request. A read request to system memory is
  8137  considered drained when the Root-Complex has finished fetching all of its read response data from
  8138  memory.
  8139  
  8140  Requirements for draining are described below:
  8141   • Draining applies only to requests to memory and do not guarantee draining of requests to peer
  8142     destinations.

  8153   • Draining applies only for untranslated requests (AT=00b), including those processed as pass-
  8154     through by the remapping hardware.
  8155   • Draining of translated requests (AT=10b) requires issuing a Device-TLB invalidation command to
  8156     the endpoint device. Endpoint devices supporting Address Translation Services (ATS) are required
  8157     to wait for pending translated read responses (or keep track of pending translated read requests
  8158     and discard their read responses when they arrive) before issuing the ATS invalidation completion
  8159     message. This effectively guarantees draining of translated read requests. The ATS invalidation
  8160     completion message is issued on the posted channel and pushes all writes from the device
  8161     (including any translated writes) ahead of it. To ensure proper write draining of translated
  8162     requests, remapping hardware must process ATS invalidation completion messages after all
  8163     preceding writes are considered drained.
  8164   • Read and write draining of untranslated requests are required when remapping hardware status
  8165     changes from disabled to enabled. The draining must be completed before hardware sets the TES
  8166     field in Global Status Register (which indicates remapping hardware is enabled). Hardware
  8167     implementations may perform draining of untranslated requests when remapping hardware status
  8168     changes from enabled to disabled.
  8169   • Read and write draining of untranslated requests are performed on IOTLB invalidation requests
  8170     specifying Drain Read (DR) and Drain Write (DW) flags respectively. For IOTLB invalidations
  8171     submitted through the IOTLB Invalidate Register (IOTLB_REG), draining must be completed
  8172     before hardware clears the IVT field in the register (which indicates invalidation completed). For
  8173     IOTLB invalidations submitted through the queued invalidation interface, draining must be
  8174     completed before the next Invalidation Wait Descriptor (inv_wait_dsc) is completed by hardware.
