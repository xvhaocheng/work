## 1. 五个不同研究问题

### Q1：异构加速器数据流水中的“流水阶段感知翻译服务”

**实际需求**：生产者-消费者流水里，DMA 翻译延迟并不等价。上游生产者写描述符、下游消费者读数据，某些翻译处于关键路径，某些可隐藏。当前 IOMMU 只看到请求到达、DID/PASID、hit/miss，不看到应用阶段。

**现有抽象忽略的信息**：`SPEC.md:4` 明确“主 PTW/MSI 稳定 `req_data.did` 决定 fill 份额”。也就是说，现有抽象主要按 DID 分配翻译填充/服务份额，而不是按流水阶段、依赖链或截止期。`E3.md:35` 的受控结论也显示：A 侧被延长的 S1 PTW 响应会传导到一个已在等待的 V read，V 首次命中随后在共享串行控制器/AR 队列上等待。即共享服务顺序会决定谁先过。

**为何增加 TLB / 预取 / 分区不够**：TLB 提高命中率，但一旦 miss，共享控制器仍可能按普通 FIFO 或按 DID 服务；预取增加在途请求，可能让非关键流式请求占用控制器；固定分区无法区分同一 DID 内的关键阶段与非关键阶段。

**最小机制**：在 DMA 请求里携带一个轻量“阶段/依赖/截止期”标签；IOMMU 或共享控制器只按该标签对同一依赖链排序，例如让下游消费者已预译的请求或关键阶段请求优先。最小改动是增加一个可选的标签字段和一个排序/旁路规则，而不是重做 TLB。

**最强廉价对手**：应用层静态预翻译所有流水阶段地址 + 大 TLB + 普通 FIFO。

**一条足以否定价值的观察**：若软件预翻译后关键路径端到端延迟与“标签排序”无差异，或标签排序不改变共享控制器上的等待分布，则价值低。

**证据等级**：【事实基础】`BRIEF.md:7` 多 DMA 共享翻译干扰；`SPEC.md:4` DID 决定 fill 份额；`E3.md:35` A-miss 导致 V-hit 阻塞。【推断】阶段/依赖标签可能改善关键路径。【假说】该信息不能被简单预取/大 TLB 替代。

### Q2：动态内存管理中的“在途翻译一致性窗口”

**实际需求**：页迁移、回收、热插拔、内存压缩需要低延迟失效或重映射，不能长时间停止 DMA。当前实现的 quiet 是粗粒度全静默：`SPEC.md:41` 要求 TL quiet 包含 state IDLE、无 req_valid/输入 req/ATS/debug、无 fastbusy/响应/故障、无 walker 更新/有效端口/规范 inval、top 无 bank 在途及 TR/COMP/DS 通道 valid，DMA quiet 覆盖所有 lane 且排除同周期 issue/launch。`SPEC.md:45` 还写明软件 mutex 串行，失败不能强制 flush 在途。

**现有抽象忽略的信息**：它忽略在途翻译事务的“剩余生命周期”和“可迁移窗口”。IOMMU 只有全局 quiet，没有按 IOVA 范围、按 epoch、按请求检查点的细粒度失效。

**为何增加 TLB / 预取 / 分区不够**：增大 TLB 不减少必须等待 quiet 的时间；预取反而增加在途请求，可能拉长静默；分区只隔离 DID，不解决全局失效。`E3.md:43` 还显示控制器在 AWAIT_RESP 保持当前请求，COMPLETE 要等输出地址被接收后才回 IDLE，说明在途请求会真实占住状态。

**最小机制**：给翻译事务加 epoch/检查点。失效时只等待已越过检查点的请求；未越过检查点的请求可丢弃或重定向。或提供按 IOVA 范围的迁移屏障，而不是全设备 quiet。

**最强廉价对手**：停止 DMA 队列 + 等待所有完成 + 重新配置。这是当前最稳、最便宜的软件排空。

**一条足以否定价值的观察**：若在途窗口只占迁移/失效总延迟很小比例，或停止队列成本明显低于细粒度屏障，则价值低。

**证据等级**：【事实基础】`SPEC.md:41` quiet 定义；`SPEC.md:45` 失败不能强制 flush；`E3.md:43` 控制器保持当前请求。【推断】细粒度 epoch 可缩短静默。【假说】该缩短在真实迁移负载中可测且不可由排空替代。

### Q3：异步取消/迁移中的“取消令牌”

**实际需求**：应用取消推理请求、网络流、任务或迁移时，希望已发 DMA 尽快停止占用翻译和数据路径，而不是完成后丢弃结果。

**现有抽象忽略的信息**：IOMMU 只做地址翻译，不传播取消语义。请求一旦进入 PTW/AR 队列，缺少“这个请求已被取消”的信息。`E3.md:43` 说明 AR FIFO 头只在 `ar_ready` 时前进，只有 IDLE 才做 select，AWAIT_RESP 保持当前请求，COMPLETE 等输出地址被接收后才回 IDLE；这意味着在途请求不可轻易撤回。

**为何增加 TLB / 预取 / 分区不够**：TLB 和预取让更多请求在途，取消时更难排空；分区不解决单个请求的取消；普通优先级不表达生命周期。

**最小机制**：DMA 引擎与 IOMMU 共享取消域/epoch。翻译请求携带取消令牌；IOMMU 在队列中丢弃已取消请求，或返回“无效/取消”响应而不产生地址。最小改动是请求字段加令牌，控制器在 select/fill 前检查一次。

**最强廉价对手**：应用让 DMA 完成再丢弃结果 + 软件 quiet 等待。

**一条足以否定价值的观察**：若取消率低，或取消延迟对资源占用/QoS 无可测影响，则价值低。

**证据等级**：【事实基础】`E3.md:43` 控制器状态机；`SPEC.md:41` quiet 全静默。【推断】取消令牌可减少无效占用。【假说】取消延迟是关键资源指标。

---

### Q4：稀疏间接访问的“结构感知翻译”

**实际需求**：稀疏张量、图遍历、gather/scatter、描述符链常形成两级或多级间接：先读索引/描述符页，再按结果读数据页。访问稀疏但结构化，翻译请求有父子依赖。

**现有抽象忽略的信息**：IOMMU 按 IOVA 独立翻译，看不到描述符链的父子关系、访问模板、分支结构。`SPEC.md:4` 只有 16 条 IOTLB，`SPEC.md:22-24` 只记录 V/A/other 的正常首次 lookup/hit/miss；这些观测不表达“哪个翻译属于同一条链”。

**为何增加 TLB / 预取 / 分区不够**：增加 TLB 不能解决每个新索引页导致的 miss 和依赖顺序；盲目预取可能预取错误分支，加剧共享控制器干扰；分区不能跨 DID 跟随链依赖。`E3.md:35` 已显示共享串行控制器上的等待会传导。

**最小机制**：翻译请求携带结构提示/父子 ID；IOMMU 按同一描述符链聚合或排序，或对同一链的子请求做范围合并。最小改动是让请求带一个轻量结构 ID，控制器按 ID 做局部排序。

**最强廉价对手**：应用预分配大页、连续 IOVA、软件预翻译整个描述符链。

**一条足以否定价值的观察**：若大页/连续分配或软件预翻译整个链后，端到端时间与结构感知机制无差异，则价值低。

**证据等级**：【事实基础】`SPEC.md:4` 16 IOTLB；`SPEC.md:22-24` 观测粒度；`E3.md:35` 共享控制器阻塞。【推断】链结构信息可改善排序/聚合。【假说】该收益不能由大页或全链软件预翻译替代。

---

### Q5：共享设备多租户的“翻译 QoS 等价类”

**实际需求**：网卡多队列、RDMA、GPU 多进程共享同一物理设备，多个租户/队列交替访问。需要 QoS 和公平，而不是仅隔离。

**现有抽象忽略的信息**：当前抽象按 DID/PASID 隔离与固定分区。`SPEC.md:4` 中 P 固定 low2 保护 DID（本批 10），其余 14；`SPEC.md:5` 是 mask 约束 tree-PLRU。它忽略共享设备内部队列/租户的翻译工作集签名和动态交替模式。

**为何增加 TLB / 预取 / 分区不够**：简单按 DID 固定分区会造成 TLB 容量碎片；增加 TLB 可能被交替租户冲刷；普通优先级/限流不表达共享设备队列的延迟敏感度；固定分区不能跟随动态工作集。

**最小机制**：按设备共享的“翻译工作集签名”或队列 QoS 动态共享/迁移 TLB 条目，而不是每 DID 固定。最小改动是允许少量条目在等价类之间按签名共享或迁移。

**最强廉价对手**：每租户独立 TLB/固定分区 + 软件预翻译。

**一条足以否定价值的观察**：若租户数少、工作集不重叠、共享设备队列不交替，则共享收益不存在。

**证据等级**：【事实基础】`SPEC.md:4` 固定 DID 保护分区；`SPEC.md:5` tree-PLRU；`BRIEF.md:7` 不要求未来局限两路或 16 条目。【推断】共享设备 QoS 与 DID 分区不等价。【假说】动态等价类共享优于固定分区。

## 2. 两个具体可检验的小工作负载

以下不是机制验证，而是“需求/张力是否存在”的小规模验证。均建议在 S 模式或关闭 P/N 的基线上做，避免变成 P/N 有利工作集比较。若不实现新机制，也可作为主 Codex 判断是否值得立项的阴性/阳性观察。

### W2：在途翻译窗口下的 quiet / 失效延迟

**对应问题**：Q2 动态内存管理。

**平台假设**：现有 CVA6 + 四 iDMA + RISC-V IOMMU + Linux、Genesys2。`SPEC.md:4` 四 DMA、DMA0/1 同 512 拍缓冲、16 IOTLB。`SPEC.md:44` 可用 `Vpages=1`、`Apages=8/16`、`chunk=4096`、`gapV=0/1000/4000`、`Agap=0`。`SPEC.md:15` 有 live quiet，`SPEC.md:18` 有 window cycles，`SPEC.md:22-24` 有 V/A/other 首次 lookup/hit/miss。

**工作负载**：
1. DID10 作为 V，DMA0/DMA1 对 V 区域持续读/写，形成在途请求。
2. DID11 作为 A，DMA2 触发长 S1 PTW。若现有 E3 delay 模块可用，可参考 `E3.md:41-43`；若 composition profile 不含该模块，则需主 Codex 决定是否用软件慢页表或将其标记为待实现注入，不能假装已有。
3. 在 V 流稳定时，软件发起对 V 目标 IOVA 的规范化失效/迁移/quiet 操作。记录发起前、发起中、完成后的 window cycles、V/A 事件、quiet 完成时间、DMA 完成延迟。
4. 对照：空载 vs V 在途；A 长 PTW vs A 短 PTW；有/无软件预取 V。

**可检验指标**：quiet 延迟是否随 V 在途请求数、A PTW 长度显著增加；增加 TLB 条目或简单预取是否不降低该延迟。

**否定观察**：quiet 延迟与在途请求数/长 PTW 无相关，或该延迟占应用迁移预算 <5%。

**注意**：`SPEC.md:41` 的 quiet 定义非常严格；`SPEC.md:45` 说失败不能强制 flush 在途。因此这个工作负载直接检验“现有抽象是否只能在粗粒度静默上等待”。

**检索关键词（未执行检索，仅入口）**：
`IOMMU in-flight translation invalidation latency`  
`DMA remapping quiet page migration`  
`IOMMU epoch based invalidation`  
`device TLB shootdown in-flight requests`  
`address translation lifecycle for page migration accelerators`

### W4：稀疏描述符链的依赖翻译与流式翻译交错

**对应问题**：Q4 稀疏间接访问。

**平台假设**：四 DMA，16 IOTLB（`SPEC.md:4`）。DMA0 执行两阶段 gather：先读描述符表，每个描述符位于不同 4KB 页，再读数据页。DMA1 同时连续流式读/写作为干扰。需先确认 iDMA 是否支持描述符链；若不支持，主 Codex 可决定用软件模拟两阶段 DMA 或缩小为多请求间隔。不能假装已具备。

**工作负载参数建议**：
- `chunk=4096`，描述符表 32/64 项，每项 64B，故意跨 32/64 个 4KB 页。
- 链长 1/4/16/64；分支稀疏度变化；父描述符位置变化。
- DID10/DID11 分配使 lookup/hit/miss 事件可观测（`SPEC.md:22-24`）。
- 对照：软件预取整个描述符链（最强廉价对手）；只预取第一层；不预取。
- 同时运行 DMA1 连续流，观察共享控制器等待。

**可检验指标**：链式依赖完成时间是否因流式干扰显著增加；增加 TLB 条目或只预取第一层是否不消除；软件预取整个链是否消除差异。

**否定观察**：软件预取整个描述符链后，链完成时间与结构感知机制无差异，或稀疏度不影响结果。

**注意**：`E3.md:35` 已给出共享控制器上 A/V 等待传导的受控证据，但不要把它直接外推为普适 head-of-line blocking；`E3.md:82` 明确不主张普适 head-of-line blocking。

**检索关键词（未执行检索，仅入口）**：
`IOMMU descriptor chain aware translation`  
`sparse gather scatter IOMMU translation coalescing`  
`dependency-aware address translation accelerators`  
`indirect sparse tensor DMA address translation`  
`translation prefetch for descriptor chains IOMMU`

## 3. 大胆假说 vs 已验证创新

**已验证/文件事实，不能当创新**：
- 平台有四 DMA、RISC-V IOMMU、Linux、Genesys2；同一 BIT 四模式 S/N/P/PN，172 功能验收，仅单启动重复，不能当统计充分性（`BRIEF.md:7`）。
- 16 IOTLB、50MHz、4DMA、DMA0/1 同 512 拍缓冲；P 固定 low2 保护 DID；主 PTW/MSI 稳定 DID 决定 fill 份额（`SPEC.md:4`）。
- quiet 定义很严格，软件 mutex 串行，失败不能强制 flush 在途（`SPEC.md:41`、`SPEC.md:45`）。
- E3 受控观察：A 侧延长 S1 PTW 响应会传导到等待中的 V read，V 首次命中随后在共享串行控制器/AR 队列等待；精确措辞是“本实现的 A-miss 引起的 V-hit 阻塞，发生在共享串行控制器/AR 队列上”，不说 AXI 规范强制如此（`E3.md:35`、`E3.md:37`、`E3.md:43`）。
- PN 在某些工作集比 N 慢，但这不是已确立新理论或新机制（`BRIEF.md:7`）。
- 已有先例：MASK、HPCA2017、UCP/KPart、rIOMMU、BypassD、ShareMMU、arXiv2508.19670 等（`BRIEF.md:9`、`BRIEF.md:11`）。描述符预翻译、跨设备翻译共享、首次发现 IOMMU 干扰不能直接说成新（`BRIEF.md:11`）。

**本提案的大胆假说，尚未验证**：
- H1：翻译请求携带阶段/依赖/截止期标签，可减少关键路径等待，且不能由大 TLB 或普通预取替代。
- H2：在途翻译生命周期可被 epoch/检查点利用，缩短页迁移/失效的 quiet 延迟。
- H3：取消令牌可在 IOMMU 队列中安全丢弃请求并释放资源，且取消延迟影响 QoS。
- H4：描述符链结构信息可被 IOMMU 用于翻译聚合/排序，且不能由大页或全链软件预翻译替代。
- H5：共享设备多租户的翻译 QoS 等价类共享优于按 DID 固定分区。

这些只是假说，需要主 Codex 决定是否值得做最小原型与检索。不能写成“已验证创新”。

## 4. 给主 Codex 的判断点

1. 优先级上，Q2 与 W2 最接近现有平台可观测能力：`SPEC.md:15`、`SPEC.md:18`、`SPEC.md:41`、`SPEC.md:45` 已提供 quiet/window/事件，且 `E3.md:35`、`E3.md:43` 已证明共享控制器等待真实存在。Q4 与 W4 需要先确认 iDMA 描述符链能力，但动机清楚。
2. Q1/Q3/Q5 作为候选保留，不建议直接进入大规模实现；它们需要新的请求标签、取消域或共享设备 QoS 抽象，属于更大接口变化。
3. 所有候选都不要转成安全隔离；共享设备只谈性能 QoS。不要用“加 AI/RL”包装。
4. 新颖性检索必须区分：rIOMMU 已利用 I/O ring/buffer 信息，BypassD 是安全共享 SSD，ShareMMU 是多加速器安全共享预翻译地址，arXiv2508.19670 已测量 SMMUv2 多方干扰（`BRIEF.md:11`）。我们的关键词应检索“生命周期、取消、epoch、描述符链依赖、quiet 延迟、稀疏间接访问、共享设备 QoS 等价类”等更窄组合。
5. 价值判断不应依赖 P/N 模式比较；若机制只在 P/N 某些工作集有利，应视为不满足本问题。`BRIEF.md:7` 已明确不要求未来局限两路或 16 条目，`BRIEF.md:9` 已排除按 miss 计费/服务计费/自适应限流/普通优先级/独立 PLRU/分区作为直接创新。
