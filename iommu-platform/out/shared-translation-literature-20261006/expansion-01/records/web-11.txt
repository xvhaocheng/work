# HELM: Characterizing Unified Memory Accesses to Improve GPU Performance under Memory Oversubscription

This article is summarized in an AI Podcast.

Authors: Nathan Jones, Tyler Allen, Rong GeAuthors Info & Claims

Published: 15 November 2025 Publication History

## Abstract

### Abstract

Unified Memory (UM) technologies simplify memory management across CPU and GPU domains in GPU-accelerated heterogeneous architectures through transparent data migration. However, the default migration mechanism can severely degrade performance when applications oversubscribe GPU memory. Existing approaches to mitigating this performance degradation often fail to generalize, as they target specific application types, require specialized hardware, or integrate opaque classification methods.

We introduce HEterogeneous Locality Metrics (HELM), a novel set of semantically meaningful metrics designed to characterize UM access patterns across diverse applications. These metrics are quantified using readily accessible UM driver telemetry data, providing users with tractable and interpretable UM memory characterizations. Such insight is critical for selecting optimal UM migration and placement policies under oversubscription. We demonstrate HELM’s accuracy and interpretability through access pattern analysis across various UM workloads. Experimental results on real systems show that HELM effectively guides policy selection, which outperforms default UM behavior by 3.5x on average.

Graphics Processing Units (GPUs) have become ubiquitous in both high-performance computing (HPC) and cloud-based environments, as evidenced by the growing dominance of GPU-based systems on the TOP500 list [1, 14]. While GPUs have significantly improved the performance and efficiency of large-scale applications, they have also introduced substantial challenges in programming and system maintenance. In particular, managing memory across the CPU and GPU domains remains a complex, tedious, and error-prone task, especially when application memory footprints exceed GPU memory capacity. This burden is especially pronounced for domain scientists and other users who often lack low-level systems programming expertise, yet are required to navigate the intricacies of heterogeneous memory hierarchies.

Unified Memory (UM) technologies, such as NVIDIA’s Unified Virtual Memory (UVM), have been introduced to address the increasing complexity of heterogeneous programming. By integrating the GPU memory domain into the host’s virtual memory system and transparently managing data migration between them, UM significantly reduces the need for explicit, low-level memory management, allowing developers to focus on core domain logic. UM further enhances programmability by enabling memory oversubscription—the ability to use more memory than is physically available on the GPU through dynamic migration and eviction. UM mitigates a persistent research challenge: efficiently decomposing, distributing, and coordinating such irregular workloads across accelerators. In particular, UM provides advantages in resource-constrained settings, irregular scientific workloads, and deep GNNs—scenarios where multi-GPU approaches often prove inefficient or impractical. However, despite these advantages, some applications under oversubscription can suffer significant or even prohibitive performance degradation [2].

Figure 1 illustrates the significant performance loss under oversubscription in a GPU-accelerated Unified Memory (UM)-based matrix-vector multiply and transpose (MVT) application. Execution time increases dramatically, e.g., by 10x, when the memory footprint grows from 13 GB to 14 GB, exceeding the 12 GB GPU memory capacity. This oversubscription issue is likely to worsen as data requirements in HPC and deep learning applications continue to outpace the growth of accelerator memory. In fact, machine learning researchers have identified a growing memory wall that limits exploration and scalability [18]. As data-intensive applications in machine learning and scientific computing continue to expand, it is increasingly critical to develop UM solutions that offer both ease of use and high performance, particularly for large workloads that oversubscribe GPU memory.

However, not all applications experience the same degree of performance degradation under oversubscription. While MVT suffers from severe slowdowns as oversubscription increases, other applications, such as stream, incur only minor—and sometimes avoidable—performance penalties, even under heavy oversubscription. The varied performance impact across applications stems from how memory access patterns interact with the underlying UM technology. This variability highlights the need for adaptive solutions that can intelligently leverage UM capabilities to suit different workloads.

To address this, UM systems must incorporate intelligent designs that support adaptive memory policies and management. Such systems should be capable of identifying memory behavior and adjusting their strategies accordingly. These adaptations may involve policy-level decisions, such as migration and placement rules, as well as additional mechanisms like prefetching or intelligent eviction to improve performance under diverse access patterns.

Existing methods that apply application-specific UM policy have several limitations. Several works target specific applications rather than generalizing across workloads. Others require specialized hardware or telemetry data that are not representative of modern systems. Such works are often not human-understandable, and require large amounts of training. Further, conventional ideas such as locality in CPU caches do not apply directly to highly parallel systems due to differences in architecture.

Our novel response to these limitations is HEterogeneous Locality Metrics (HELM), a suite of semantically-meaningful metrics that fill the information gap currently preventing accurate optimal memory policy predictions for general applications. HELM distills readily accessible UM telemetry data into six metrics that preserve a similar intuition to traditional locality metrics, and serves as the first step towards building new, intelligent, adaptive, real-time memory policy and management systems for UM. Our UVM driver changes, metric quantification tools, and validation model are available at https://doi.org/10.5281/zenodo.15294080.

In particular, this work contributes the following:

(1)

We propose HELM, a novel set of locality metrics that account for highly-parallel UM data access while preserving similar intuition to traditional locality metrics. These metrics, spanning three groups—Fault Density, Duplicate Faults, Fault Span—provide a statistical foundation for characterizing applications. Although we quantify the metrics offline in this work, we specifically define them such that they can be quantified online using any segment of UM telemetry data with low overhead, making them relevant for autonomous UM runtime decisions.

(2)

We demonstrate the interpretation and intuition required for using our metrics in analysis, and then provide a broad analysis of their efficacy in classification.

(3)

We extend this analysis to a HELM-informed metric validation tool, which demonstrates HELM’s efficacy by predicting the optimal performance policy from a subset of existing strategies. Our results show that, with metric-informed policy selection, the tool achieves up to an 83x speedup over the default UVM behavior and up to 2.8x over the next best alternative.

HELM enables the development of more advanced policy mechanisms in future UM middleware and can also assist application developers in analyzing how their applications interact with UM for performance tuning. Furthermore, we demonstrate HELM’s generality by evaluating our validation tool on two complex, real-world applications.

Metric Definitions and Notation

This work contributes novel, UM-specific metrics that characterize memory access patterns for each memory allocation present in a given application. These metrics derive from page fault telemetry data. Page fault data only gives a partial view of the overall memory access—without information about accesses and reuses within CPU or GPU domains—which presents a substantial challenge to access policy decision mechanisms. We overcome this challenge by using architectural knowledge to infer information about the overall access pattern. In this section, we introduce these metrics and discuss their relationship to GPU architecture and access pattern characterization.

Table 1 summarizes our metrics and notation. Following several general terms, the table shows three main types of metrics in the lower half: duplicate fault counts, fault span, and fault density.

•

Duplicate fault counts (fdup) of Page Frame Numbers (pfn s) in a batch or across aggregated consecutive batches. They potentially indicate access locality and reuse from concurrent active device thread warps.

•

Fault span (S) represents the range of accessed pfn s. A higher fault span can indicate more irregular or sparse access patterns.

In this section, we demonstrate that HELM effectively characterizes access patterns of applications by analyzing HELM metrics of various micro-benchmarks, supporting its potential in real systems. Importantly, HELM metric collection and processing require only nanoseconds, negligible compared to the 1 − 10 microseconds the UVM driver requires to service faults. This supports the potential utility of HELM metrics in online runtime systems, as the HELM processing tasks are out-of-band with kernel execution.

Micro-Benchmarks included in our study spanning several domains. We consider tealeaf and cg complex, as their number of allocations make exhaustive policy search intractable.

Our experiment platform is a system with Titan V 12 GB HBM2 GPUs and an AMD EPYC 7551P 32-Core processor with 128 GB of memory. We modify the NVIDIA 535.104.05 GPU device driver to support fault logging.

This study uses the first five micro-benchmarks in table 2 to demonstrate HELM accurately characterizes memory access patterns for device applications. To improve the generality of our results, the micro-benchmarks span various domains and access patterns. We calculate HELM for all five micro-benchmarks at problem sizes that occupy \(100\%\), \(125\%\), \(150\%\), and \(175\%\) of the GPU memory capacity to evaluate oversubscription scenarios. To avoid altering fault patterns, we select micro-benchmarks that easily support NVIDIA UVM and oversubscription. Most micro-benchmarks have few changes from their source code, except bfs-worst, which generates an adversarial graph input for its breadth-first search algorithm. bfs-worst’s base micro-benchmark comes from EMOGI [23]. Stream experiments utilize the BabelStream CUDA implementation[8] with the triad-only option.

Experiments for this section evaluate how UVM application policy affects application performance. We use the same system with a few minor changes. We use an unmodified version of the NVIDIA 535.104.05 GPU device driver, and modify the micro-benchmarks to accept a UVM application policy at runtime. We measure total kernel execution time as performance. To avoid influencing kernel execution time, we use fault data collected offline; we do not collect fault data while measuring performance.

#### 6.1.1 Performance Evaluation.

Our performance evaluation demonstrates that HELM accurately characterizes access patterns, allowing MIM to accurately predict the optimal strategy and outperform several commonly implemented strategies. We exhaustively search all possible UVM application policies for the first five micro-benchmarks across all problem sizes in table 2 to experimentally determine the optimal policy. To demonstrate the complexity of this problem, we evaluate MIM against four static policies listed in table 3. 
We demonstrate HELM’s applicability to modern workloads by applying MIM to two micro-benchmarks not present in the original dataset: tealeaf and cg. Similarly to many modern applications, these micro-benchmarks have complex memory layouts rendering exhaustive search intractable. We therefore evaluate these micro-benchmarks against the static strategies rather than the global optimal. Unlike the five simpler micro-benchmarks loop through only a few kernels, the complex micro-benchmarks have approximately 20 unique kernels, creating a much more complex access pattern. As an offline tool, MIM treats applications as one large kernel, and thus applies one application policy to all kernels within each micro-benchmark. Future online tools could use HELM to dynamically assign kernel memory access policies for individual or groups of kernels, rather than a singular application policy. Despite the additional challenges cg and tealeaf pose, MIM achieves a 1.8x speedup over default, and 0.7x the performance of the best static strategy. We suspect that accurately differentiating between multiple streaming allocations may require more memory access pattern information, such as that provided by NVIDIA Access Counters—a feature that enables receipt of finer-grain access patterns [3, 9]. Regardless, the general success of Device Allocation Packing demonstrates that our fault span and fault duplicate application ratio metrics accurately characterize memory footprint and reuse. Despite its few errors, the Device Packing step’s necessity is underscored by the ablation result for No Device Packing in figure 10: omitting Device Packing results in a \(40\%\) slowdown from MIM.

The migration threshold predicts the relative performance of demand migration and pin-to-host, which demonstrates that fault density and allocation duplication rate indicate the efficacy of demand migration. Across our experiments, this test always successfully maps the correct strategy to the correct allocations, assuming Device Allocation Packing makes the correct decisions. The Migration Thesholding step’s perfect accuracy demonstrates that our density and fault duplicate metrics accurately characterize effectiveness of demand migration and RDMA. Due to its effectiveness, omitting this step results in the largest slowdown relative to MIM, as reflected in figure 10.

As demonstrated by MIM, HELM’s key strengths are as follows:

•

HELM provides an efficient characterization that allows MIM to perfectly predict streaming access and rank on-demand policies across our dataset.

•

HELM is interpretable and theoretically portable; page-fault telemetry exists on every UM-capable device.

HELM is limited in its ability to inform Device Packing for streaming applications—this is an especially difficult problem in UM access pattern analysis. Despite this limitation, HELM successfully informs MIM to predict optimal UM policies in \(75\%\) of cases.

## 7 Related Work

Our work primarily concerns locality metrics for UM  under oversubscribed memory conditions. This work distinguishes itself from most UM-related work because it performs on modern commodity hardware in a physical system. Prior work generally studies performance directly, either through analysis or optimization. Optimization studies may include memory policy optimization, but ours is the first to quantitatively measure these patterns and analogize them to traditional concepts of memory locality. We also focus on telemetry data and access pattern features already enabled in modern systems without needing specialized hardware.

### 7.1 Heterogeneous Memory Systems Performance Analysis

UM  performance analysis has drawn the attention of several prior works. Many of these works focus on application performance on the NVIDIA UVM system [6, 20], while others analyze deeper UVM features, including oversubscription and memory access hints discussed in this work [4, 10, 11, 13, 19, 22, 28]. 
## 8 Conclusion

This work introduces HELM, a novel, semantically meaningful metric suite that characterizes heterogeneous memory access. Through analysis of current UM telemetry data, HELM provides users with an interpretable memory characterization. HELM allows users to analyze previously opaque access patterns, opening the door to targeted optimization and effective autonomous memory management. We validate HELM through MIM, demonstrating HELM-informed adaptive UM policies consistently outperform static heuristic strategies. We illustrate HELM’s applicability to real workloads by successfully applying MIM to two complex modern micro-benchmarks.

HELM creates the foundation for multiple future works. While we expect HELM metrics to differ between systems, a more rigorous evaluation is needed. Similarly, additional study into online computation of HELM metrics could better support HELM’s use in a runtime adaptive memory management system. HELM provides the motivation for future works in this area, and demonstrates such works are worthwhile.

### E.3 Details on Artifact Reproduction

The authors provided a Docker container that included all necessary software dependencies and scripts to run the experiments. When using Chameleon Cloud, setting up is straightforward. In the old version of the AD/AE appendix, the NVIDIA driver version 535.104.05 was not correct, causing the following running scripts to fail. After contacting the authors, they provided the correct driver version 555.42.02.

After the container was successfully built, the provided scripts were run as per the instructions in the AD/AE appendix. The evaluation procedures included some back and forth with the authors to debug some errors in the scripts. In the end, the ‘paper-figs-subset.sh’ script was successfully executed to generate all figures in the paper using a subset of the data by setting a timeout limit.

The authors asked for a badge "Results Reproduced", but the artifact requires more than 8 hours for reproduction even using a subset of the data. The SC25 web pages about the Reproducibility Initiative clearly state that authors cannot expect a "Results Reproduced" badge when the required time for reproduction is more than 8 hours. Therefore, the badge "Artifact Evaluated/Functional" can be granted.

Disclaimer: This Reproducibility Report was crafted by volunteers with the goal of enhancing reproducibility in our research domain. The time period allocated for the reproducibility analysis was constrained by paper notification deadlines and camera-ready submission dates. Furthermore, the compute hours in the shared infrastructure (e.g., Chameleon Cloud) available to the authors of this report were limited and restricted the scope and quantity of experiments in the review phase. Consequently, the inability to reproduce certain artifacts within this evaluation should not be interpreted as definitive evidence of their irreproducibility. Limitations in the time allocated to this review and the compute resources available to the reviewers may have prevented a positive outcome. Furthermore, reviewers assess the reproducibility of the artifacts provided by the authors; however, they are not accountable for verifying that the artifacts support the main claims of the paper.
