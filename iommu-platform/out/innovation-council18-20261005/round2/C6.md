## 2. A6-P1：留下具体干扰问题，撤掉无条件界与不等价对手

**最强版本及应用。** A6 accepted R1:52–56、149–164 已收窄为高频 unmap/失效与静态设备共用 IOMMU 的情形；这比泛称“翻译控制面瓶颈”可审查。静态映射不等于静态缓存状态，命令也可能占用共享服务，因果链具有合理性。但摄像头/网络同实例部署、所需撤销语义、真实 burst 和逐请求失效率均未给直接轨迹；不能把 strict 自动等同于每个包一条 fence。

**先行差异。** 本次直接读 Bermuda 的背景与评估方法：`bermuda2025.txt:130–167,365–445`。158 行已提 frequent invalidations，但所核评估用并发数据读取分别制造 TBU/TCU 竞争，没有在这些段落看到独立扫描失效命令率。因此不能用 Bermuda 的背景一句话宣布 A6 已被完整覆盖；也不能宣称整篇或领域没有这种研究。更直接的机制近邻是 IDYLL：`idyll2023.txt:399–419` 明确失效请求与 demand walk 共用 walk 队列、页表缓存及 walker，并影响其时延。A6 剩下的窄差别只能是具体跨设备/跨域尾时延与实现语义，不能认领“失效影响翻译请求”本身。原文：[Bermuda](https://arxiv.org/pdf/2508.19670)，[IDYLL](https://par.nsf.gov/servlets/purl/10492257)。

**必须纠正的四处协议/界限。**

1. A6:168–182 的 `W 页数×一次 walk 时延` 只可能描述一次失效后、没有再失效/容量驱逐/重试、且服务时间受限的重建工作量近似。W=1 也可在多个访问间反复被清除；同一 DMA 内的额外 miss 不受一次重建 W 约束。若要硬界，至少需失效到达的突发界、服务界、仲裁与进展条件；观测的平均失效率 R 不够。walk 可并行时工作量也不能直接等同端到端阻塞时间。A6 R2 撤回“机制 b 无界”是进步，但 `R×单命令周期` 本身仍不是尾时延硬界。
2. A6:191 用“对 A 未使用的地址失效”作为纯命令对照，不保证只剩命令效应。规范允许忽略操作数扩大失效；只有先证该实现实际精确匹配，才可这样解释。否则应将“扩大范围”显式作为因素，不能靠命令输入名称消除它。`riscv_queues2026.txt:276–282`。
3. A6:164 的 fence “等发起方自己的命令”不准确：IOFENCE.C 等待该 CQ 内此前命令；PR/PW 请求排序的是已经由 IOMMU 处理的此前设备读/写，文本没有限定为提交 fence 的某个设备。它不自动意味着第三方数据路径停顿，但作用域也不能缩成“只等自己”。`riscv_queues2026.txt:302–326,344–355`。[官方规范](https://docs.riscv.org/reference/iommu/v20260222/iommu_in_memory_queues.html)
4. C1/C2 对照之间的差值不能默认相加分解总效应；改用有效的析因对照、服务事件与交互项。修改正在使用的页表但不失效，还可能改变语义；只允许不影响被测映射的合法对照。p99 差值是该分布上的比较，不是可复用的最坏响应时间证明。

**最强可行基线及成本。** 软件基线是在同一严格撤销边界内允许的批组、真实可复用缓冲池和驱动供给优化；硬件基线是精确范围失效、合理页表缓存/LLC，以及可实现的命令服务隔离。分开比较其成本，不假造一个零成本全能组合。大页须应用允许；passthrough 不满足隔离要求时只能作机会参考；lazy flush 若延后权限撤销，不能作为同语义胜者。单独 PSCID 也不是独立硬件队列，遇全局扩大仍会受影响。独立 IOMMU 是存在相应平台资源时的部署对手，其成本与可获得性须计入。

LLC/暖页表是必要的合理配置对照，DATE2025 所测 gemm 只支持这个要求；它没有证明所有短 DMA 或命令仲裁尾部都低收益。精确失效、多端口、服务隔离会增加状态、面积或吞吐代价；协议更精确也未必需要完整多端口，这是待实现核实的成本。

**最低成本判别。** 将 K1 放在 K0 前：先确认上述实际事件与阻塞边，再选择真实工作量和同语义普通方案。没有阻塞边，淘汰该平台实例；只有不现实的失效负载才出现，淘汰该应用主张。若以后观察到合理基线下仍有截止期风险，才值得测因果归属。5% p99 是筛选阈值而非理论界，“小于容量干扰”可以否定原先更强命题，却不独自否定一种仍会击穿真实截止期的干扰。

## 3. D6-P1：保守目录已在最直接先行中，回退不修复旧副本

**公平版本。** 将授予建立在安装缓存条目之前，是比“事后猜谁访问过”更严格的协议设计；设备数多、实际持有者少时定向失效可能省通信。但 GPS 的数据订阅者分布不能证明翻译副本稀疏，也不能从现有四个 iDMA 推出设备 ATC 广播成本。

**直接致命证据。** D6:43 以“IDYLL 必须精确，而本方案允许保守超集”为核心差异。本次核到 IDYLL §6.2/Fig.8：`idyll2023.txt:463–477` 将多 GPU 的 access bits 哈希到同一 bit，明确允许 false positives，它们只增加无用失效、不影响正确性；`885–896` 还讨论了误报随规模的代价。这直接反驳所声称的区分点，超过了 A6 R2 仅凭一般目录常识的反驳。[IDYLL 原文](https://par.nsf.gov/servlets/purl/10492257)

令 H 为仍能使用旧翻译的实际持有者，S 为失效接收者；无另一个强制检查点时，必须保持 H⊆S。多报安全、漏报危险。D6:53 的“无有效授予就不缓存”可建立这个不变量，却不能免费维护它：授予与失效并发、安装中的 walk、撤销确认前删除授予、持有者退出都需定义顺序。若 H 中有持有旧翻译的设备遗漏于 S，让另一个无授予设备走新 walk 不会使前者停止；“欠订阅只伤性能”只适用于从未安装/已经可靠撤销的条目。若每次访问由可信节点重新检查 grant，就要计入这个检查点，与 ShareMMU 比较。

本次直接读 `sharemmu2026.txt:364–430`：Permission Tracker 对私有 TLB 包含、驱逐触发 back-invalidation，权限下降仍等待脏数据写回/flush 确认。其每次预翻译访问的权限检查也是重要区别；不能只把它简化成一张目录。[ShareMMU](https://d1qx31qr3h6wln.cloudfront.net/publications/ShareMMU_MICRO26_Camera_Ready.pdf)

**成本与强基线。** 对应平台上比较 IDYLL 的保守哈希目录、普通包含式目录+定向失效、ShareMMU 式可信检查；前两者与后者的安全模型不同，应分开匹配。保守 S 的规模可能远大于 H，故流量应按实际接收集合与误报计，不能无条件写 O(真实持有者数)。D6 的 `1−E[subscribers]/N` 仅在每接收者成本相同、统计权重适当且忽略额外授予/确认开销时，估计特定轨迹的接收者数量节省；不是端到端收益或一般硬界。稀疏分布即便证实，也救不了已被原文覆盖的新颖性主张。

**最低成本否证与停止。** 纸面比较已完成关键否证，无需先统计 trace 或做 FPGA 控制面模拟。保留目录为普通基线知识，淘汰当前候选。未来若有具体协议新差异，应重新立命题、成本和错误交错；“当前板不支持 ATS”不是淘汰理由。

## 4. D6-P2：按完整生命周期偏序审查，不能发明普遍两段下界

**公平版本。** 地址翻译撤销、已经翻译请求的完成，以及逻辑地址能否重新命名对象，确实不是同一事件。动态池/RDMA 撤销是可研究的真实领域；但 D6 对具体 CXL/MR 完成契约仍只有待核入口，不能把“固定 timer 是工业默认”当事实。

**原强主张为何淘汰。** 失效传播与旧请求排空可以同时发生。例如二者从同一时点起分别耗时 10 和 8，在允许重叠且无其他依赖的协议里可在 10 完成，而非 18。这足以反驳普遍相加；同样不能改成普遍 `max(两段耗时)`，因为协议可能要求串行、重试或另一个完成点。应画依赖图，用同一时间原点记录完成事件，检查全部复用条件何时满足。若某失效完成契约已内含排空，再单列相加还会重复计算。

RISC-V 原文已规定页表撤权、IOTINVAL 同步、PR/PW 对已处理请求排序，并指出未抵达 IOMMU 的请求可能需要互连 fence，`riscv_queues2026.txt:332–355`。因此“失效确认不等于所有设备在途已消失”是已有规范边界。ShadowUpdate 的已核摘要说明迁移更新/在途门控有直接近邻，但摘要不足以证明所有池页回收协议都已解决；不以它替代缺失的全文审查。

**对 A6 R2 的必要反纠正。**

- 非 ATS 迟到请求是否 fault 取决于到达时的命名状态：保持该 IOVA 未映射会拒绝；若同一 domain/IOVA 已映到新对象，旧逻辑请求可能按新映射访问。必须检查正常 DMA 的完成/停发契约、IOVA 复用和必要的互连顺序，不能只看 ATC 是否存在。反过来，现成 DMA 完成契约也可能已经排除了这个交错，不能据反例宣布新硬件必需。
- 有限队列容量约束在途数量；若没有仲裁公平、有限服务或故障处理保证，数量有限不保证完成时间有限。D6 的“有限但无界在途”应明确到底指个数还是时间；A6 的“只有 ATS 才可能无界”也不成立。对恶意设备仍持续请求的讨论要指定可信拒绝点，不能由“不停发”独自推出无解。
- **延迟复用不是权限撤销。** 隔离旧物理页/暂不重用 IOVA 可以防止旧引用命中新对象，但不能代替严格时限内停止访问旧对象；保持未映射则还要确认旧缓存已撤销。比较时须保持相同的撤权时刻、完成语义和命名复用规则。

**代价、基线与实验缺陷。** 强普通方案为目标平台原有的设备完成/停止发起契约、规定的失效与等待、必要的互连 fence、合法的 IOVA/物理页复用隔离；不得混合不兼容平台的能力，也不得把保护窗口忽略掉。隔离容量、设备暂停、批组延迟均计成本。退休字节速率×平均滞留时间只在适用稳态条件下给平均占用，既不是突发容量硬界，也不自动随设备数/RTT 线性增长。

D6:141 的“停止发起到 IOMMU 不再收到请求”只观察入口，漏掉已通过 IOMMU、尚未到全局排序点的访问；也不检验新命名何时开放。`t_drain/(t_ack+t_drain)` 因重叠与漏项不能作为可优化份额。`t_drain≈t_ack` 不构成不是一阶成本的证据；两项同量级反而需要看关键路径。故不执行这个两分量实验。

**最低成本判别。** 选一条具体真实 DMA 生命周期，读完成、unmap、fence、IOVA 释放/重用的契约，纸面构造“撤权后旧请求迟到、同地址已复用”的交错，说明它是否已被禁止。若现成契约已给完整保证且真实回收等待没有独立成本缺口，停止。若契约缺失，仅说明还无法审查；不称不可能性论文，也不因 FPGA 可以制造 outstanding 就称真实 CXL 回收验证。

## 5. A1-P1 跨方向查漏：DVM 对照必须先于命中/miss 实验

**公平版本。** IOVA 由 OS 分配而物理页通常已存在，确有别于要求应用 VA 与物理分配器共同适配的场景；在短、串行读 DMA 中，翻译依赖延迟也可能暴露。仅缺少在途并发并不否定这个问题。

本次直接核 [DVM 作者全文](https://research.cs.wisc.edu/multifacet/papers/asplos18_dvm.pdf) §3.2、§4.2：它保留映射/权限验证，让 PA=VA 的读 preload 与验证并行，失败丢弃并重试；写不能这样预发。它不是关闭 IOMMU 的 passthrough。§4.3 同样让 OS 在得到 PA 后选择 VA，但多页连续分配及应用 VA 条件与 IOVA 场景不完全相同。故不能认领“先算地址、边读边验证”或“OS 选择地址”作为空白；也不能因此抹掉 IOVA 的约束差异。

最强可行对手是同等保护检查下的 identity IOVA/普通可计算映射，加相同预读能力与成本核算。带密钥 π 不自动增强撤销正确性，也不是通过验证的证明。应先回答：为何 identity 不满足需求，而双射满足？连续多页 IOVA 段在任意页号置换后通常不再对应原 PA 连续段，可能需更多 scatter/gather 描述符、分段或受限置换；DMA mask、对齐、别名与同页不同权限也需回退。不能同时承诺任意双射、原有连续映射接口、无额外描述符成本。预验证读还须限定普通内存副作用及攻击者可观测状态；是否符合目标保护模型未审定，不能把密钥当豁免。

“命中/miss 实测差就是硬上界”也应撤回：只有构造了相同其余条件的合法模型放宽，才可作为该配置的条件性机会界；人工强制命中可能改变请求次序、缓存和排队，且新方案仍付权限验证。没有排队不等于不能隐藏依赖延迟；walker 吞吐饱和才是另一个必须排除的限制。

首判应是纸面语义/接口比较：若 identity 加验证已满足全部需求，π 无额外优势，淘汰该机制。若存在明确需求，再估算真实短 DMA 的残余关键路径，并与适用的暖页表/预取方案比；大页或 lazy 只在同语义允许时列入。当前缺口足以阻止 RTL 立项，但不是“DMA 场景不真实”的结论。

## 6. 回应 A6/D6 对 C6 的质疑，并修订自己的 R1

**接受降级。** C6 R1 已承认 WIC 应用仅支持“有独立工作、外部等待”的部分条件，未证明就绪工作被等待者保留资源挡住、状态转存代价形成困难、真实 demand-fault 压力与人工等待共存。A6/D6 指出这些不足是正确的。修改结论为：**仅保留测量入口；没有已成立的新规律、机制或发表承诺。** 我不把“资源账本”视为可发表贡献。

**原文支持到哪里。** WIC §5.1–5.2（`wic2025.txt:505–565`）描述借 fault 停住 warp 并调度 ready warp，§6.4（`865–903`）报告所测配置 fault 并发限制及合批，不能据此证明 CTA、寄存器、shared memory 或硬件 replay 状态何时归还。软件 PFQ 长度不等于硬件保留资源。GPU Coroutines 已直接给 continuation/live-state、wavefront/persistent 调度和寄存器/共享内存/全局存储成本，本席 R1 的具体阅读范围保留在来源审计；普通协程、固定预留、就绪队列均不能改名认领新贡献。[WIC](https://www.usenix.org/system/files/atc25-zhang-jiajian.pdf)，[GPU Coroutines](https://sites.cs.ucsb.edu/~lingqi/publications/paper_siga24gpucoroutines.pdf)

**接受因果要求，修正其证明形式。** D6 说“非可加交互”才可能保留，应收窄为：有非单调曲线/交互项本身仍不够，普通共享资源模型也会产生它。A6 要求至少两种依赖形状下没有任何固定阈值接近上界，方向有用，但不必试图证明所有可能阈值都失败，更不能把打败固定阈值当终点。需要在训练输入外比较：仅等待时长的充分调优策略、加入实际资源信息的可实现策略、现成就绪流水/协程调度；证明新增信息提供稳定、重要且成本后仍存在的决策价值。

**基线保持可共同实现。** 同一应用与保护/通信语义下，分别实现或建模：批量 split-kernel/事件与只提交就绪任务；普通通信 warp+就绪队列及准入；经过 live-state 裁剪/布局优化的 GPU Coroutines；WIC 合批加简单准入；应用允许的预取/预生产。按各自消耗的 SM、寄存器、主机核、状态存储、带宽、kernel 启动及队列操作计费。不把这些不同设计的优点无代价相加，也不故意只对比低效 polling。

**最低成本否证。** 步骤 0 仍是读 WIC 精确版本的 PCM fault→PFQ→PAT→搬运→replay 路径与资源释放条件。拿不到可审实现则暂停该实例，不宣告整个问题不存在。只有找到可能的资源保留边，才考虑真实 FEM/stencil 等依赖轨迹中是否出现“就绪工作被等待者挡住”的窗口；不人为缩显存或制造无限外部等待。不存在该窗口，停止本候选。

**修正收益界用语。** R1 的“普通方案达理想上界 95%”只保留为预先声明的经验筛选思路，不能用未经证明的离线 oracle 冒充界。有限输入也可以拥有严格的条件界，关键在于放宽模型是否确实包含所有合法调度、外部就绪时间是否会被调度反过来改变，而非仅在于 trace 有限。可用同一固定输入、经论证的理想时间下界 T_lb 与强普通方案 T_b：若 T_b/T_lb−1 小于预定的 10% 机会阈值，便不值得机制开发。若 oracle 不满足这些条件，只报经验比较，不称硬界；10% 是项目筛选选择，不是发表标准。若最后只剩“长等待用协程、短等待轮询”或固定预留已解决，立即停止。

**不接受以平台否定应用。** A6 R2 的“与本平台无关”只能说明需真实 GPU/驱动/任务数据及其取得成本，不能作为问题不存在的推理。现有 FPGA 的 172/172 也不能支持 GPU 驻留/UVM 论断。后续是否值得取得外部平台，由真实缺口和剩余机会决定，不默认扩展项目。
