## 1. 地图的因果结构、一个遗漏与一处过度概括

### 1.1 地图在方向1上的因果骨架（简）

地图的主干判断是"每个强机制都有适用条件，条件失效时瓶颈迁移"（map 9, 28, 31）。压到方向1内部，它实际给出的是一条**三层因果链**：

1. **索引方式决定依赖结构。** Barr 证明：物理索引的 page-table cache 必须自顶向下串行查找（每级给出下一级的物理地址），而虚拟索引的 translation cache 可乱序甚至并行查找，并可直接从被跳过的层级开始 walk（translation_cache2010 337–347, 352–362）。这是"依赖"一词在方向1里最本源的来源。
2. **映射函数决定能否与取数重叠。** SPARTA 用"VA 唯一确定内存分区 + PTE 与数据同分区"把翻译与数据取回从串行变重叠（sparta2020 383–399, 444–460, 481–495）。它不需要连续性，只需一个**很弱的放置不变量**（分区内任意位置，数百万选项，sparta2020 226–232）。
3. **分布式放置决定搜索路径长度与复用。** HDPAT 把中央 IOMMU 的翻译工作分散到按"离 IOMMU 的距离"分层的晶粒上，用聚类（每层每个 PTE 只出现一次）与旋转保证任意方向都有近邻缓存，用重定向表让后到的请求追上刚完成的翻译（hdpat2026 74–96, 496–534, 569–591）。
4. **OS 可构造的放置不变量决定碎片下是否仍可预测。** Revelator 用 tiered hash 把"VA→PA、VA→末级 PTE 框"变成可被硬件重算的函数，并且**用真机测量证明**SpOT 式连续性在碎片/分配干扰下崩掉（覆盖从 >85% 跌到 <10%，revelator 239–286, 405–423；精度 100%→~70%，revelator 267–275）。

综合看，方向1的重复困难不是"缓存不够大"，而是**"翻译与数据/翻译与下一级走表/翻译与失效"三者之间的依赖链在何处被切断，以及放置信息由谁、以什么代价维护"**。地图的六个卡点里，卡点1（粒度）、卡点3（放置与更新代价）、卡点6（静态资源与物理扩展）基本覆盖了这条链，但有两处值得质疑。

### 1.2 一个遗漏：地图没有把"翻译目录"立为独立结构层

地图把翻译结构隐含二分为"缓存/翻译缓存"与"页表缓存"（map 15, 60–71, 173–175），只在 HDPAT 一句里提到"重定向"（map 50）。但本批材料里**反复出现第三类结构**——**有损、不反压、只记录"翻译在哪/在不在"的目录**：

| 实例 | 键 | 存什么 | 关键性质 | 出处 |
|---|---|---|---|---|
| HDPAT Redirection Table | PID+VPN | 指向持有该翻译的 GPM | 1024 项；**不占 MSHR、不产生翻译并发反压**；同面积下比 TLB 省近一半 | hdpat2026 555–604, 854–863, 917–924 |
| HDPAT Cuckoo filter | VPN | 该 VPN **是否可能**在本地 | 负例可直接跳过走表；**假阳性使延迟翻倍** | hdpat2026 130–146, 465–476 |
| Revelator NUMA Bloom hint | VPN | 该页**可能**在哪个 NUMA 节点 | **不在正确性关键路径上**，只影响推测方向 | revelator2026v2 769–797, 823–828 |
| IDYLL PTE directory | 页 | 哪些设备可能持有有效副本 | 用来**过滤不必要失效**，即"在场/缺席"信息 | map 41, 122 **[待核]** |

这四者的共同抽象是：**它们不是缓存（不存翻译内容），而是"翻译的位置/在场目录"；它们允许假阳性、不做反压、键是 VA/上下文。** 地图没有命名这一层，也没有问"何时该加目录、何时该加缓存、何时该加 walker"。这是本席 P1 的直接入口。**【推断】**

### 1.3 一处过度概括："覆盖"被当成"容量/命中率"的同义词

地图在多处用"覆盖/TLB reach"混指容量、reach 与命中率（map 15, 173）。但 Barr 对 coverage 有**严格定义**："coverage means that no memory accesses were required to fetch L4, L3, or L2 page table entries"（translation_cache2010 405–407），而且**同一命中在两种索引方式下 coverage 语义不同**：

- page-table cache 要算"覆盖"，必须**同时**持有 L4+L3+L2 三项；
- translation cache 只需**一个 L2 项**即可覆盖（translation_cache2010 408–416）。

也就是说，**coverage 是指数方式的属性，不只是容量的属性**；地图把这层结构区分抹平了。这直接支持 P1：**"位置信息"（一个项即可）与"翻译内容"（要多项才覆盖）在容量-收益曲线上是不同量纲。**【事实 + 推断】

（附带一处小不一致：SPARTA 2020 已经是"memory-side 翻译 + OS 分区协同"，但在 map §2.1 的分期里它被放在第一阶段（map 67），而同类"OS 协同/物理扩展"被描述为第三阶段（map 28）。分期叙事会掩盖"放置不变量"其实是**一条贯穿 2020–2026 的单一设计轴**。**【推断】**）

## 2. 候选 D1-P1：翻译"在场/位置目录"作为第三类结构——覆盖与依赖的解耦

### 2.1 真实应用、具体触发条件与"为什么现在"

**应用条件**：一个 IOMMU 被多个发起者共享，PTW 并行度受限，翻译请求以突发形式到达。项目平台正好是这个条件的可测实物：CVA6 + 4 iDMA + RISC-V IOMMU + Linux/Genesys2（map 184），产生"小 DMA 干扰 / IOTLB miss / PTW 排队"这类可观测需求。

**触发条件（有直接原文支撑）**：
- 中央 IOMMU 的硬件约束使其只有约 16 个并发 walker，请求在突发下排队（hdpat2026 148–158）；
- 48 GPM 时队列积压接近 **700** 条翻译请求，pre-queue delay 成为单笔延迟的最大分量（hdpat2026 190–191, 182–201）；
- 理想化"极低延迟或 4096 walker"都只换来约 5× 上限，说明**排队**而非单次 walk 是主项（hdpat2026 182–201）；
- HDPAT 明确指出**不能简单按 GPM 数扩 walker**（面积/功耗，hdpat2026 59–60, 150–151）。

**为什么现在值得研究**：设备共享一个 IOMMU 的数量在上升（HDPAT 晶圆级、SPARTA 多加速器、ShareMMU 不可信共享，map 50, 93），而 walker 并行度受面积/功耗封顶。此时"**减少到达 walker 的请求数**"与"提高命中率"是两条不同路径，后者已被大量研究（大页、更大 IOTLB、Victima、HDPAT 分层缓存），前者只有 HDPAT 的整流/重定向做了局部尝试，且**从未被抽象成一层、也从未与"队列内合并"这条最强普通方案正面对撞**。**【推断】**

### 2.2 最接近的先行工作与精确差别

1. **HDPAT Redirection Table（行级最接近）**：1024 项、只存 PID+VPN、无 MSHR、允许请求"追上刚完成的翻译"，同面积下比 TLB 好 **1.27×**（hdpat2026 555–604, 854–863）；无 HDPAT 时 42.1% 的翻译被下放到分布式机制（hdpat2026 707–708）。
   **精确差别**：(a) HDPAT 把目录当作**peer GPM 缓存定位器**，服务对象是晶圆级 GPU 的 peer cache，而 P1 把它当作**共享 PTW 的请求整流器**，服务对象是多设备小 DMA；(b) HDPAT 明确排除 GPU-to-GPU 迁移，因此完全没评估失效（hdpat2026 78–84）；(c) HDPAT 用 MGPUSim 仿真，P1 要求实物可测；(d) HDPAT 未把"仅有队列内合并"作为独立强基线去比较（它把 Barre 作为对手，hdpat2026 711–713, 673–681）。
   来源：`.../papers/hdpat2026.txt` 555–604, 854–863；URL: https://sarchlab.org/hdpat_hpca_2026.pdf
2. **IDYLL 的 PTE directory**：用目录过滤不必要失效，是"谁可能持有副本"的在场信息，其目的是**失效过滤**而非 walk 剪枝/请求整流；真机双 A100 剖析显示约 42% 执行时间耗在失效，但方案收益来自 MGPUSim（map 41, 122；RR 12）。
   **精确差别**：IDYLL 的目录方向相反（为失效服务），且不测排队/吞吐边界。**[待核：IDYLL 全文]**
3. **Barr translation cache 的索引性**：虚拟索引使查找可乱序/并行，且"一个 L2 项即可覆盖"（translation_cache2010 352–362, 408–416）。
   **精确差别**：Barr 的项**存翻译内容**（是缓存）；P1 的目录**不存翻译内容**（是位置/在场），二者容量-收益量纲不同。这是 P1 与"再加一层缓存"的本质区别。来源：`.../papers/translation_cache2010.txt`；URL: https://cs.rice.edu/CS/Architecture/docs/barr-isca10.pdf
4. **Revelator Bloom hint**：有损、非关键路径、按 VA 索引，但只指 NUMA 节点，不指翻译副本位置（revelator2026v2 769–797）。**[待核：SpOT/DMT/ASAP/ECH/Mosaic Pages 等 Revelator 对手全文]**

**重叠风险判断**：与 HDPAT 重叠最高；与 IDYLL、Barr 属不同用途的"同类结构"。新意必须落在**抽象 + 边界**，不能落在"发明一个 VA 索引表"。

### 2.3 一句可被推翻的研究主张

> **在由受限 PTW 并行度主导的 queue-limited 区间内，一个"不存翻译内容、不产生反压"的 VA 键翻译位置/在场目录，仅凭位置信息即可把共享 IOMMU 的翻译完成时间压到 (a) **等面积 IOTLB** 与 (b) **仅 PW 队列内请求合并**这两种强基线之下；其收益随发起者数量单调上升、随复用距离衰减，并在"每个 VPN 仅被翻译一次"的负载上归零。**

（可被推翻点：若在 queue-limited 区间内，"仅队列内合并"已经吃掉全部收益，或目录容量必须随工作集而非 churn 增长——即它退化为缓存——则主张失败。）

### 2.4 因果链、代价、关键假设与最可能致命反例

**因果链**：walker 并行度固定 → 突发下排队（hdpat2026 148–158, 182–201）→ IOTLB 命中可减少请求，但**未命中的请求会占用 MSHR/outstanding 并可能阻塞**（hdpat2026 600–603 明确指出"当 MSHR 满时，后续请求被挡在 TLB 外，无法享受 PW 队列重访机制"）→ 目录不占 MSHR、不存内容，只回答"该 VA 的翻译正在/已在某位置"，从而支持**合并与转发**（hdpat2026 569–591 的整流逻辑）→ 到达 walker 的请求数下降。

**代价**：目录本身有面积/功耗（HDPAT 1024 项 = 0.034 mm²、0.16 W、CPU tile 的 0.02% 面积 / 0.09% 能耗，hdpat2026 917–924）；假阳性会多一次跳并可能使延迟翻倍（hdpat2026 139–146）；目录未命中仍需回退完整 walk；维护一致性需要失效语义（map 41, 132；RR 14）。

**关键假设（未验证）**：
- **H1【假设】**：目标负载的 miss 路径确实是 **queue-limited** 而不是单次 walk 延迟受限。
- **H2【假设】**：存在复用——同一 VPN 在窗口内被多次请求或在途重叠。
- **H3【假设】**：目录的更新一致性可沿用现有 IOTINVAL/IODIR/IOFENCE，不额外引入新的正确性风险（map 132；RR 14）。

**最可能致命的反例（有原文证据）**：
- HDPAT Observation O3 显示 **AES、RELU 等每个虚拟页整个执行期只触发一次 IOMMU 请求**——此时"复用"不存在，缓存/目录都没用（hdpat2026 320–326）；BT 因强空间局部性由本地 GMMU 解决，几乎无远程请求（hdpat2026 692–695）。**若项目上的设备负载是流式 IOVA（每次不同），P1 直接归零。**
- 第二反例：HDPAT 的 PW-queue 重访（"handle identical pending requests"，hdpat2026 578–580）说明**在途重复请求本可在队列内免费合并**；若如此，目录是冗余的——这正是必须做判别实验的核心。

### 2.5 最强普通方案与低成本"杀死候选"实验

**强普通方案（不得弱化）**：
- (B1) **等面积 IOTLB 扩容**：HDPAT 已用等面积 TLB 对照，重定向仅 1.27×（hdpat2026 854–863, 512 vs 1024 项）。
- (B2) **仅 PW 队列内合并**：HDPAT 的 "revisits the PW-Queue"（hdpat2026 578–580）与 Barre 的 PW 队列机会（hdpat2026 711–713）。
- (B3) **加 walker**：HDPAT 的上界实验（hdpat2026 182–201）。

**判别实验（FPGA 可做）**：
1. 用 4 个 iDMA 生成小传输突发，构造两种翻译请求复用距离 d：(a) d=1（同一 VPN 窗口内重复/在途）、(b) 无复用（每页一次）。
2. 扫描 PTW 容量（受平台可配即可）。
3. 比较三条曲线：**(A) 基线 + 等面积 IOTLB**、**(B) 仅队列内合并**、**(C) 位置目录**，指标用 IOTLB miss、PTW 队列占用、翻译完成时间、小 DMA 完成时间。
4. **停止条件（任一即淘汰）**：(i) 在 d=1 的所有点 C 都不显著优于 B（说明合并已吃掉收益）；(ii) 在无复用点 C 无收益且带来开销（与 hdpat2026 320–326 一致，说明应用窗口不存在）；(iii) C 所需容量随工作集而非"在途/churn"增长（说明它退化为普通缓存，抽象不成立）。

**应用真实性门槛**：只允许用平台可测的 IOTLB/PTW/小 DMA/ map-unmap churn 指标做主张，不得外推到 100–200 Gbps IOTLB wall、多租户 GPU walk stealing、wafer-scale（map 184）。

### 2.6 成功/失败产出与平台依赖

- **成功可写什么**：一篇"**翻译目录层**"的抽象与边界论文——给出目录（位置/在场）与缓存（内容）、与 walker 容量三者之间的**定量可替换边界**，并把 HDPAT 重定向、IDYLL PTE directory、Revelator Bloom hint 统一为一个设计空间；落点可为 HPCA/MICRO/ISCA 或 ASPLOS（系统+体系结构）。
- **失败留下什么**：**"共享 PTW 下，一阶量是请求数还是命中率"** 的负面证据，以及 HDPAT 结论向"多设备小 DMA、非 GPU、非晶圆级"迁移的边界；即使失败也回答"HDPAT 1.27× 是否可推广"。
- **现有 FPGA 能做什么**：IOTLB/PTW 计数与归因探针、小 DMA 干扰、map/unmap churn、可加低面积目录/直方图原型（map 184 已列此项为候选测量用途）。
- **必须依赖什么**：GPU 多租户 / wafer-scale / 真实高速网卡（map 184）。

## 3. 候选 D1-P2：放置不变量的"可预测性预算"——复合是否可加，更新代价如何随规模走

### 3.1 真实应用、具体触发条件与"为什么现在"

**应用条件**：同一虚拟地址空间上需要**同时**满足多个由 VA 索引的物理放置约束——分区/哈希可预测性（SPARTA、Revelator）、NUMA 节点作用域（Revelator §4.6）、大页机会（THP，revelator 690–733）、安全熵（SPARTA Table 1 的 entropy 行，sparta2020 203–215, 241–242, 407–409）。

**触发条件（有原文支撑）**：
- Revelator 自身把 hash(4KB) 与 THP、NUMA 用**优先级回退**串联，而不是联合求解：`2MB hash → 传统 THP → 4KB hash → buddy`（revelator 690–733, 708–732）；NUMA 是"policy-first node-scoped hashing"，先选节点再在节点内 hash（revelator 742–756）。
- Revelator 自己的 k 页实验显示：**约束一旦从 1 页扩到 k 页，分配成功率在低/中碎片下快速坍塌，即便有 4 个独立 hash 层**（revelator 664–689, Fig 7）；这已是"约束叠加非可加"的强暗示。
- SPARTA 明确承认分区与 **page coloring**"可能正向或负向干扰"，但只说"未来工作"（sparta2020 1034–1045）；共享/重映射页必须**调整 VA 区域**去迁就既有物理分区（sparta2020 563–589）；分区下的 CoW 压力会"带来更多换页"（sparta2020 609–616）。
- 碎片与竞争随规模恶化：16 核下 THP 的 L2 TLB MPKI 比 4 核涨 >20%，而 Revelator 精度稳定在 87–88%（revelator 1202–1214）。

**为什么现在值得研究**：碎片与多租户使"连续性"假设普遍失效，领域正转向"**用 OS 构造的放置不变量换取翻译可预测性**"（Revelator、SPARTA）。但**没有工作研究多个不变量同时成立时的联合可行性**，也没有把"读路径收益"与"**更新路径代价**"放在同一张曲线里。Revelator 只报稳态缺陷成本：真机上 minor fault 延迟比 Linux **低 19%（Linux 更低？原文：baseline Linux's minor fault latency is on average 19% lower than Revelator's）**，即 Revelator 故障处理更慢，但占总时间仅 0.078% vs 0.063%（revelator 888–909）。**这恰恰是"不变量把代价从读路径挪到更新路径"的直接证据，只是被稳态掩盖了。**【事实 + 推断】

### 3.2 最接近的先行工作与精确差别

1. **Revelator v2（最接近）**：证明 hash 放置的精度只取决于内存利用率、不取决于碎片（revelator 68–91, 558–569），并把 PTE 也做 hash 放置（revelator 580–603）。
   **精确差别**：它**只研究单一不变量族（tiered hash）的稳态行为**；与 THP/NUMA 是**优先级回退而非联合**；未做 churn 扫描，未做多发起者失效扇出，未给"多不变量叠加"的可行性边界。来源：`.../papers/revelator2026v2.clean.txt`；URL: https://arxiv.org/pdf/2508.02007v2
2. **SPARTA**：分区不变量 + 数据/PTE 同分区 + Linux 4.10 真机原型（sparta2020 20–31, 383–399, 526–600, 669–672）。
   **精确差别**：SPARTA 的"分区内任意位置"是**极弱不变量**（数百万选项，sparta2020 226–232），与 Revelator 的逐页 hash 属不同强度；它指出分区与 page coloring/CoW/共享重映射的张力，但**没有量化"不变量强度 × churn × 发起者数"的代价曲线**。来源：`.../papers/sparta2020.txt`；URL: https://arxiv.org/pdf/2001.07045
3. **IDYLL / RISC-V IOMMU 队列语义**：失效是一阶成本（真机 42%，map 122；RR 12）；标准支持按上下文/地址失效，但也**允许简单实现扩大为全局失效**（map 41, 132；RR 14）。
   **精确差别**：IDYLL 研究 GPU PTE 失效的过滤，不研究"放置不变量把重映射代价推高"；RISC-V 语义说明代价可随实现变化，正是 P2 需要测的量。**[待核：IDYLL 全文；RISC-V 队列文档 §319–355（RR 14 给出的行段）]**

**重叠风险判断**：与 map 卡点3（动态放置与更新代价）部分重叠；新意必须落在**"复合不可加 + 未读/写路径代价交换曲线"**这一**定量边界**上，而非重述"失效有代价"。

### 3.3 一句可被推翻的研究主张

> **多个 VA 索引放置不变量（分区/哈希、NUMA 节点作用域、大页机会、熵/安全）的联合分配成功率不是各自成功率的乘积，而是以快于乘积的速度衰减——即"可预测性预算"不可加；因此存在一个最大可用不变量数与一个可行组合区域，超过后应主动退回更弱不变量。该衰减由空闲帧的结构决定，而不是由碎片百分比单独决定。**

（可被推翻点：若把各不变量设计成作用于地址的不同位段、彼此近似正交，则联合成功率≈乘积，"预算不可加"被证伪。）

### 3.4 因果链、代价、关键假设与最可能致命反例

**因果链**：每个不变量都把可分配帧集收缩为一个子集（SPARTA 分区、Revelator hash 候选、NUMA 节点、大页对齐）→ 当多个不变量同时要求，候选集是交集 → 在不变量数增加时，交集非空概率以**快于各概率乘积**的速度下降（因为各不变量都在争夺同一批"富余"空闲帧/低碎片区域）→ 分配回退到传统分配（立即失去可预测性）→ 读路径收益塌陷；同时，一旦某 VA 的 PA 需要改变以满足不变量，每个持有副本的发起者都要失效（IOTLB/在途请求），**更新代价 ∝ 持有者数**，从而把"读路径收益"抵消。**【推断，需实验判定】**

**代价**：分配延迟与失败率（revelator 890–909 已给出 +19% minor fault 延迟的量级）；重映射后的失效扇出（map 41, 132）；可能牺牲大页/熵（sparta2020 203–215 明确列出各方案在 CoW/碎片/保护/安全上的取舍）。

**关键假设（未验证）**：
- **H4【假设】**：存在非平凡 churn（映射会被改写），否则更新代价可忽略——**注意：设备侧 DMA 缓冲常一次性 map、生命周期内不改**，这会直接杀死"规模放大更新代价"的论证。
- **H5【假设】**：失效代价随持有者数增长——**在允许全局失效的实现上不成立**（map 41；RR 14），平台可能正是这种实现。
- **H6【假设】**：OS 无法总是通过"调整 VA 去迁就既有 PA"来消除重映射——但 **SPARTA 恰恰是这么做的**（sparta2020 563–589）。

**最可能致命的反例**：**H6 被 SPARTA 直接反驳**——对共享/重映射页，SPARTA 调整虚拟区间使其分区序列与既有物理页一致，于是"满足不变量"**不需要移动物理页、不需要失效**。若 OS 对目标工作负载也能自由选 VA，P2 的更新代价项消失，主张退化为"应使用足够强的不变量"，无新论文。**因此 P2 的真实应用必须限定在 VA 不可自由移动的场景**（应用固定 VA、page-locked/硬件描述符、共享库映射等）。**【推断，是本候选最大的脆弱点】**

### 3.5 最强普通方案与低成本"杀死候选"实验

**强普通方案（不得弱化）**：
- (B1) **Revelator+THP 的优先级回退**（revelator 690–733）——已经在复合场景下工作，P2 必须证明"联合"显著优于"回退"。
- (B2) **SPARTA 的 VA 调整**（sparta2020 563–589）——可能直接消灭重映射代价。
- (B3) **传统 THP + 常规分配**（revelator 991–1028：低碎片下 THP 已很强，L2 TLB-64K 也只多 ≈3–4%）。

**判别实验（部分可在 FPGA 测，核心需 Linux 内核原型）**：
1. 在平台上给 IOMMU 映射引入**软件不变量强度旋钮**：(L0) 无约束、(L1) 连续 PA/大页式、(L2) VA 索引 hash 放置；**不变量数**从 1 增到 3（+NUMA 作用域 / +对齐）。
2. 在固定内存利用率、扫碎片（低/中/高，参照 revelator 956–964 的定义：可用 2MB 页比例 90%/50%/10%），测**联合分配成功率 vs 各不变量成功率之积**；再扫 churn（map/unmap 速率）与发起者数（1 vs 4 iDMA 上下文），测 **总代价 = 分配延迟 + map/unmap + IOTINVAL/IODIR + 重填充**。
3. **停止条件**：(i) 观察到联合成功率≈乘积（可加）→ 主张被证伪，P2 淘汰（留下负结论：不变量可组合）；(ii) 在所有平台上可达的 churn 速率下，受约束映射的额外总代价 < 真实负载总时间的 ~1%（与 revelator 906–909 的 1.25% 同量级）→ 不变量无条件安全，P2 不成立；(iii) IOTINVAL 在本实现上是全局且 O(1)，导致代价与发起者数无关 → 规模论证在本平台不成立（此时需换有按上下文/地址失效的平台）。

**应用真实性门槛**：不得用"每个 I/O 都 map/unmap"这种不真实模式；必须给出目标负载的真实 churn 与 VA 可动性证据。

### 3.6 成功/失败产出与平台依赖

- **成功可写什么**："**翻译可预测性预算**"的定量边界论文——给出多不变量联合可行性区域、读路径收益与更新路径代价的交换曲线，并回答"何时应退回更弱不变量"。落点可为 ASPLOS/ISCA/OSDI 类（OS + 体系结构）。
- **失败留下什么**：**"放置不变量是可加的"** 或 **"稳态结论在 churn 下仍成立"** 的负面证据，这本身对 Revelator/SPARTA 的推广边界有价值。
- **现有 FPGA 能做什么**：map/unmap 与 IOTINVAL/IODIR 代价测量、IOTLB 重填充、小 DMA 干扰、不同上下文数的失效扇出（map 184）。
- **必须依赖什么**：Linux 内核分配器原型（Revelator 式，revelator 128–129, 946–954）、高碎片/高竞争的真实或仿真系统（revelator 956–964）、以及**支持按上下文/地址失效的 IOMMU 实现**；多不变量联合与碎片扫描更适合仿真/内核原型，不适合仅靠本 FPGA。

## 6. 假设与不确定项（供 R2 定向质询）

1. **【假设】** P1 的核心前提"miss 路径是 queue-limited"**尚未在本平台验证**；若平台 PTW 并行度充裕，P1 归零。
2. **【推断】** "目录容量随 churn 而非工作集增长"这一子假设**可能被 IDYLL 反例削弱**（失效过滤目录的容量更接近已映射页数）；两者可能把目录设计拉向相反方向，这本身是可发表的边界。
3. **【不确定】** 本平台的 IOMMU 失效粒度究竟是按上下文/地址还是被实现为全局；若是全局，P2 的"代价 ∝ 发起者数"不成立（map 41；RR 14）。
4. **【不确定】** 设备侧 DMA 映射的真实 churn 率与 VA 可动性；这是 P2 的**生死条件**（H4/H6）。
5. **【不确定】** HDPAT 的 1.27×（等面积 TLB 对照）是 MGPUSim 结论，迁移到"多设备小 DMA + 实物 IOMMU"是否仍成立，**必须实测**。
6. 本席未读取任何其他席材料，也未运行实验；以上所有"收益/边界"均为待验证主张，不构成已交付结果。
