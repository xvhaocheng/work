## 0. 地图的因果结构与一个可能的系统性遗漏

**因果结构（我的读法）**
- 地图的主干因果是：规模、共享、动态性、低可见性同时出现 → 翻译代价转移。[E] 地图把困难落在"这些条件相遇时的代价"上（research-landscape:9）。
- 六个卡点里有四个本质上是**控制面代价**，不是数据面代价：
  - 粒度切换（:35）
  - 失效与更新（:41）
  - 观测成本（:44）
  - 布局与可编程性（:47）
- 但研究线总表第一行和第六行仍以 TLB reach、PTW 时延、walker 数量为中心（:15、:50）。

**可能的遗漏或过度概括：地图默认"翻译时延在关键路径上"，没有把"可见性点决定翻译是否关键"当作一等变量。** 本方向四篇原文给出了反例和旁证：

- **GPS** [E]：远程写在下一个同步边界前不必可见，因此"address translation unit 的时延不是关键因素，即使发生 TLB miss"（gps2021:489-493）。GPS-TLB 只用 32 项，命中率就接近 100%（gps2021:1210-1217）。
  - [I] 一旦语义允许延迟可见，翻译时延就离开关键路径。真正的约束转到同步点的排空、塌缩和失效上：sys-scoped 写会触发 fault、flush 和页塌缩（gps2021:573-581）。
- **MINISA** [E]：在可重构阵列上，瓶颈不是计算或数据，而是控制信息的搬运。
  - 16×256 规模下，取指停顿占 micro-instruction 周期的 96.9%（minisa2026:43-44, 232）。
  - instruction-to-data 比约为 100×（minisa2026:113-114）。
- **WIC** [E]：它把 UVM 的缺页/重放机制（一种翻译控制面）改作 warp 级同步原语（wic2025:489-507）。
  - 这条通道有硬上限：UVM 一次只能处理 256 个 fault，超出部分排队成为瓶颈（wic2025:877-880）。
- **NDS** [E]：一条多维命令替代了 8192 次 I/O 请求（nds2021:152, 528-535）。设备侧 STL 翻译每次增加 17–41 µs，但能被大块访问摊销（nds2021:1384-1398）。

**[I] 综合判断**：在地图覆盖范围之外的条件下，扩展瓶颈常常落在翻译的**控制面**：命令、失效、fault 通道、控制字节与数据字节之比。这些控制面又是**跨租户共享**的。

**[R] 对本平台的含义**：惯性路线是"更大/更快的 IOTLB/PTW 数据面"。这条路线已有 Victima、IOTLB wall 等强对手（:173）。如果平台的 DMA 写语义允许延迟可见，这条路线还可能根本不在关键路径上。我建议不默认继续它，而是先做第 1 节 P1 的判别实验。

**另一个题录层面的疑似遗漏（待核）**：地图没有收录面向嵌入式异构 SoC 的轻量 IOMMU/MMU 研究线，例如 ETH/PULP 的 Vogel、Kurth 等人关于 accelerator 虚拟内存、TLB 预取和 "MMU-aware DMA engine" 的工作。它们与本平台的 iDMA + RISC-V IOMMU 架构最近。如果存在，就是任何"描述符驱动预翻译"类候选的头号先行工作。
- 正因为这个重叠风险，我**主动放弃**了一个候选："N 维 iDMA 描述符的地址足迹在发出时已知，可做批量预翻译"。这个想法受 NDS 和 MINISA 启发，但我判断重叠风险过高，不列为正式候选。

## A6-P1：共享 IOMMU 的翻译控制面（失效与 fault 通道）是跨设备时间耦合的独立来源

### 1. 真实应用、触发条件、为什么现在

**应用场景**
- 混合关键性 SoC：车载场景中，摄像头或控制回路的周期性 DMA 与网络/存储驱动共享同一个 IOMMU。
- 云端多租户 I/O：一个租户在 strict 模式下按包或按请求 map/unmap，另一个租户是延迟敏感型。

**具体触发条件（四项需同时满足）**
1. 关键设备的映射是静态的。按传统观点，它"不受映射变化影响"。
2. 同一个 IOMMU 上，另一设备的驱动以高频率执行 unmap → IOTINVAL → IOFENCE。
3. IOMMU 实现把失效扩大到更大范围，或者命令队列处理与 PTW/IOTLB 查找串行共享同一引擎。
4. 关键设备的指标是尾时延或截止期，不是吞吐。

**为什么现在**
- [E] 失效扩大是规范允许的：RISC-V IOMMU 规范允许简单实现把按上下文/地址的失效扩大为全局失效（research-landscape:41；ROOT_REVIEW:14）。所以这不是"实现缺陷"，而是规范内合法的设计点。
- [E] 地图列出"更广实时 QoS/形式化界"为未覆盖范围（research-landscape:188；ROOT_REVIEW:38）。
- [E/I] fault 通道正在被挪作他用：WIC 用缺页做同步（wic2025:489-507），RDMA ODP（待核）用缺页做按需注册。fault 和失效通道的负载会上升，而它们恰恰是共享的、有容量上限的（wic2025:877-880）。
- [I] 已有文献主要从容量竞争和 walker 竞争角度研究共享干扰（MASK、DWS、Bermuda，见 :38, :92）。我没有在材料中看到以"另一租户的控制面操作率"为自变量、以关键设备尾时延为因变量的定量研究。**但这只是"给定材料中未见"，不是"不存在"。**

**[I] P1 的新意边界**：不是"失效有代价"（已知），而是三点：
1. 失效对**第三方静态映射设备**的时间传播；
2. 规范允许的失效扩大和命令处理串行化，作为可调的实现参数；
3. 由此得到的定量边界，用于判断这类干扰何时超过容量干扰。

### 3. 可被推翻的主张

> 在共享 RISC-V IOMMU 上，即便关键设备只使用静态映射，另一设备的驱动以现实频率（Linux strict 模式下的逐请求 unmap）发出失效时，关键设备 DMA 的 p99 时延膨胀**大于**同一负载下 IOTLB 容量争用造成的膨胀；而且这种膨胀主要由失效范围和命令处理串行化决定，IOTLB 分区或 way 划分无法消除它。

推翻条件（任一成立即可）：
- 失效引起的膨胀小于容量争用引起的膨胀；
- 或者，在实现了精确失效后，膨胀消失到噪声水平。

### 4. 因果链、代价、关键假设与最致命反例

**因果链** [I]
1. 租户 B 执行 unmap，写入命令队列（IOTINVAL + IOFENCE）。
2. 两条可能的路径：
   - a. 失效被扩大，清掉租户 A 的 IOTLB 项，A 随后重走 PTW；
   - b. 命令处理占用 IOMMU 的共享流水线或 PTW 端口，A 的查找排队。
3. 结果是 A 的单次 DMA 时延出现长尾。

**代价与可选解**
- 精确失效需要按 GSCID/PSCID/地址范围匹配的硬件，增加面积。
- 命令与查找并行处理需要多端口。
- 软件侧缓解办法是 lazy/flush-queue。但这会引入保护窗口（:89）[E]，并且把多次失效合并成更大、更突发的失效。

**关键假设**
- [A1] 平台 IOMMU 的失效实现是"扩大"或"与查找串行"。**未知，需读 RTL 核实。**
- [A2] Linux RISC-V IOMMU 驱动在 strict 模式下逐次发出失效。**待核。**
- [A3] 存在真实场景：关键设备与高 unmap 率设备共享同一 IOMMU 实例。

**最可能致命的反例**
- 如果平台实现已做精确的 PSCID/地址失效，并且命令处理与查找互不阻塞，那么机制 a 和 b 都不成立。此时问题退化为"实现质量"，不构成论文问题。
- 另一个反例：真实系统中关键设备通常被放进独立 IOMMU 实例或 passthrough 模式，这个场景本身就会被工程手段绕开。

### 5. 最强普通方案与低成本判别实验

**最强普通方案（必须同资源比较）**
1. 关键设备用 identity/passthrough 或独立 IOMMU 实例；
2. B 用 Linux lazy flush queue；
3. 关键设备用静态大页映射加 IOTLB way 分区（KPart 思路，:78）；
4. 精确失效的实现（规范已允许，:41）。

只有当 1–4 都不能以可接受代价解决时，P1 才有论文空间。

**判别实验 K1（静态审查，几乎零成本）** [R]
- 先读平台 IOMMU RTL 和 Linux 驱动，回答三个问题：
  - IOTINVAL 是否按 PSCID/地址精确匹配？
  - 命令处理是否与 IOTLB 查找/PTW 共享端口？
  - strict 模式下每次 unmap 是否发出 IOFENCE？
- **停止条件**：三项都是"精确、并行、批量"，则 P1 在本平台不成立，转为只做文献性定量综述或放弃。

**判别实验 K2（上板，未来轮次，本轮不做）** [R]
- 设置：
  - iDMA-A：周期性 4 KB 读，映射静态，用 cycle counter 记录每次时延分布；
  - iDMA-B 的驱动循环 map/unmap，操作率 R 从低扫到平台可达上限，分 strict 和 lazy 两种模式；
  - 对照负载：B 只做 IOTLB 容量冲刷，不做失效。
- 判据：
  - A 的 p99 膨胀 Δ_inval(R) 与 Δ_capacity 的比值；
  - 并核对平台可达的 R 是否落在真实驱动的 unmap 率范围内。
- 真实 unmap 率需从网络/存储文献取得：IOTLB wall（:90）和 IOMMU Scalably（:89）的场景，**数值待核**。
- **停止条件**：在真实 R 范围内 Δ_inval < Δ_capacity，或 Δ_inval < 5% p99。（5% 是我暂设的阈值。）
