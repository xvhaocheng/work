# C4 · R1 独立研究：数据表示、执行接口、间接访问与搬运

作者席位：Codex C4。日期：2026-10-06。已独立阅读共同地图、ROOT_REVIEW、DAE、IMPICA、DX100、Tiara，定向检查补充原始来源；没有读取其他席提案，没有采用旧讨论的候选优先级，没有修改源码或运行实验。

**结论：保留一个有明确否定门槛的问题候选 C4-P1，暂不提出已成立的新架构。最值得核查的是：批量间接访存一旦失去静态大页与整块就绪的方便条件，搬运窗口应该按多少个元素划分，还是按翻译需求和下游可开工的最小数据组共同划分？“按页分组”“异步重放”“访问计算解耦”本身均不是新意。** 若真实应用的内存池已经把这一条件维持住，或强软件分组已经覆盖性能空间，应立即淘汰，不转而制造人为碎片。

## 1. 我看到的因果结构，以及地图需要补的边界

地图把问题划为翻译、共享、生命周期和搬运是有用的，但从程序到性能的链条还应写清楚：**谁产生下一批地址 → 哪些地址现在可独立发出 → 允许怎样重排及合并 → 地址如何翻译 → 数据在哪里服务 → 哪个下游计算必须等齐哪些结果**。瓶颈可能位于任一箭头；“indirect”一词不足以决定架构。

- DAE 的贡献首先是允许访问流领先计算流；它已经处理存储依赖和队列死锁。因此增加访问队列、双流执行并不是新的抽象。[DAE 原文](https://people.eecs.berkeley.edu/~kubitron/courses/cs252-F00/handouts/papers/p231-smith.pdf)，本地 `out/research-landscape-20261005/papers/dae1982.txt`，§2、§3、§8。
- IMPICA 降低单条链的节点服务距离，同时靠多条链交错获得并行；它没有把真正依赖前一个返回值的链改造成任意并行的散读。其区域页表、专用分配及 CPU/加速器数据访问分工也属于成本条件。[IMPICA 原文](https://pdl.cmu.edu/PDL-FTP/associated/16iccd_impica.pdf)，本地 `impica2016.txt`，§3–5，特别是 435–456 行。
- DX100 的关键不是“能发 gather”，而是看见足够大的索引窗口并利用物理地址做行局部性、合并和 bank/channel 交错。它同时要求合法的独立循环和写所有权。值得追问的前提是大页、256-entry TLB，以及 PTE 在应用生存期中一次预装。[DX100 原文](https://arxiv.org/pdf/2505.23073v1)，本地 `dx1002025.txt`，§3.2、§3.6，432–446 行；§4.2，499–513 行。
- Tiara 把远端应用间接表的解释移到 NIC；其批处理 PagedAttention 对手应是 2 RTT。它也已经把解表与传输流水起来，不能把“查到一项立即发传输”当新方案。[Tiara 原文](https://arxiv.org/pdf/2606.13708v1)，本地 `tiara2026.txt`，Table 1，82–98 行；§3.2，320–327 行；§4.6，481–504 行。

**一个实质性补充：地图还低估了软件对手。** Milk 已有延迟访问、协程式 collection/distribution/delivery、TLB 与缓存容量约束、DRAM bank 排布，以及需要时保留串行次序；AMAC 已经按 lookup 保存独立状态，适应可变链长和早退。不能把软件对手写成“朴素按原顺序逐个访问”。[Milk 原文 §3、§5.2](https://commit.csail.mit.edu/papers/2016/kiriansky16pact-milk.pdf)、[AMAC 原文 §3](https://www.vldb.org/pvldb/vol9/p252-kocberber.pdf)。本轮补充阅读范围见[来源记录](../sources/C4-source-notes.md)。

**一个证据性质更正：Tiara 不是主要性能全由 FPGA 实板测得。** §4.1 明确：Tiara latency 使用 Verilator 周期模型；饱和吞吐按延迟和 8 MPs × 12 outstanding tasks 推导；主要非 Tiara 对手是分析模型。BF-2 对照图是物理 NIC 测量，单 MP FPGA build 有布线后时序。正文还给出 RPC 在部分条件下胜出的情况。因此它可以证明已有设计思路，主要性能图不能直接充当部署收益证据。参见本地 `tiara2026.txt` 348–378、395–408 行。这个更正不等于判定整篇无效。

## 2. C4-P1：让批量间接搬运的窗口同时对应翻译需求与下游可开工的数据组

### 2.1 真实应用、触发条件和研究边界

首选核查场景是**自适应科学计算在重网格或粒子重新分布后，多个 patch/计算块的非规则 gather**：逻辑索引已能批量产生，各块收齐自己的输入后即可独立计算；有些源数据会被多个块重复读取。DX100 的 AMR/UME/xRAGE 动机说明这类间接访问有应用基础，但其代理负载不能证明实际运行存在我们需要的映射条件，二者必须分开。

候选只有在下列条件同时出现时才成立：

1. 一段真实 gather 的不同有效页数 `U(W)` 超过可用于该工作集的翻译容量，且软件预取/普通 miss 合并不能把余下翻译成本隐藏掉。
2. 应用确有多个可独立开工的消费组。消费组 `g` 指“必须拿齐集合 `R_g` 才能运行的一次真实计算”，不是为了结果好看人为切出来的任意数组片段。
3. 索引批次中的重复访问、页局部性或行局部性足以奖励跨组聚集；与此同时，聚集到大批次或等全批完成会推迟部分消费组的真实关键路径。
4. 长期大页区域、内存池、一次预装所有映射，或先复制成紧凑数组，在相同内存预算下不能免费解决问题。

这里的“动态”不等于允许任意时间释放仍在使用的页。首个研究范围可只处理**合法读阶段内映射稳定、阶段间允许换映射**；不发明新的失效规范，不要求全系统 quiet。首先研究性能，现有生命周期约束照常执行。

为什么现在值得核查：DX100 2025 的公开设计把大量索引可见性变成了性能资产，却明确采用很强的翻译预装条件；现行异构应用的池化/流式分配又可能让该条件足够合理。两种解释都可信，真正欠缺的是把地址集合、底层映射和下游开始计算的时间放在同一条应用证据链上。**是否存在这个缺口尚未得到实测证明。**

特别保留反证：AMReX 官方文档已有大规模 arena、长期保留数据和异步安全分配。regrid、短命对象及逻辑索引变化，都不自动推出 OS 映射频繁更新或物理小页碎片。[AMReX Memory Arenas / Async Arena](https://amrex-codes.github.io/amrex/docs_html/GPU.html)。如果真实应用因此长期维持良好翻译覆盖，本候选应在应用门槛处停止。

### 2.2 一句可推翻的主张

**在实际存在上述四个条件的应用上，用消费组及有限翻译工作集共同形成搬运窗口，能在相同总缓冲和相同结果语义下，比调优后的大页/池化、软件按页分组、普通细分 tile 与 DX100 式物理重排取得额外的端到端收益；这种收益不能仅由增加在途数或放宽浮点/顺序语义解释。**

这不是“所有 gather 都更快”的主张。预先采用一个立项判据：在至少一个完整真实应用阶段有超过 15% 的净时间收益、其余关联阶段的代价已计入，并在另一类实际索引/分配轨迹仍可解释同类现象。15% 是建议的研究筛选门槛，不是测量结果或理论常数；如果最佳普通方案与理想上界仅差 5%，无需继续造硬件。

### 2.4 一个可检查的机制草案，而非堆组件

输入描述只增加每个元素所属的消费组和源逻辑地址；同一源可对应多个组。第一版只允许只读源及无别名的独立输出，不同时承诺一般 RMW、逐位浮点确定性和并发写。

内部有两类有限状态：尚未取全输入的消费组，以及为当前发出批次准备的页/地址元数据。调度可按页合并访问，也可提前结束聚集以完成一个能解锁后续计算的组。结果写到该组原有目标位置，组完成后发送就绪通知；不必恢复整个大索引 tile 的全局次序，但**组内部需要的逻辑位置与值完全保留**。CPU/GPU 是否真的能及时消费，必须连同通知、同步与 kernel 启动计入。

这份草案故意允许普通对手实现相同的组切分与通知。若它只是“把 tile 切小”，或一个软件贪心调度即可得到相同结果，应报告这一事实。只有现有方案因缺少可表达的消费依赖、有限翻译状态与返还粒度之间的结构性矛盾而留下可测差距，才值得继续。

### 2.5 因果链、资源与最危险的反例

假设的因果链是：大索引窗口增大可合并/可重排机会，但也增大有效页集合和未完成消费组数；地址转换与数据返回延迟不均，使部分组迟迟无法开工；暴露组完成条件后，可用有限的跨组局部性换更早的真实消费。收益不是单看 IOTLB miss 数或 row-hit。

对一个窗口记录 `N`（引用数）、`U`（不同有效页数）、`L`（不同 cache line 数）、`C`（可用翻译项数）、`B`（全部中间状态字节）、各 `R_g` 与消费耗时。简单资源下界至少包含 `max(翻译服务需求/服务率, 数据字节/带宽, 依赖关键路径, CPU提交与消费成本)`；这只是下界，不是把四项加起来的性能预测，队列和重叠需要实际事件顺序。

不可隐藏的成本包括：扫描索引、建页分组和去重、源到多个消费者的 fan-out 元数据、跨页元素处理、目标写入/缓存维护、就绪位与通知、翻译 miss 合并表、PTW 流量、生命周期约束、对其他请求者的排队影响。全部 SRAM 预算统一计，不许把页表缓存、reorder buffer 或 shadow copy 移出表格。

最可能致命的五个反例：

1. **内存池＋大页已经足够**：逻辑数据动态，但物理映射长期不变，翻译耗时没有上关键路径。
2. **页排序也保留主要行局部性**：实际地址映射使两个顺序近似嵌套，所谓双目标冲突不存在。不能预设“按页排序必然破坏 DRAM 局部性”。
3. **消费者必须全批 barrier**：没有能提前开工的真实组，额外就绪接口只增加成本。
4. **软件分组/小 tile＋pipeline 已接近上界**：所谓新信息在应用运行时本来可见，普通接口就能表达，额外硬件无独立贡献。
5. **复制或布局重建更便宜**：数据或索引重复使用次数足够，一次 compact/pack 的成本被摊销；保留零拷贝的执念反而较差。

还应保护一个正确性反例：若要从只读扩至 scatter/RMW，必须说明重复目标、WAW、别名以及浮点次序。DX100 的 associative/commutative 表述不能让普通浮点加法自动获得严格结合律；第一候选不以数值语义放宽赚速度。

### 2.6 最强基线与最低成本的否定步骤

**在开发任何新 RTL 前，先做 A，再做 B；本轮均未执行。**

**A．应用真实性与收益上界。** 选实际有重网格/重分配的完整应用阶段，保留默认高性能 arena；记录逻辑索引、分配/映射粒度与持续时间、消费依赖、同步点和各阶段墙钟时间。至少同时评估池化/大页可行配置与实际内存预算。不要把 UME 的静态随机索引直接宣称为动态生产轨迹。再做两个理想反事实：翻译零成本；消费组可以在最后一个必要输入返回时零通知开工。它们用于估算上界，绝不称为实物可实现结果。

停止条件：拿不到实际页/映射信息；应用阶段并非瓶颈；优化后映射稳定且翻译完全隐藏；消费者只有全批 barrier；或任一理想反事实也不足以留下有意义的端到端空间。此时不进入硬件设计。

**B．用普通方案杀机制。** 对同一批请求和真实依赖，比较以下适用配置的 Pareto 最优点，不只比较默认参数：

- 生产池化/大页/预分配；compact 数据或预先 pack 输入，包括实际复制及摊销。
- Milk 式软件分组、按虚拟页稳定排序、编译器预取；扫描和中间数据读写全计。
- 调优后的 DX100 式重排：合理 demand translation/预取支持、tile size sweep、双缓冲、相同总 SRAM、相同可用带宽。
- 普通按消费组拆成小任务，page-first、oldest-group-first、ready-group-first 等简洁策略；允许相同组信息。
- 对确实有链间并行的子阶段，补 AMAC；不要求它加速没有独立 lookup 的单链。

只需要先建小规模 trace/event 研究工具来比较上界与简单策略；不得把没有真实到达/消费约束的离线排序收益当端到端加速。其结果若显示任一普通方案在误差内达到候选，机制候选终止。若只剩下某个 SRAM 数量或恰好 tile 尺寸的窄点收益，降为参数优化。若存在稳健剩余空间，再核 Terminus/Phloem/MAPLE 等原文，并考虑最小原型。

报告至少包含完整阶段耗时、消费者空等时间、实际有用字节、翻译服务及数据流量、总缓冲、CPU准备/通知成本；IOTLB 命中和 DRAM 行命中只作为因果指标。需要分别消融翻译分组、消费组通知、更多在途和数据重排，以排除“只是换了并发数”。

### 2.7 成功/失败能留下什么，平台如何分工

若成功，可写成“动态稀疏搬运接口的批次定义与端到端可组合性”论文：用真实消费依赖和映射事实指出现有性能外推的边界，提出最小接口并给出完整成本模型。只有一条合成 trace 的局部延迟改善，不足以支持这一题目。

若失败，至少能得到有用的否定结论：在给定应用与内存预算下，普通池化/页分组/双缓冲已经消除需要；或页局部性与物理行局部性实际上可兼容；或消费者同步消灭了早完成价值。这些结论仅限定测过的条件，不扩写成普遍“不需要新硬件”。

现有 CVA6＋4 iDMA＋IOMMU FPGA 可以在后续验证相同访问集合下的翻译覆盖、分组和有限在途竞争，检查请求/完成事件与正确性。它没有现成的 DX100、AMReX GPU pipeline、远端 NIC 或通用 gather execution engine；即便四路 DMA 可重放 trace，也不能代表真实应用收益，更不能把 172/172 功能验收当此候选验证。完整性能证据需要真实应用主机/加速器或经校准的执行与内存模型；不为了现有板适配而降低问题标准。

## 3. 为什么没有第二个候选

“近内存执行图搜索”“把应用间接表放 NIC”“给 gather 增加预取和重放”“用协程支持可变链长”都已有直接先行工作。尤其 CXL-ANNS 的官方摘要已明确邻居预取、依赖放宽和并行搜索；Terminus 被 DX100 明列为递归稀疏结构读/更新的近邻。在未读这些关键全文前，再包装一个“通用指针/ANN引擎”只会产生弱候选。[CXL-ANNS 官方页面](https://www.usenix.org/conference/atc23/presentation/jang)、[Terminus 作者题录](https://people.csail.mit.edu/sanchez/)。本席因此只交一个需严苛首验的候选，不凑两个。

|---|---|---|---|---|
| C4-P1 | 在真实翻译覆盖受限且消费者可分组开工时，以翻译工作集与消费依赖共同决定 gather 窗口，检验强软件方案之外的净收益 | **高**：DX100 的小 tile/内部流水、Milk 的动态分组/协程、MMU-aware DMA、现有细粒度数据流都可能覆盖 | 应用实际 arena/页映射与 barrier；Milk完整适用边界；Terminus MICRO2024、Phloem HPCA2023、MAPLE ISCA2022；2018 vDMA后续；按页分组能否达到上界 | **证据不足，允许先做低成本否定；不进入 RTL 立项** |

最先检查的不是把哪项组件装进 IOMMU，而是：**默认高性能内存管理下，能否找到一个真实阶段，同时有翻译关键路径、足够的重排局部性以及可提前启动的消费组。** 三者缺一，本候选就应停止。
