# A3-P1：强制撤销中的"已翻译在途窗口"——用完成纪元控制物理复用，以替代同步排空（定位为最值得先否定的候选）

| 项 | 内容 |
|---|---|
| 候选 | A3-P1：映射撤销分两件事。一是"翻译撤销"，即失效 IOTLB 和 PTE；二是"访问撤销"，即已经拿到旧翻译的在途请求全部完成。两者之间有一段窗口，本文称为已翻译在途窗口（TIW）。候选的做法是：用设备完成事件作为纪元，延迟物理页、块或 IOVA 的再分配，而不在撤销关键路径上同步等待排空或 flush ack。 |
| 核心假设 | 在非协作的强制撤销中（迁移、压缩、CoW、权限降级），关键路径的主要代价是同步等待在途请求排空，而不是失效命令本身。把这段等待改成"隔离复用"后，安全语义不弱于严格模式，且隔离内存有上界。 |
| 强基线 | ① pin 加严格 unmap（不迁移）；② 驱动先停队列、等设备空闲再撤销；③ Linux 式延迟批量失效；④ ShareMMU 式定向 back-invalidation 加 flush ack；⑤ BypassD 式延迟到同步点再复用；⑥ CPU 侧惰性 shootdown 加延迟复用（LATR、EcoTLB，待核）。 |
| 停止条件 | 出现以下任一情况即停止：规范的 IOFENCE PR/PW 已对非 ATS 路径关闭 TIW；实测 TIW 低于撤销关键路径的 5%；找不到每秒上千次"撤销仍在 DMA 中的页"的真实负载；与 LATR/EcoTLB 的差别只剩"把 CPU 纪元换成设备完成事件"。 |

说明：本回复只依据共同地图、ROOT_REVIEW，以及 ShareMMU、BypassD 两份原文（文本已在材料中给出）。此前截断请求里的另两份论文本回复没有重读，内容未知。我没有运行任何实验，也没有浏览网页。

## 1. 真实触发条件与为什么现在值得研究

[证据] ShareMMU 列出的映射更新起因包括页迁移、内存压缩和 copy-on-write（`papers/sharemmu2026.txt:438-441`）。它即使使用定向 back-invalidation，系统仍要等加速器写回脏行、刷私有 TLB 并回送 flush ack（`:427-430`）。在过渡状态中，它会锁住共享 TLB，私有 TLB miss 只能停等（`:510-520`、`:552-557`）。DiMap 的 6.27% 减速被归因于很高的权限变更率（`:796-798`）。

[证据] BypassD 承认一种竞争：SSD 已完成翻译但还没访问闪存时，失效无法取消这些请求。它的处理办法是把块的再分配推迟到 fsync 之类的同步点（`papers/bypassd2024.txt:347-363`、`:531-533`）。

[证据] RISC-V IOMMU 的 PR/PW 只覆盖已被 IOMMU 处理的请求，尚未抵达的设备在途请求可能另需互连 fence（`docs/research-landscape-20261005.md:41`；`ROOT_REVIEW.md:14`）。

[推断] 上面三处是同一个结构性缺口：失效完成不等于访问撤销完成。两篇论文都用"阻塞"（ShareMMU）或"粗粒度推迟到用户同步点"（BypassD）绕过它，都没有把这段窗口当作一个可测、可设计的对象。迁移和权限翻转越频繁，这个缺口越重要。

[假设] Linux 为 DMA 长期 pin 页面，会妨碍压缩和 CMA 迁移。这一点我凭记忆提出，待核。

## 2. 最近先行工作与精确差别

- **ShareMMU**（MICRO 2026，gem5 PARADE 仿真，`:96-97`）。差别：它用 Permission Tracker 解决不可信设备的伪造和陈旧地址问题，但保留同步 ack 和锁。A3-P1 不处理恶意设备，只处理在协作或可信设备下，撤销关键路径能否去掉同步等待。按 `ROOT_REVIEW.md:11`，安全不作为主线。
- **BypassD**（ASPLOS 2024）。它的 VBA 翻译代价用 UserLib 中的延迟来模拟（`:562-565`、`:651-654`）。差别：它在同步点推迟复用，依赖应用调用 fsync。A3-P1 的纪元来自设备完成事件，不依赖应用语义。
- **Utilizing the IOMMU Scalably**（ATC 2015）。延迟失效存在保护窗口（`landscape:89`）。差别：延迟失效让陈旧 IOTLB 在窗口内仍然有效，而且页可能已被复用。A3-P1 要求失效及时生效，只延迟物理复用。
- **重叠风险最高、凭记忆提出、均待核**：
  - LATR（Kumar 等，ASPLOS 2018，CPU 惰性 TLB 一致性加延迟回收）；
  - EcoTLB（`sharemmu:1152-1155` 引用）；
  - DAMN（Markuze 等，ASPLOS 2018，常驻映射的 DMA 缓冲分配）；
  - "When Copy is Faster than Zero Copy"（ASPLOS 2016，影子缓冲）。

  [推断] 如果 LATR 已经把"延迟复用直到所有翻译持有者确认"一般化到设备，A3-P1 就没有新意。

## 3. 可被推翻的主张

[假设] 对于在途事务数有上界的 DMA 引擎（如 iDMA），按完成纪元隔离复用，可以在保持严格模式"撤销返回后不存在对已复用物理资源的访问"的前提下，把强制撤销的关键路径延迟降到接近延迟失效模式。隔离内存的上界约为"未完成字节数 × 一个纪元的时长"。

## 4. 因果链、代价与致命反例

**因果链（推断）：** 撤销 → 立即发出失效，异步确认 → 在途请求按完成事件结算纪元 → 纪元推进后释放物理资源。被去掉的代价是 ShareMMU 式的锁和停等。

**新增代价：**
- 隔离期间物理内存或 IOVA 被占用；
- 需要可信的完成事件语义，即完成时该描述符的全部写已经可见；
- 驱动和 OS 的分配器需要改动。

**致命反例：**
1. 规范已经关闭 TIW。如果对非 ATS 设备，IOFENCE 加 PR/PW 已保证已翻译请求可见，而未抵达的请求会因失效直接 fault，那么 TIW 只存在于 ATS 或预翻译场景。本平台不具备这些（`landscape:137`、`:184`），候选只能留在仿真里。
2. 撤销关键路径主要是失效命令队列的延迟，而不是排空。这样批量失效已经够用。
3. 真实系统一律 pin，从不强制撤销正在 DMA 的页，触发条件就不成立。

[证据] 另需提防的数据问题：ShareMMU 正文称 DiMap 的 PCPKI 为 0.31（`:250-251`），但 Fig. 5 纵轴上限约 0.05（`:275-286`），两者疑似不一致。用它论证"撤销频繁"之前应先核实。

## 5. 低成本判别（未执行，均为建议）

[建议] 第一步是纸面判别，不改代码：精读 RISC-V IOMMU 队列文档 319–355 段关于 IOFENCE.C PR/PW 的确切保证，并比对 Linux RISC-V IOMMU 驱动的严格 unmap 路径，确认非 ATS 下 TIW 是否存在。若不存在，立即降级为"仅 ATS/仿真"。

[建议] 第二步是实物测量，留待后续：在 CVA6 + iDMA 平台上把一次强制撤销拆成四段：失效提交、IOFENCE 完成、等待 iDMA 完成、恢复。同时注入不同的在途深度，看排空等待所占比例。若低于 5% 则停止。

[建议] 第三步是检验应用真实性：找出 Linux 中因 DMA pin 导致迁移或压缩失败、需要强制撤销的路径及其频率，并记下来源。频率过低则停止。
