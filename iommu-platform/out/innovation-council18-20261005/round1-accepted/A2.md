## 0. 地图的因果结构，以及一个遗漏

**地图的主干因果**

- 【证据】地图第 2 条研究线把共享问题归结为一条轴：一端是静态分区（隔离好、利用率低），另一端是动态共享（吞吐高、可预测性差）。见 research-landscape:16、:38。
- 【证据】ROOT_REVIEW 明确要求：这条轴不能写成形式化的不可能定理（ROOT_REVIEW:23）。

**遗漏或过度概括：把"共享资源"当成需求外生的单个服务台**

【推断】四篇原文反复出现同一类现象：**某一级的服务速度或容量改变后，另一级、另一请求者的需求随之改变。** 对干扰起主导作用的往往是这种跨级"诱发需求"，而不是单一资源的分配比例。证据如下。

- **走表更快，TLB 反而更糟。**
  - 【证据】只增加 walker 会使 walk 更快完成、TLB 填充更频繁，从而冲掉有用条目（walk_stealing:305-306、:333-334）。
  - 【证据】DWS 在部分 HH 负载上无益，原因正是"降低 walk 延迟 → 提高 TLB 填充率 → 加剧 thrashing"（walk_stealing:582-587）。
- **walker 份额决定 TLB 份额。**
  - 【证据】DWS 改变各租户的 walker 份额后，L2 TLB 占用比例随之成比例改变（walk_stealing:394-400、:846-865）。
- **给后台更多缓存，前台反而获益。**
  - 【证据】给 batch 应用更多 LLC，会降低它们的内存带宽需求，从而改善带宽敏感的 moses 的尾延迟（kpart:1500-1504、:1458-1461）。
- **一方的 TLB 停顿释放了共享带宽。**
  - 【证据】MASK 优于 Static：一个应用因并发 TLB miss 停顿时，不再需要大量 DRAM 带宽，其他应用可以利用这部分带宽（mask:1005-1011）。
  - 【证据】部分组合共跑甚至优于单跑（mask:1084-1092）。
- **局部优化不可叠加。**
  - 【证据】MASK 与 DWS 叠加相比单独使用 DWS"未带来显著额外收益"（walk_stealing:863-864）。
  - 【证据】在含 page walk cache、1024 项 L2 TLB、有限 walker 的基线上，MASK 的收益比原文弱（walk_stealing:857-862）。
- **单一级指标不能决定吞吐。**
  - 【证据】Skylake 与 IceLake 的 IOTLB misses/MiB 相近，但吞吐差别显著。作者归因于可承受的在途事务数不同（iotlb:634-637）。
  - 【证据】作者给出的上界为 B ≤ N/(T_MEM+T_IOMMU)（iotlb:198-204），这本身就是一个**闭环（在途数受限）**模型。
- **干扰会改变状态，并且难以逆转。**
  - 【证据】丢包 → buffer 打乱 → IOTLB miss 增加 → 更多丢包，形成正反馈环。系统可能进入难以逃离的低性能区（iotlb:222-228）。
  - 【证据】即使用 hugepage 加激进回收的池，misses/MiB 仍会随时间上升（iotlb:954-971）。

【推断】因此地图漏掉了两个维度：

1. **稳态的跨级耦合。** 一级的服务率会内生地改变另一级的命中率与到达率。
2. **时间上的状态记忆。** 干扰可以改写某个请求者自身的布局状态，产生滞后效应。

地图第 3 节"卡点 6"写了"加 TLB/walker 不自动消除瓶颈"（research-landscape:50），但没有把背后的因果抽象出来。下面两个候选分别对应这两个维度。

**平台的定位**

- 【证据】平台已有"PN 部分配置改善一方、损害另一方"的现象，但根因未定（research-landscape:184）。
- 【证据】KPart 已有同类先行观察，不能据此宣称首发现（ROOT_REVIEW:8）。
- 【推断】两个候选都不把这一现象本身当作新意，而是把它当作可被解释或推翻的对象。

## A2-P1：把共享翻译路径的干扰建模为"闭环在途 × 内生命中率"的不动点，检验局部优化何时可组合

### 1. 真实应用、触发条件、为什么现在

**应用场景**

- 【假设】一个 SoC 或服务器上，多个 DMA 主设备（NIC、NVMe、NPU/ISP、DMA 引擎）共用一个 IOMMU 的 IOTLB、walker 和 walk cache。运维或驱动方各自独立调节本设备的参数。
- 【证据】IOTLB wall 显示，这些参数都会显著改变 misses/MiB：
  - MTU（iotlb:541-549）
  - LRO（iotlb:567-576）
  - TSO（iotlb:578-601）
  - 驱动的回收策略（iotlb:657-680）
  - hugepage 映射（iotlb:899-910）
- 【推断】但这些都是**单设备**调优。一个设备"成功"的局部优化（例如走表更快、命中更多），可能通过改变共享 IOTLB 的填充率或 walker 占用，改变另一设备的需求。

**触发条件**

- 【推断】请求者受在途数限制（闭环），共享结构是有限容量缓存加有限 walker，并且至少一个请求者接近 IOTLB wall 区。
- 【证据】wall 附近是高度非线性的：misses/MiB 从约 420 降到约 360，就能显著推迟开始丢包的速率（iotlb:536-539）。

**为什么现在**

- 【证据】RISC-V IOMMU 已有公开的规范语义（research-landscape:132）。
- 【证据】本平台有可修改的实物 IOMMU，以及"共享替换、命中绕过、组合退化"等受控干预能力（BRIEF:13）。
- 【推断】这使得在真实 RTL 上做因子化干预成为可能，而先行的 GPU 工作都是模拟（walk_stealing:224、mask:897-898）。
- 【推断】应用真实性**尚未建立**，见第 5 节的杀死实验 K1。

### 2. 最接近的先行工作与精确差别

| 先行工作 | 做了什么 | 与 P1 的差别 |
|---|---|---|
| Walk Stealing（HPCA 2021） | 用 S-TLB、S-(TLB+PTW) 去共享消融，分解 TLB 与 walker 各自的干扰头寸（walk_stealing:286-303）；定性指出 walker 份额牵动 TLB 份额（:846-865） | 它做的是"移除共享"的消融，目的是给机制找动机。它没有给出预测组合干预符号的模型。MASK+DWS 不可叠加只作为结果陈述（:863-864），没有解释。平台是 GPGPU-Sim。 |
| KPart（HPCA 2018） | 用带宽曲线对 IPC 按带宽"降额"，把缓存容量与带宽耦合起来（kpart:434-463） | 这是最直接的"跨资源耦合"先行，但它显式假设各应用 MLP 相同（kpart:458-463），而且用于 LLC 分区决策。P1 针对翻译路径，耦合方向是"服务率 → 填充率 → 命中率"，而且命中率是内生的。 |
| IOTLB wall（PeerJ CS 2023） | 闭环上界 B ≤ N/(T_MEM+T_IOMMU)（iotlb:198-204） | 只针对单请求者，T_IOMMU 被当作 miss 数的线性函数（iotlb:205-210）。没有多请求者交叉项。 |
| Application Slowdown Model（ASM，MICRO 2015） | 量化共享缓存与主存干扰下的 slowdown | KPart 参考文献 [51]（kpart:1539-1542）、MASK [124]（mask:1476-1477）都引用了它。我未读全文，**待核**。P1 必须与它比较：它估计的是"单跑性能"；P1 预测的是"组合干预的交叉效应"。 |

### 3. 可推翻的研究主张

> 在受在途数限制的多个 DMA 请求者共享 IOTLB 与 walker 的系统中，若把每级命中率设为由各请求者吞吐决定的内生量，并与闭环吞吐联立求不动点，则对"两项局部干预同时施加"所引起的各请求者吞吐变化，其**符号**的预测正确率应显著高于两类模型：①各干预单独效应的线性相加；②命中率固定的闭环 MVA。并且误判集中出现在可由"容量裕度"刻画的 wall 附近区间。

**推翻条件**

- 若①或②的符号预测已经与不动点模型相当，P1 无新意，判死。
- 若不动点模型本身也普遍误判，则该抽象不足，判死。

### 4. 因果链、代价、关键假设、最可能致命的反例

**因果链（推断）**

1. 局部干预（例如给 A 更多 IOTLB 容量，或提高 walker 并发）缩短 A 的 T_IOMMU。
2. A 的闭环吞吐上升。
3. A 对共享 IOTLB 的填充率上升。
4. B 的有效容量下降，命中率下降。
5. B 的 T_IOMMU 上升，B 的吞吐下降。
6. B 的 walk 需求上升，挤占 A 的 walker。
7. 结果可能回到 A 自身，造成"自伤"。

【证据】第 3、4 步在 GPU 情境有直接证据（walk_stealing:305-306、:582-587）。第 5 步在单请求者情境有证据（iotlb:198-204）。

**代价**

- 需要每请求者的 IOTLB 命中/填充计数、walker 队列占用、在途数。
- 【证据】商用平台的 IOTLB 细节"公开文档极少"，规模与策略也不可修改（iotlb:165-166、:207-208）。因此模型参数只能在可插桩平台上测得。
- 【推断】这正是 FPGA 的价值所在，也是外推到商用硬件的弱点。

**关键假设**

1. 【假设】请求者行为近似闭环（在途数上限 N）。iDMA 是否如此**未知**，需要查平台。
2. 【假设】替换策略足够接近 LRU，使 Che 近似一类的特征时间模型可用。
3. 【假设】walk cache 的命中同样可以内生化处理。

**最可能致命的反例**

- 【推断】反例一：在本平台的规模下（4 个 iDMA、IOTLB 项数**未知**），交叉项被单一瓶颈（例如内存带宽或总线仲裁）淹没，所有组合都退化为"谁占带宽谁赢"，简单的带宽模型就够了。
- 【推断】反例二：替换策略或 walk cache 的行为使命中率对填充率不单调，不动点不唯一或不收敛。

### 5. 最强普通方案与低成本杀死实验

**最强普通方案（不弱化）**

1. 经典的闭环排队网络 / MVA，每类每级服务需求取实测固定值。
2. 线性相加：把单项干预的效应相加。
3. 黑盒配置搜索（贝叶斯优化或穷举）。在小配置空间上，这往往才是工程上最强的方案，P1 必须在**样本效率或跨负载迁移**上胜过它。
4. 机制层面的对照：静态分区、统一共享、DWS 式偷取。地图要求翻译调度类问题至少与动态偷取/调度比较（research-landscape:174）。

**杀死实验 K1：应用真实性（纯检索，0 硬件成本）**

- 【建议】请协调者检索：是否有公开报告记录"同一 IOMMU 下，一个设备的映射或调优改变导致另一设备性能变化"。
- 检索对象：Linux 邮件列表、SMMU 或 VT-d 性能 issue、车载 SoC 的 SMMU QoS 文档。
- **停止条件**：找不到任何真实场景时，P1 降级为"方法学/特征刻画"类工作，不作为主线。

**杀死实验 K2：模拟复现不可叠加（低成本软件）**

- 【证据】MASK 的源码已开源（mask:905、:1452-1453）。DWS 作者使用了该源码（walk_stealing:847-848）。
- 【建议】在 MASK 的模拟器上复现"MASK+DWS ≈ DWS"。DWS 代码是否公开**未知**，可能需要按论文 §VI 重实现。
- 先用固定命中率的 MVA 和线性相加去预测，再用不动点模型去预测。
- **停止条件**：若 MVA 已能解释这一不可叠加，说明诱发需求项无独立价值，判死。

**杀死实验 K3：FPGA 2×2×2 因子实验（中成本，本轮不执行）**

- 设计：两个 iDMA 请求者；干预 X 为限制 A 的 IOTLB 有效容量（借助"共享替换"）；干预 Y 为提高 B 的 walk 负载（借助"命中绕过"）；再加一个负载强度维度。
- 测量：每请求者的吞吐、IOTLB 命中/填充、walker 队列、内存带宽。计算交互项。
- **停止条件**：所有配置的交互项都落在重复测量噪声内，或者所有符号反转都能被单级队列长度解释，则判死。
- 【缺口】平台是否能调节 walker 并发、是否有 walk cache、IOTLB 项数是多少、是否能按请求者计数——提供的材料中**没有**这些信息。

### 6. 成功能写什么、失败留下什么、平台分工

**成功时**

- 【推断】可以写一篇特征刻画加模型的论文，主题是"共享 I/O 翻译中的诱发需求：何时局部优化可组合"，目标偏 ISPASS/IISWC 或系统方向的 workshop。
- 核心贡献是一个可检验的模型，以及在真实 RTL 上的因子化验证。它不是新机制。

**失败时**

- 若诱发需求项可忽略，则得到一个有用的负结论：对共享 IOMMU，经典 MVA 加实测服务需求已经足以指导组合调优。这会让平台上的 PN 现象回归普通的带宽争用解释。

**平台分工**

- FPGA 能做：受控干预与完整插桩（K3）。
- 必须依赖其他平台：商用 IOMMU 上的可迁移性检验，例如 Intel 平台用 pcm-iio 读 IOTLB 计数（iotlb:372-374）。但这类平台无法改变 IOTLB 规模，只能做观测型验证。

## A2-P2：共享翻译中的"干扰滞后"——瞬时共跑干扰能否把另一请求者推入自身无法恢复的低局部性状态

### 1. 真实应用、触发条件、为什么现在

**应用场景**

- 【假设】一台 Linux 服务器上，高速 NIC 与另一 DMA 设备（例如 NVMe 或第二块 NIC）共享 IOMMU 的翻译资源。另一设备出现突发负载，例如备份、压缩或 compaction 窗口。

**机制来源**

- 【证据】IOTLB wall 在**单请求者**下已显示正反馈环：丢包与重传会延迟 buffer 回收，打乱 buffer 顺序，增加 IOTLB miss，进而造成更多丢包。系统可能进入"难以逃离"的低性能区（iotlb:222-228）。
- 【证据】多队列、多池会放大这种打乱（iotlb:232-233）。
- 【证据】带回收的 2 MiB 池在约 2 分钟后 miss 开始持续上升，池越小上升越快（iotlb:954-971）。

**P2 的问题（推断）**

若 B 的突发通过共享 IOTLB 或 walker 抬高 A 的 T_IOMMU，导致 A 越过 wall 开始丢包，那么 A 的 buffer 布局状态就被改写了。**即使 B 停止，A 也可能停留在高 miss 区。** 这就是干扰带有记忆、存在滞后。

**为什么现在**

- 【证据】作者提议"检测 thrashing 后换一批新 hugepage"来恢复，但**尚未实现**（iotlb:888-892）。
- 【证据】作者指出链路继续提速会需要越来越大的页，hugepage 并非万能（iotlb:985-991）。

### 2. 最接近的先行工作与精确差别

| 先行工作 | 差别 |
|---|---|
| IOTLB wall（iotlb:222-228、:937-971） | 只研究单请求者。正反馈的触发源是自身过载或人为丢包（iotlb:692-697），没有跨设备的触发源，也没有测量"撤除触发后能否恢复"。 |
| Metastable failures（Bronson 等，HotOS 2021；Huang 等，OSDI 2022；凭记忆，**待核**） | 研究分布式系统中，触发撤除后由持续性效应维持的故障状态。P2 把这一框架搬到硬件共享翻译加驱动 buffer 状态的层面，需要核实是否已有人做过 I/O 或 IOMMU 版本。 |
| DAMN（ASPLOS 2018，iotlb:1412-1415 引用；未读全文，**待核**） | 用永久映射 buffer 消除 map/unmap 开销，关注 4 KiB 与 CPU 开销（iotlb:86-93）。没有研究跨设备干扰下的布局退化。 |
| Bermuda（arXiv 2025，research-landscape:92；只有地图级信息） | 研究混合关键性下 SMMU 干扰的逆向工程。是否涉及滞后**未知**，**必须核查**，它是最可能撞车的工作。 |

### 3. 可推翻的研究主张

> 在采用回收式 buffer 池（例如 Linux page_pool）的高速 DMA 设备与共享同一 IOMMU 的第二设备共跑时，第二设备持续 T 的瞬时突发若使第一设备越过 IOTLB wall，则突发撤除后，第一设备的 misses/MiB 与吞吐恢复到突发前水平所需的时间远大于 T（或不恢复）；而使用"无池/每次新分配"或"定期刷新池"的配置不出现该滞后。

**推翻条件**

- 若在越过 wall 的条件下，撤除突发后恢复时间与 T 同量级，则判死。

### 4. 因果链、代价、关键假设、最可能致命的反例

**因果链（推断）**

1. B 的突发占用共享 IOTLB 与 walker。
2. A 的 T_IOMMU 上升。
3. A 闭环带宽下降（iotlb:198-204）。
4. A 在接收端丢包。
5. TCP 重传延长 buffer 寿命，buffer 被打乱（iotlb:688-697）。
6. A 自身的 misses/MiB 结构性升高。
7. 即使 B 已撤除，A 仍处在高 miss 区，并通过自身的丢包维持这一状态。

**代价**

- 需要在真实服务器上逐秒记录 IOTLB 计数与吞吐时序。

**关键假设**

1. 【假设】不同设备之间确实共享 IOTLB 或 walker。Intel 的 IOTLB 与重映射单元的组织、哪些设备挂在同一单元下，材料未给出（iotlb:165-170 只说"公开文档极少"）。**这是第一致命点。**
2. 【假设】第 7 步的自维持确实存在。原文只说"难以逃离"（iotlb:227-228），没有给出撤除触发后的恢复实验。

**最可能致命的反例**

- 【推断】反例一：只要 B 撤除，A 的 T_IOMMU 回落，闭环带宽重新高于入流，丢包停止。之后 page_pool 正常回收，布局逐步恢复，滞后很短。
- 【证据】这一反例有可能成立：原文中 512 页池的 miss 上升是在"持续"有丢包的条件下观察到的（iotlb:954-961），并不是撤除触发之后的测量。

### 5. 最强普通方案与低成本杀死实验

**最强普通方案**

1. 静态 hugepage 映射池（iotlb:899-910）。
2. "无池"新分配，原文显示该配置不打乱（iotlb:956-958）。
3. 定期刷新池（iotlb:888-892 的提议）。
4. 按设备划分 IOMMU 资源或 domain 隔离；对于不可修改的硬件，则改为错峰调度。

若 1 或 3 能以可忽略的成本消除滞后，P2 只能算一个运维提示，不足以支撑论文。

**杀死实验 K1：先行与硬件事实核查（0 成本）**

- 【建议】请协调者检索以下两项：
  - Bermuda 全文。
  - Intel VT-d 与 AMD-Vi 中，IOTLB 与 page walker 是否跨设备共享。可用关键词："DMA remapping hardware unit IOTLB shared across devices"、"VT-d IOTLB per remapping unit"。
- **停止条件**：若商用硬件上不同设备的翻译缓存与 walker 完全独立，则跨设备触发源不存在，P2 降为"同设备多队列间"的问题，新意大减。

**杀死实验 K2：真实服务器时序实验（低到中成本，本轮不执行）**

- 设计：在 IOTLB wall 作者开源的 iommu-bench 设置上（iotlb:1249-1253），A 设为 iPerf 接收端，运行在接近 wall 的速率（例如约 130 Gbps，见 iotlb:509）；B 用 fio 驱动 NVMe 做 T 秒的突发。
- 记录：逐秒的 A misses/MiB 与吞吐（pcm-iio，见 iotlb:372-374）。
- **停止条件**：撤除后 A 在约 T 的时间尺度内回到基线，判死。
- **成立条件**：恢复时间远大于 T，并且该滞后在"无池"配置下消失（区分出"布局状态"这一机制）。

**杀死实验 K3：FPGA 可行性（低成本检查，本轮不执行）**

- 【推断】要在 FPGA 上复现，需要满足两个条件：用户态驱动的 freelist 按完成顺序回收；iDMA 的完成存在乱序或丢弃的可能。
- 【缺口】iDMA 是否会乱序完成，材料**未提供**。若完成严格按序，就没有打乱机制，FPGA 无法复现，只能作为排除干扰源的对照平台。

### 6. 成功能写什么、失败留下什么、平台分工

**成功时**

- 【推断】可以写一篇现象加诊断的论文，主题是"共享 IOMMU 中的亚稳态翻译：跨设备干扰的滞后"，偏 HotOS/EuroSys 的特征刻画风格。附带一个最小恢复机制：按 misses/MiB 斜率触发池刷新。
- 性能主线仍然是主体。安全只作为"IOMMU 不能关"这一背景条件（iotlb:1065-1069），不转向安全论文。

**失败时**

- 得到一个确定结论："回收式池在跨设备瞬时干扰下可自愈，wall 的正反馈需要持续触发。"这可以直接约束运维策略，也能让 P1 的稳态模型免去时间状态项。

**平台分工**

- 主体实验必须依赖 x86 加 200G NIC 的真机。
- FPGA 只能在 iDMA 支持乱序完成时做机理对照。
