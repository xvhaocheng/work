## 1. 地图的因果结构与遗漏

地图主干可以概括为：应用访问/生命周期决定请求集合，布局和页粒度决定需要搬多少数据、查多少映射，共享结构决定请求何时完成，最终由依赖关系决定这段时间能否被计算覆盖。地图已提醒命中率、walk 延迟与应用吞吐不能互换；我建议再显式区分：**有独立工作、独立工作已驻留、有资源让它执行，是三件事。**

“把同步换成挂起”可能释放发射机会，却未必释放等待任务占用的寄存器、共享内存、驻留块或缺页处理资源。后面几项是否释放要核具体硬件与驱动，不能由“warp interruption”这类措辞推出。另一个跨领域反例是 Linux 已把 recoverable fault 与内存管理 fence 的依赖环列为正式约束；安全合法的地址映射并不自动带来系统进展。这里不是要把当前项目转成安全研究。

这个边界也限制了地图的综合表述：更多重叠有时增加留在系统中的中间状态；因此先让工作进入设备、再等待，不一定优于只发已就绪任务。但这种取舍不自动新颖，GPU coroutine 和 task-graph 领域已经研究不少。

## 4. C6-P1：跨设备等待时，何时应保留执行状态，何时应把状态交回运行时？

### 4.1 候选性质与一句可推翻的主张

这是**定量边界/系统抽象候选**，不是已经设计好的新调度器。

> 在至少一类真实的细粒度跨设备生产—消费任务中，当正常数据缺页与等待通知共存时，仅按预计等待时长选择 polling 或 fault-suspension 会系统性选错；引入“等待期间实际保留的执行/缺页资源”和“continuation 状态搬运量”后，可以解释并预测一种普通静态就绪队列或固定资源预留尚不能低成本覆盖的性能区域。

该主张里最后半句最危险，也最值得先杀。若测到的只是“轮询耗发射、spill 耗带宽”的常识，或者直接使用现成就绪队列就已解决，候选不成立。

### 4.2 真实应用、触发条件和现在的意义

第一目标应用不是人为构造无限等待的 kernel，而是 WIC 已使用的 CPU–GPU 有限元/共轭梯度、跨 GPU stencil/halo 交换：消费者先做本地独立工作，再等待外部生产的数据；各分块完成时间不均。第二个待核对象是多 GPU GNN 的细粒度聚合，MGG 已说明其通信计算流水的重要性。[WIC](https://www.usenix.org/system/files/atc25-zhang-jiajian.pdf) §3、§4；[MGG 官方摘要](https://www.usenix.org/conference/osdi23/presentation/wang-yuke)

**必须同时满足的条件：**（a）仍有可做的独立任务；（b）消费者等待足够长且不能完全预测；（c）这些独立任务因某项被等待者保留的资源而未能执行；（d）转存等待状态又不是免费；（e）内存容量/真实缺页需求来自应用本身，不能仅为压垮 fault path 人为制造。WIC 的应用证据只支持（a）（b）的存在，不证明（c）–（e）在目标部署中成立。

现在值得查，是因为 fine-grained in-kernel 通信与可恢复缺页被作为更通用的编程设施使用，而等待已不一定发生在 kernel 边界。这里的“现在”是研究条件变化，不是宣称这一问题首次出现。无需先改 IOMMU。

### 4.4 替代抽象、因果链与不能隐藏的成本

建议先用“**等待的资源账本**”做分析接口：每次等待记录所等的依赖、数据是否驻留、保留多少执行状态、实际占用哪类 fault/replay 状态，以及换出后要读写多少 continuation 数据。它是待验证的测量视角，不是发明了协程。

预期因果链是：早到消费者停在等待点 → 发射减少，但部分执行状态或恢复资源可能仍被占有 → 已经就绪的独立任务无法进入/恢复 → 生产或消费进展下降、状态存活更久 → 缺页/容量压力扩大。把等待者改成 continuation 则可能释放前一类资源，却增加状态访存、缓存污染、排队与恢复成本。这两条链的大小都必须实测。

必须分别核实三种资源，不能把它们加成一个“并发槽”数字：

1. **发射与驻留：**某 warp 没有发射，不代表 CTA、寄存器、shared memory 已返还。若驱动实际进行了 context 换出，则必须按实况计入，不能预设“必然保留”。
2. **硬件 fault/replay 与软件 PFQ：**WIC 把事件放进软件队列后，原硬件条目何时释放、是否会有重复 fault、是否阻碍 PAT 或真实缺页，要读该版本代码/实测；不能以 `PFQ length = hardware slots held` 建模。
3. **待续状态与数据：**编译器 live-state 字节数、读写次数、页驻留、数据重取和重算成本分别计；已经存在的 GPU Coroutines SoA、compaction、只存活字段是强基线必配能力。

不可隐藏的代价包括：主机通知与轮询核成本；状态保存/恢复与重算；kernel launch 或 persistent scheduler 成本；额外映射/失效/PCM 页轮换；固定保留资源造成的正常吞吐损失；跨设备正确性所需的 release/acquire；实现对源代码改动、可编译 kernel 和驱动版本的限制。不预设依赖图全可见，不用平均等待代替尾部分布。

### 4.5 最强普通方案

至少比较以下适用方案，资源和正确性预算相同：

- **只派发就绪分块**：现成 task graph / stream event / 分块 kernel，合批以摊薄 launch；禁止故意让消费者抢占完所有资源再称其为最强对照。
- **一个或少量通知/通信角色配合就绪队列**：普通 warp specialization / persistent worker；调好 polling backoff，按实际角色保留必要的资源，计算其预留代价。
- **GPU Coroutines 的强实现**：活跃字段裁剪，适用的 wavefront 或 persistent 调度，状态帧布局优化；允许手工优化的分块/continuation 胜过通用框架。
- **WIC 原机制及简单准入限制**：人工等待 fault 合批、最大待处理等待数；优先尝试最简单的固定限制，并测真实缺页是否独立受理。
- **消除需求的应用策略**：合法预取、提前生产、分块重排、保留足够内存或固定一个进展资源集合。只要符合部署成本，就应允许它击败候选。

### 4.6 最便宜的判别步骤与停止条件

**步骤 0：先读实现，不搭新硬件。** 取得 WIC 对应版本/作者实现，画出 PCM fault → 软件 PFQ → PAT → DMA → replay 的资源生命周期，区分 fault buffer 和 software queue。若拿不到实现且无法在可用硬件观测，不把猜测当已证机制；该候选暂停在问题阶段，不启动大工程。

**步骤 1：应用真实性门槛。** 在一个真实 finite-element/stencil 或图聚合任务中，仅记录每个分块生产就绪、消费者到达、独立就绪工作量、工作集/真实缺页。对照在可接受内存成本下的预取与静态分块。若不存在“有独立就绪工作却被等待者保留资源挡住”的可观测窗口，立即淘汰。不要靠新增故意失配依赖、无限延迟或人为压缩显存预算制造窗口。

**步骤 2：两端上界先杀。** 对同一依赖 DAG 与数据，比较最强就绪任务流水，以及尽量只保存必要字段的 continuation 版本；核算通知、launch、状态访存和迁移。再用理想就绪时间仅作为离线上界，判断还有多少无法被已有机制取得的空间。理想 trace 回放不能改变依赖或隐藏生产者反馈。

预先约定的项目筛选门槛（不是文献定律）：若普通方案在应用允许内存预算内已达到该上界的 95%，或者剩余端到端改善不足 10%，停止机制探索。若收益只有合成测例，或不能跨至少两种依赖形状/工作集配置保持，降为测量笔记。数字可在实验前按噪声和实际目标修订，不能看到结果后为保留候选改门槛。

**步骤 3：只有前两步存活才寻找新机制。** 要证明同一个普通策略并非只差一个显而易见的固定阈值：区分资源占用结构带来的交叉，和单纯等待变长/硬件队列变满。如果优化最后只剩“较长等待用协程、较短等待轮询”或“给通知加优先级”，回到已有方案，不写成新架构。

**最可能致命的反例：**等待 fault 已经充分让出瓶颈资源；生产者在独立设备上不受该资源影响；真实应用已用就绪流水而非早派发消费者；简单准入上限让所有竞争消失；continuation 状态量太小而现成协程直接胜出；或者状态量太大导致任何换出都不值得。任何一种都能使本候选失去论文价值。

### 4.7 成功/失败能留下什么、需要什么平台

若成功，论文应围绕**跨设备等待方式的适用边界和可验证的资源语义**：指出某类真实应用中旧的“等待可被计算覆盖”假设失败，给出可迁移的判别条件，再提出超越强普通方案的最小改动。只做性能相图也需要有足够新、可泛化的现象，不能自动承诺系统顶会。

若失败，留下可复用的反例：少轮询不等于更少驻留；或反过来，在实用资源预算内简单就绪流水已经足够。后者是明确的选题停止依据，避免为当前 FPGA 强造问题。

**当前 CVA6+4 iDMA+IOMMU FPGA 不能验这个候选。** 它没有目标 GPU warp/CTA/寄存器驻留、UVM fault/replay 行为，最多能在另行授权后做抽象队列示例，不能支持应用结论。实证至少需要一块支持可观测 UVM 的 GPU 与可修改相应驱动；跨 GPU 工作需要第二块 GPU。若研究 continuation，则还需可改应用/编译链。当前 172/172 验收与该主张无关。
