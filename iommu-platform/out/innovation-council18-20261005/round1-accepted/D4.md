## 1. 地图在这一方向的因果结构，以及一个可能的遗漏/过度概括

**因果结构（我的概括，基于地图 §2 研究线 4、卡点 5）：** 地图把间接访存干净地分成两极。一极是**真串行指针链**：下一跳地址依赖上一跳返回的数据，延迟 ≈ 深度 × 每跳成本，只能用解耦/近数据/寄存器链式 Load 来折叠（`impica2016.txt` 第 50–53、58–60、74–82 行；`tiara2026.txt` 第 309–313 行；`dae1982.txt` 第 42–52、119–152 行的访问/执行解耦是历史根）。另一极是**可并行 scatter/gather**：地址在发射时已（或可批量）知道，瓶颈是带宽，靠重排/合并/交织提高行缓冲命中与 MLP（`dx1002025.txt` 第 71–77、138–144、306–363 行）。地图明确要求不得把已知地址散读算成串行链、不得拿 Tiara 的朴素 160 RTT 当对手（`docs/research-landscape-20261005.md` 第 47 行；`ROOT_REVIEW.md` 第 18 行），这一点我完全接受并会在下面严格保持。

**一个可能的遗漏/过度概括：** 地图把“串行 vs 可并行”当作**算法固有属性**来分类，但真实负载位于两者之间的连续谱：它们有一个有限的**“地址已知窗 K”**（发射前能解析出多少地址），而 K 既不是 0（纯指针链）也不是全部（理想批量）。DX100 其实承认了这一点——它靠 tiling 把窗口从内存控制器的 32–128 提到 16K（`dx1002025.txt` 第 138–144 行），但前提是索引已在 scratchpad（第 203–205、273–291 行），且它**明确不支持 pointer chasing**（第 477–495 行）。IMPICA 走另一极，用 address-access decoupling 并行多条链（第 74–82、338–344 行），但把翻译问题**独立解掉**（region-based page table，第 405–408、452–471 行），不研究窗口与翻译互相约束。地图把“布局”（卡点 5，第 47 行）与“翻译代价”（卡点 1、3，第 35、41 行）作为两条独立瓶颈，于是**留下了未参数化的边界**：K 由什么决定？K 能否被布局/翻译结构移动？在设备/DMA 路径上，K 的增大是否会反噬 IOTLB/PTW？这些在给定材料里没有形成可证伪的定量命题。

## 2. 候选 D4-P1：地址已知窗 K 与翻译工作集的联合选择——设备侧批量散读的“翻译感知窗口”

**1）真实应用、触发条件、为什么现在值得研究。**
应用：PagedAttention/vLLM 的 block-table → KV block gather（`tiara2026.txt` 第 90、486–500 行）、hash-join 的 bucket chaining 探针（`dx1002025.txt` 表 1 第 224 行）、CSR SpMV/SpGEMM（`dx1002025.txt` 第 22 行）、图 BFS frontier 扩展（`dx1002025.txt` 表 1 第 221 行）。它们的共同点：既不是纯指针链（DX100 已声明不覆盖，第 480–482 行），也不是一次性全知地址；需要先解析索引，再发出数据读。触发条件：这些散读**经由设备/DMA 路径发出**，且散读地址跨越的页集合**大于 IOTLB reach**。为什么现在：数据搬运正从 CPU 侧走向设备侧与 disaggregated 内存（`tiara2026.txt` 第 39–68 行），而 DX100 把窗口做成 16K 却把翻译用 huge page + 256-entry TLB 直接绕开（第 449–452 行）；IOTLB wall 又指出 200 Gbps 下 IOTLB miss 是数据路径瓶颈、hugepage 非 panacea（地图第 90 行，**待核**）。把“重排窗口”与“翻译工作集”当成同一个自由变量的两个约束来联立，在给定材料里没有先例。

**2）最接近的先行工作与精确差别（引用路径/行、URL）。**
- **DX100**（ISCA’25，arXiv:2505.23073v1，`papers/dx1002025.txt`）：可编程数据访问加速器，16K 窗口内 reorder/coalesce/interleave 优化 DRAM 行缓冲、通道与 bank-group（第 71–77、129–137、306–363 行），报 2.6× 几何平均加速、3.9× 带宽（第 742–745、874–881 行）。**差别**：(a) 第 477–495 行明确不支持 pointer chasing；(b) 它把翻译假设为 huge page + 小 TLB（第 449–452 行），**没有把翻译工作集当作窗口选择的约束**；(c) 是 CPU 侧共享加速器，不是 I/O/DMA+IOMMU 路径。
- **IMPICA**（ICCD’16，`papers/impica2016.txt`）：内存内 pointer chasing 加速器，address-access decoupling + region-based page table（第 74–82、405–408、452–471 行），并指出把翻译请求发回 CPU 会抵消收益（第 87–99 行）。**差别**：它把翻译**独立**解掉（2MB flat pages，连区域表仅约 68B，第 452–460、464–467 行），只覆盖可区域化链表；不研究“窗口与翻译互相约束”，也不覆盖并行 bulk scatter（第 105–113 行）。
- **Tiara**（arXiv:2606.13708v1，`papers/tiara2026.txt`）：memory-side NIC 的可验证 ISA，register-chained Load 折叠多跳（第 309–313 行）；Table 1 明确 PagedAttention **最优批处理基线是 2 RTT**、朴素 stop-and-wait 才是 160 RTT（第 83–100 行；并见第 150–157 行“indirection 与 scatter-gather 不同”）。**差别**：它是 NIC 本地解析、把 RTT 折成 1，不是把重排窗口与 IOMMU 翻译工作集联立。
- **待核**（仅记忆/仅地图）：IOTLB wall（PeerJ CS 2023，地图第 90 行）、Direct Segments（ISCA 2013，地图第 66 行）、Milk 与 Propagation Blocking（`dx1002025.txt` 第 1307–1314 行引用其软件批处理）。

**3）一句可被推翻的研究主张。**
对经由设备/DMA 发出的批量散读，端到端吞吐对 lookahead 窗口 K **不是单调的**：当地址集合跨越的虚拟页数超过 IOTLB 覆盖时，把 K 从“纯 DRAM 最优”继续增大，会因 IOTLB/PTW 压力而降低吞吐；存在由数据本地性与翻译工作集共同决定的最优 K\*，且 K\* 可由布局（页大小、页着色、物理合并）移动。

**4）因果链与代价、关键假设、最可能致命的反例。**
K↑ → 发射前可重排地址增多 → 行缓冲命中↑、bank/通道并行↑、MLP↑（`dx1002025.txt` 第 725–745、890–969 行）→ 但同批地址覆盖的虚拟页数↑ → IOTLB 未命中↑ → walk 队列与 demand walk 争用（类比 IDYLL 的失效/walk 争用，地图第 41 行，**待核**）。代价：IOTLB 容量、PTW 带宽、以及更新时的失效同步。**关键假设**：散读地址跨越的页集合显著大于 IOTLB reach。**最可能致命反例**：数据由单一池/大页分配（LLM 服务里很常见），页集合极小，翻译成本被布局吸收，此时 K 单调，候选退化为“DX100 的 I/O 版”，新意消失。

**5）最强普通/现成方案与低成本杀死实验。**
强基线（不得弱化）：(i) 直接用大页/连续物理分配把翻译摊销（Direct Segments，地图第 66 行；IOTLB wall 的 hugepage，地图第 90 行，均**待核**）；(ii) 取最大可行 K 做纯 DRAM 重排（DX100）；(iii) 软件批处理（Milk / Propagation Blocking，`dx1002025.txt` 第 1307–1314 行，**待核**）。
判别实验（可在现有平台做）：在 Genesys2 的 CVA6 + 4 iDMA + RISC-V IOMMU + Linux 上，构造同一语义的散读微基准，页布局取两种（4K 散落 vs 连续/大页），K 从 16 扫到 64K；测 iDMA 完成时间、IOMMU 读事务/PTW 计数、IOTLB 行为。应用真实性用一条真实地址 trace（PagedAttention block-table gather 或 hash-join 探针）而非合成均匀分布。**收益空间**：若存在 K\* 且相对“最大 K”有可测回撤，即说明需要联合调度；**停止条件**：若在大页/连续布局下端到端时间随 K 单调改善、且与纯 DRAM 最优 K 的差距 <5%，则证伪/降级。（地图第 184 行说明 IOTLB/PTW 探针是候选用途、**尚未执行**——本实验需要先建探针。）

**6）若成功/若失败、现有 FPGA 能做什么、必须依赖什么。**
成功可写：一条可预测的 K\*(布局, 翻译结构) 曲线 + 一个翻译感知的窗口调度机制——属于“新定量边界 + 新机制”，且落在 I/O 路径这一未覆盖区间。失败留下：若 K 恒单调，则说明在 I/O 路径上翻译成本被布局吸收、indirection 退化为纯带宽问题，这本身收窄了“数据表示/搬运”的问题域。**FPGA 能做**：4K/大页布局变体、K 扫描、iDMA 完成时间、IOMMU 读/PTW 计数（需先补探针）。**必须依赖其他平台**：真实 NIC/PCIe ATS/多设备来验证 disaggregated 情形；大 IOTLB、大 walk 并行度需模拟。

## 3. 候选 D4-P2：间接解析点的分工——把应用级 indirection 交给 IOMMU 遍历，还是描述符链/近数据解析

**1）真实应用、触发条件、为什么现在值得研究。**
应用：设备发起的应用级 indirection——CSR 索引数组、block table、key→slot 表、MoE expert 表（`tiara2026.txt` 第 128–134 行）。触发条件：indirection 深度 ≥2、表驻留远端内存、每个元素解析都要一次等待。为什么现在：RISC-V IOMMU 已在 I/O 路径做多级 walk 且带 IOTLB/Walk cache（地图第 41、132 行；**队列规范待核**）；Tiara 展示 memory-side NIC 能把**应用管理的 3 级 indirection 当页表 walk**在 1 RTT 内解掉，并明确“这不是 OS 页表”（`tiara2026.txt` 第 163–166、172–175、326–329 行；`ROOT_REVIEW.md` 第 18 行）；IMPICA 展示加速器需要专门 region-based page table 才能避免每访问一次就回 CPU 翻译（`impica2016.txt` 第 87–99、405–407 行）。合起来的问题：**IOMMU 的页表 walker 能不能作为通用 indirection 解析器**，替代软件/描述符链？

**2）最接近的先行工作与精确差别。**
- **Tiara**：自己的 8 个轻量 MP + 受限 OpenCL C 编译的 ISA，register-chained Load（第 309–313 行），静态验证终止与内存区域隔离（第 279–302 行）。**差别**：解析发生在它自己的 MP，**不复用**已有 IOMMU 的 PTW/IOTLB；它把应用 block table 与 OS 页表明确区分（第 163–166 行）。
- **IMPICA**：region-based page table 在 3D 内存内，把翻译与 CPU 解耦（第 405–408、452–471 行）。**差别**：专用、假设区域连续（第 105–113 行）、面向 pointer chasing，不是在通用 I/O 路径复用系统 IOMMU。
- **DX100**：array-based indirection 用描述符/ISA 解析（第 481–495 行），用 huge page + 256-entry TLB 绕开翻译（第 449–452 行）。**差别**：完全不碰翻译结构。
- 强对手还有：预注册近数据程序（eBPF/NAAM，`tiara2026.txt` 第 237–257 行，**待核**）、Direct Segments（地图第 66 行，**待核**）。**差别一句话**：没有人在“描述符链 / IOMMU PTW / 近数据”三处做**同语义、同成本**的对照，也没有给出“何时用翻译结构承载应用 indirection”的可证伪判据。

**3）一句可被推翻的研究主张。**
对深度 ≥2、表驻留远端、以设备发起为主的一类 indirection，把应用 indirection 编码为可被现有 RISC-V IOMMU walk 解析的多级结构，比软件/描述符链解析端到端更省时且 CPU 占用更低，同时不违反隔离；其净收益随表更新率上升而反超为负。

**4）因果链与代价、关键假设、最可能致命的反例。**
描述符链解析 = 每次描述符 fetch 一次内存访问 + 串行（`dx1002025.txt` 第 173–190 行的依赖链；`tiara2026.txt` 第 227–228、383 行：RedN 每 WR ~0.54 µs、~1 Mops）。IOMMU 解析 = 复用已有 IOTLB/Walk cache 与流水化 PTW，把多级解析并行/缓存（地图第 15 行），并免去每元素软件参与。**代价/风险**：(a) 规范页表叶项是 PPN + 权限，**无法直接存任意指针**，需把 indirection 约束成天然浅 radix 结构、或叶指向数据页；(b) 更新表触发定向失效，需 IOTINVAL/IODIR/IOFENCE（地图第 41、132 行，**待核**）；(c) 隔离/权限分层不能混同（SVA/HMM/ShareMMU，地图第 93、137 行，**待核**）。**关键假设**：该类 indirection 天然浅（≤3 级）且更新冷。**最可能致命反例**：vAttention 风格细粒度改 block table 的负载，会造成 IOTLB 失效风暴，反而劣于软件/描述符链——候选在此类负载上被推翻。

**5）最强普通/现成方案与低成本杀死实验。**
强基线：(i) 软件 walk + 批量 DMA；(ii) iDMA 描述符链（当前平台已有 4 iDMA）；(iii) 预注册近数据程序（eBPF/NAAM，`tiara2026.txt` 第 237–257 行，**待核**）；(iv) 大页/连续分配绕开翻译。
判别实验：三路同语义对照，解析 N 项 indirection——(a) 软件 walk + DMA；(b) iDMA 描述符链；(c) 把同一 indirection 编码为 IOMMU 可 walk 的 radix 结构（若现有格式不允许，则先用一个只改 PTE 语义的 RTL 变体/模型，并明确这是模型而非实物）。测解析延迟、CPU 占用、IOMMU 读事务/IOTLB miss、失效次数；同时注入高频更新场景。**停止条件**：若 (c) 在现有格式下无法表示、或相比 (b) 无显著优势、或失效成本随更新率立即反超，则淘汰。

**6）若成功/若失败、现有 FPGA 能做什么、必须依赖什么。**
成功可写：一份“indirection 解析点”的设计空间与判据（何时 IOMMU walk 优于描述符链）+ 一个最小的“可解析 indirection 结构”契约——属于新抽象，但必须承认它是 Tiara 思想在系统 IOMMU 上的迁移与验证，而非全新机制。失败留下：确认翻译硬件不应被当作通用 indirection 引擎，收窄“translation-as-indirection”的适用域，并反对把 Tiara 的特例过度泛化。**FPGA 能做**：用现有 RISC-V IOMMU 驱动合成 radix 结构，测 walk 延迟/并行/失效。**必须依赖其他平台**：要真正把应用 indirection 映射成 PTE 语义，需要改 IOMMU/格式（RTL）；多节点/真实 NIC 情形需 RDMA/NIC，不应把现状平台的小规模结果外推为通用结论。

## 4. 可导航摘要与候选表

| 候选编号 | 一句话 | 先行工作重叠风险 | 待核来源 | 优先判断 |
|---|---|---|---|---|
| D4-P1 | 设备侧批量散读的 lookahead 窗口 K 必须与翻译工作集（IOTLB/PTW）联合选择，存在可预测且可被布局移动的最优 K\* | 中：DX100 的重排、IOTLB wall 的 hugepage、Direct Segments 的连续分配、软件批处理（Milk/Propagation Blocking） | DX100 artifact、IOTLB wall（PeerJ CS 2023）全文、Direct Segments 全文、Milk、Propagation Blocking、IDYLL（失效/walk 争用） | 较高：可在现有平台做最小判别实验，失败也有负面结论 |
| D4-P2 | 把应用级 indirection 放到 IOMMU 遍历还是描述符链/近数据解析，需要同语义、同成本的解析点对照与判据 | 中高：Tiara 已将应用 indirection 当页表 walk；IMPICA 已有专用页表；ShareMMU/IOMMU 权限分层 | RISC-V IOMMU 队列规范、Tiara 全文（已有）、NAAM、ShareMMU、vAttention 更新粒度 | 中：需要 RTL/格式变更与跨设备验证，落点较远 |

**事实 / 推断 / 假设的分界：**
- **事实（本次已读全文）**：DAE 是访问/执行解耦的历史根（`dae1982.txt` 第 42–52、119–152 行）；IMPICA 用 address-access decoupling + region-based page table 处理 pointer chasing，并指出翻译请求回 CPU 会抵消收益（`impica2016.txt` 第 74–82、87–99、405–471 行）；DX100 做 16K 窗口重排/合并/交织以优化 DRAM 带宽，且明确不支持 pointer chasing（`dx1002025.txt` 第 71–77、138–144、477–495 行）；Tiara 用 register-chained Load 折叠多跳、Table 1 的最优批处理基线是 2 RTT 而非 160 RTT、并区分 indirection 与可并行 scatter-gather（`tiara2026.txt` 第 83–100、150–157、309–313 行）。
- **推断（我的综合，非任一论文单证）**：串行/并行的二分应被“地址已知窗 K”参数化；K 同时受数据本地性与翻译工作集约束。
- **假设（待检验）**：K\* 可由布局移动；IOMMU walk 可承载浅 radix 应用 indirection 且在冷更新负载下优于描述符链。
