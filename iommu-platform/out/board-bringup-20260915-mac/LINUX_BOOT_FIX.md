## 实板原子指令复现

通过 FT2232 channel 0 连接 CVA6 CPU 调试接口，OpenOCD 0.12.0 检出单 hart RV64。FPGA 配置使用另一通道；不要混用。

小程序在 firmware 与 Linux 之间的间隙 `0x801f0000` 运行，代码、结果和测试数据都在备份的 64 KiB 区域中。先 LR/SC 成功，再不重新 LR 执行第二次 SC：后者必须报告失败且不改变内存。

| 操作 | 首次 SC 返回/写入值 | 第二次 SC 返回/内存值 | 失败轮数 |
|---|---|---|---|
| SC.W，地址低三位 0 | 0 / 2 | 1 / 2 | 0/1000 |
| SC.W，地址低三位 4 | 0 / 2 | **0 / 2** | **1000/1000** |
| SC.D，8 字节对齐 | 0 / 2 | 1 / 2 | 0/1000 |

关键：高半部 SC.W 第二次没有写入，却错误报告成功。原始结果：
`results/debug/atomic-20260916/results.bin`，每条记录为 8 个小端 uint64：tag、LR 值、首次 SC 状态、首次内存值、第二次 SC 状态、最终内存值、轮数、失败数。

## 对应 RTL

实际 BIT 启用 `WT_DCACHE`。生产源码
`cva6/core/cache_subsystem/wt_axi_adapter.sv` 的请求组合逻辑把 `amo_off_d` 默认赋为零；请求出队后、B 响应到来前，已保存的 SC 字节偏移丢失。响应逻辑于是把失败标志放到低半部，高半部读取为零（成功）。

修复候选：默认保持 `amo_off_q`，在新 SC 请求时更新，直到响应使用完毕。原始内核调用栈中的 `s_active` 位于 superblock 偏移 188（低三位 4），使用 LR.W/SC.W 更新；这与实板复现吻合。是否彻底消除启动异常仍须新 BIT 上板验证。

## 调试工具注意事项

首次调试脚本使用 OpenOCD `get_reg`，读到了未刷新的寄存器缓存（几乎全零），因此那次不能声称成功恢复了原 Linux CPU 上下文。指定 RAM 区域已从备份写回，但 CPU 需要重新启动；原始日志保留，不把它算作修复验证。

脚本已改为 `get_reg -force`、拒绝 PC=0 的“保存现场”模式，并检查完成标志。后续上板须先重新配置/启动，再使用改进后的脚本。SD 和 Flash 均未因调试而写入。
