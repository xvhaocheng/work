Runtime mode today: `enable = (mode == "n")` (`cpp:1575`), `tb.policy_partition = false` (`cpp:1600`) — **`policy_partition_i` is never asserted by the C++ harness today**, and no build ever passes `-GPolicyEnable=1`. That is the whole gap for P/PN.

Elaboration vs runtime: the compile-time `NonblockEnable` defaults to 1 and is never overridden by the runner (`tests/nonblock_actual_dma_top.sv:43`, `tests/nonblock_actual_dma_system_top.sv:70`); the C++ only drives the runtime port `nonblock_enable_i` (`cpp:463`). `policy_partition_i` reaches `rv_iommu_tl_wrap` via `system_top:994 → top:546 → banked_top:796`, with `policy_clear_i=!rst_ni` and `policy_did_i=24'd10` (= V_DID, `cpp:76`) at `banked_top:797-798`. In a `PolicyEnable=0` build these inputs are inert (`banked_top:20-32` comment). This matches the audit's finding that P/PN share the compile-time gate and differ only by a runtime input (`audit-summary.json:126-130`).

## A2. Scenario / window structure (what a "window" is today)

`run_scenario()` (`cpp:1287-1516`) phases:

1. `setup_memory` + `reset` + `scenario_start = g_cycle` — `cpp:1295-1299`
2. warm phase (batch OFF, A first / V second driver order) — `cpp:1301-1320`
3. configure A autonomous batch + V batch (both before any trigger) — `cpp:1322-1329`
4. triggers `start_batch(SEL_A)` then `start_batch(SEL_V)` (`cfg_rd(REG_NEXT)`) — `cpp:1331-1333`
5. wait for V batch `complete` (from `REG_B_CTL`) — `cpp:1335-1372`; break at `:1364`
6. `stop_batch(SEL_A)` + drain to inactive — `cpp:1374-1394`
7. drain-to-quiet — `cpp:1396`
8. byte verification — `cpp:1398-1414`
9. guards + `ACTUAL-DMA-SUMMARY` — `cpp:1416-1515`

Existing "window switches":

* `warm_hw_track` — warm-phase-only scoreboard switch, `cpp:229`, set `:1160`, cleared `:1236`, consumed `:566-576`. **This is warm-only and must not be reused as a measurement window.**
* `scenario_start` — whole-scenario origin, `cpp:1297`; the printed `cycles=` is `g_cycle - scenario_start` (`cpp:1506`), i.e. **warm + configure + trigger + hardware + drain + quiet**. It is *not* the audit's `W`.
* batch state registers read through `REG_B_CTL` (`0x88`, `cpp:103`, `read_batch_ctl cpp:1033-1041`: bit0 enable, bit1 active, bit2 stopped, bit3 complete, bit32 error) — the existing switch used by the step-5/6 loops.
* hardware batch activity: `dbg_dma_batch_active` / `dbg_dma_batch_gap` per bank (`top.sv:817-818`, already used at `cpp:1352` and `system_top.sv:465`). Usable in principle as a hardware window, but `batch_gap_active_o` exists precisely because `batch_active` drops between jobs, so its per-job level semantics are unverified in these files → the patch below does **not** rely on it.

The audit's `W` / `V_hardware_phase` / `V_poll_phase` / `V_refill_phase` (`window-decomposition.json:4-16`) come from a **different counter set** (board-side reduction). This harness has no equivalent of `V_poll_phase`/`V_refill_phase` (the batch path just polls `REG_B_CTL` in one single-threaded loop, `cpp:1339-1370`) and no equivalent of `shared_AW_backpressure` (`window-decomposition.json:12,57,102,115`). Do not present model numbers as those fields.

## A3. Pre-edge sampling (the required gating point)

`tick()` (`cpp:462-728`):

* drives inputs, `clk_i=0`, `eval()` — `cpp:462-482`
* **pre-edge snapshot**: system `f_ddr_ar/aw/w/b/r` + `s_ddr_ar_addr/len/id`, `s_ddr_aw_addr/len/id`, `s_ddr_w_*` — `cpp:487-502`; non-system comp/ddtw/ptw AR + AW/W/B/R — `cpp:503-556`
* progress stamps and all existing counters, all from that pre-edge sample — `cpp:558-628`
* rising edge `clk_i=1`, `eval()` — `cpp:630-632`; post-edge model updates — `cpp:634-672` (system) / `673-723`
* `++g_cycle` — `cpp:727`

So a counter that consumes `top->…_valid && top->…_ready` at `:578-628` is pre-edge gated; anything appended after `:630` is not. The patch below inserts strictly inside the pre-edge region.

## A5. What is missing and must not be invented

1. **Shared-AW-wait / IOMMU-ingress AW backpressure** — the exact quantity the audit measured (`audit-summary.json:146`, `window-decomposition.json:57,72,87`). Not observable here:
   * the only exported AW handshake is at the DDR master port (`system_top.sv:1119-1120`), and the C++ DDR model drives `ddr_aw_ready = 1` **permanently** (`cpp:436`) and `ddr_w_ready = 1` (`cpp:437`) → any AW/W-stall counter there is structurally 0;
   * the completion/ingress AW handshake (`u_comp_aw_valid`/`slv_resps[2].aw_ready`, `system_top.sv:244-268`, `:1018-1020`) is **not in the module port list** (`system_top.sv:168-186`); only the combined fire is exported (`:1105`). Same for the non-system top: `comp_aw_ready` is hardwired `1` by the C++ (`cpp:383`).
   → requires a new SV tap; **deferred to Codex** (task explicitly forbids adding SV signals now).
2. **Per-source AW stall** (comp vs DS vs CPU) — same reason.
3. **AW/W backlog/occupancy inside the DUT** — no queue-occupancy tap.
4. **`V_AR_backpressure`/`A_AR_backpressure`/`V_poll_phase`/`V_refill_phase` equivalents** (`window-decomposition.json:11-16`) — do not exist in this harness.
5. **V vs A split of DDR AW by ID** — impossible (shared mux, A4 caveat); only the address-region heuristic is available.
6. **`ptw-latency` semantics** — in system mode the model applies `ptw_latency` to **every** accepted DDR read, not only PTW (`cpp:640`, comment `:431-434`), and prints a warning (`cpp:1583`). `--ptw-latency 100` must never be equated with the RTL 50/50 `axi_delayer` (`system_top.sv:354-373`, `:81-82`).

Field semantics (all window-scoped, none fabricated):

* `runtime_N` = runtime `nonblock_enable_i` (1 for `n`/`pn`). `policy_enable` = runtime `policy_partition_i` (1 for `p`/`pn`). **The elaboration `-GPolicyEnable=1` is not readable from the C++** — it is identified by the runner's obj dir / build log name.
* `W_cycles` = window length in model ticks (`w_cycles`), self-checked against `win_close_cycle − win_open_cycle`. **Not comparable to the existing `ACTUAL-DMA-SUMMARY cycles=` field** (that one includes warm + drain + quiet).
* `v_completed`/`a_completed` = `dbg_dma_done` bit0/bit1 pulses inside the window (expected `v_completed == v_transfers`).
* `ddr_*_slv{k}_*` = DDR-port split by xbar slave index in ID[5:4] (0 = synthetic CPU, 2 = completion master, 3 = DS/delayer), the same convention already used at `cpp:637` and printed at `:1481-1487`. **V and A cannot be separated this way** (they share one mux port, `top.sv:432-465`); `ddr_aw_v_region`/`ddr_aw_a_region` are an **address-region** heuristic (V: `0x8000_0000..0x8100_0000`; A: `≥0x9000_0000`).
* `ddr_aw_stall` / `ddr_w_stall` are 0 **by model construction** (`cpp:436-437`) and are labelled as such in `unavailable` context — they are not evidence about the board.
* `iotlb_miss = lookup − hit` (valid only because hit is counted inside `if (lookup)` at `cpp:591-594`).

# D) Assumptions

1. `dbg_dma_issue`/`dbg_dma_done` are 1-cycle pulses — the existing warm scoreboard already assumes this and self-checks issue==done (`cpp:566-576`, `:1242-1245`). Same for `dbg_ddtw_ar_fire`/`dbg_ptw_ar_fire`/`dbg_tl_ptw_r_fire` (existing usage at `cpp:599-600`).
2. `dbg_tl_ptw_active` is a level → counted per cycle, matching `cpp:590`.
3. Window = `run_scenario()` steps 3→4 (after both NEXT_ID triggers, until `REG_B_CTL.complete`). Mapping to the audit's `W`/`V_hardware_phase` is a naming correspondence, not a proven physical equivalence.
4. Obj-dir/log naming: I chose `obj-policy-system` / `build-policy-system.log` (and `obj-policy` / `build-policy.log` without `--system`) to match the requested literal `build-policy-system`, while reproducing all legacy names byte-for-byte when `policy == 0`. If Codex prefers `obj-system-policy`, only the two `tag` lines change.
5. `p` = policy + nonblocking **disabled**, `pn` = policy + nonblocking **enabled** (the "PN = P + N" reading; same runtime difference as s/n). If the intended encoding of P/PN differs, only `enable = (mode == "n" || mode == "pn")` changes.
6. `.u.` semantics at xbar ID bits — I reuse the existing `(id >> 4) & 3` convention from `cpp:637` rather than re-deriving it.
7. No file other than the two test files is modified; `-GPolicyEnable=1` is a Verilator top-level parameter override on both tops (`top.sv:47`, `system_top.sv:77`), both of which forward it (`top.sv:542`, `system_top.sv:989`).
