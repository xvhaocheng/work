# E3 v5：补齐等待识别，再做有限的 D0/D128 配对

2026-09-18。00085 的 D0/D0 诊断已完成；结果见[独立复核](e3-diag-results-review.md)。本轮修订已实现并通过主机验证，软件与 FPGA 完整构建均已通过，BIT/MCS 非空；配套产物见[交付说明](README.md)。新版尚未上板。

## 为什么还要做这一步

正式 A8 八个子轮全部触发，旧约 8 ms 的轮次差没有稳定重现。然而两轮预热 miss 仍不同，第一对还选中了不同的 A/V 请求。预热任务数量和末页相同，只说明这两项外部条件相同，不能证明 IOTLB 状态和到达顺序相同。D0/D0 也不能回答延迟 128 周期是否传给 V。

旧触发条件只看 AR FIFO 队头是否为 V。A 读已进入翻译服务时仍占据物理队头，后面的 V 虽已被接收且尚未获得服务，却不满足旧条件。这是已确认的代码覆盖缺口，不是已确认的全部实验根因。

新版按真实握手跟踪“已接收、尚未被控制器选中”的 V 读数量：接收时增加，选中时减少。A 的正常一级翻译首次缺失且 V 在等待时，选择一笔 A PTW 响应做 D0/D128；同时记录旧队头、触发候选数、触发前计数和最多两条中间请求。计数覆盖从复位开始，ARM 不伪造空队列；ARM 前必须排空，溢出/下溢/身份错误使观测无效。

目的仍是检验：**同一类 A 页表服务被延长后，已经排队的 V 是否增加相应等待，而 V 自身服务不变。** 这属于 E3 因果条件修正阶段，尚未进入缓解方法效果评估，也没有证明 HOL。

## 本轮固定条件

保持 DS50/50、50 MHz、V=DMA0/DID10、A=DMA1/DID11，V 源/目标各一页，A 各一页或八页，4 KiB 硬件自动接续，CPU 整批轮询。两轮共享映射生命周期，各自预热、排空、核验，继续记录 00085 的软件前史。没有增加 IOTLB 清空或改变启动方式。

必须同时更新本轮 BIT 和 SD `fw_payload.bin`，不能沿用旧 v4 BIT。新内核为 `6.5.0-rc2-00086-gd2cd32d78918`，程序已在 rootfs 的 `/usr/bin/idma_e3_pair`。按已用的 SD 原始分区流程更新软件，不把它当整盘镜像。下载、刷卡、串口采集沿用已有板卡流程。

新配置名 `migration-4dma-e3-queue`，observer 外层 magic 为 `0x49444d414f425305`，E3 bank 为 `0x49444d4145330002`。`--diagnostic 2` 使用独立 ioctl 0x0b/能力位 bit5，要求 v5 BIT；旧 BIT 会在 DMA 启动前拒绝。输出 schema 为 `idma.e3_queue_pair.v1`，保留 `diagnostic` 对象，第二轮 D 与首轮互补。旧 `--diagnostic 1` 仍是 D0/D0，schema `idma.e3_diag.v1`，在本次新板卡上同样应读到 bank v2。

新触发条件可能更早选中 A 读，所以 v5 数据独立成组；不要与 v4 的旧 D0/D0 或 D0/D128 数据混算。

## 上板只运行这份有限矩阵

先三个短验收，每条命令两轮：

```sh
idma_e3_pair --diagnostic 2 --aggressor none --transfers 8 --warmup 0 --first-delay 0
idma_e3_pair --diagnostic 2 --aggressor 1 --aggressor-pages 1 --transfers 64 --warmup 32 --first-delay 0
idma_e3_pair --diagnostic 2 --aggressor 1 --aggressor-pages 8 --transfers 64 --warmup 0 --first-delay 128
```

短验收全部通过后，仅做下面十对正式实验。每对 V 为 4096 项、warmup256。两对 A8 的 D0/D0 用来检查新版本自身的轮次差；六对 A8 配对首轮 D 交替；两对 A1 是阴性控制。

| 顺序 | A 页数 | diagnostic | first-delay | 两轮 D |
|---|---:|---:|---:|---|
| 1 | 8 | 1 | 0 | 0 / 0 |
| 2 | 8 | 2 | 0 | 0 / 128 |
| 3 | 8 | 2 | 128 | 128 / 0 |
| 4 | 1 | 2 | 0 | 0 / 128 |
| 5 | 8 | 2 | 0 | 0 / 128 |
| 6 | 8 | 1 | 0 | 0 / 0 |
| 7 | 8 | 2 | 128 | 128 / 0 |
| 8 | 8 | 2 | 0 | 0 / 128 |

idma_e3_pair --diagnostic 2 --aggressor 1 --aggressor-pages 8 --transfers 4096 --warmup 256 --first-delay 0

总计 13 对、26 子轮，预期每轮各有 3 条 batch +16 条 path，即 26 个不同 sequence、每个 19 条观测，共 494 条；串口重复打印同一行不算新增样本。真实错误立即停，保留失败 JSON 和 UART；无触发、首次缺失、前史不同、记录截断均保留并分类，不补采、不自动扩大矩阵。Solo 预期无触发；A1 预期无热态 PTW 触发，若不符先保留原始结果，不重跑替换。

## 采集器需要同步的地方

每条命令 stdout 仍只输出一条含两轮的 JSON；软件诊断在 `rounds[r].diagnostic`，E3 数据在 `rounds[r].e3_words`，每轮 256 个 64 位数。保留完整 UART、退出码、taint、版本与产物来源记录，并按两条 sequence 收齐日志。失败 JSON 不裁剪；没有执行到的阶段可能为零。

采集器先接受新 schema 和 bank v2，不能再要求下面新增字段为零；D0/D0 第二轮仍为 0，其余为首轮互补。64 位 magic 和计数须按整数处理，使用 JavaScript 时避免经过有损的 Number 解析。

已有状态/数据/排空/窗口/AXI/path/E3 延迟精度检查继续保留。新增的触发前摘要和旧队头字段由内核原样回传，**命令 success 不能代替这些字段的外部自洽性检查**。软件诊断时间是 Linux 单调时间，E3 时间是 ARM 后硬件周期；不能直接跨域相减。字段基础定义见 [E3 原协议](E3_SERVICE.md)和[软件诊断字段](E3_DIAGNOSTIC.md)。

## v2 新字段：均为 e3_words 相对索引

旧 0～24、32～45、64～77、96～255 的口径保持；原保留区新增如下。lane 顺序统一为 Vr、Vw、Ar、Aw。

| 索引 | 含义 |
|---|---|
| 25 | 测量窗口内，内存侧 PTW R 实际握手数 |
| 26 | 其中属于符合触发类别的 A 正常 S1 首次缺失请求的握手数 |
| 27 / 28 | 26 中，有 / 没有已接收而未选中的 V 读 |
| 29 | 27 中，物理 AR 队头不是 V 的次数，即旧识别方式覆盖不到的机会 |
| 30 | A 处于上述 S1 缺失状态且 V 等待的周期数；不是握手数，也不是 V 排队时间和 |
| 31 | 实际触发当拍旧队头是否为 V；无触发为 0 |
| 46～53 / 54～61 | 触发后、目标 V 被选中前，前两条其它被选中的请求 |
| 62 / 63 | 插入记录是否截断 / 实际保存条数，最多 2 |
| 78～81 / 82～85 | 触发前四 lane 的首次 hit / miss 数 |
| 86～89 / 90～93 | 触发前四 lane 的 TR 接收数 / COMP 首次有效数 |
| 94 / 95 | 触发当拍物理 AR 队头身份 / IOVA |

每条插入记录的八项依次为：该 lane 的请求序号、AXI ID、DID、IOVA、是否写、TR 接收时间、控制器选中时间、首次查询命中结果。ID0/DID10 为 V，ID4/DID11 为 A；首次结果 0=miss、1=hit、2=尚未观察到。`e3_words[12]` 仍保存实际插入总数；超过两条时总数保留、62=1，不能把只存下的前两条当全部轨迹。

94 的 bit32 是 head_valid，bits31:8 是 DID，bits7:0 是 AXI ID；高位应为零。仅 head_valid=1 时解释 IOVA。31 应等于“head_valid 且 ID0/DID10”。78～93 是触发时钟沿**之前**的计数快照；它们不是完整 IOTLB/替换状态，也不是握手事件的全序列。78～85 只累计 active 窗口内查询，不大于对应最终 hit/miss；86～93 从 ARM 后累计，可能包含窗口打开前已经完成的 A 请求，不直接与仅窗口内的 stage entered 作大小或相等断言，也不能只靠 opening carry 还原窗口前已完成的请求。

门槛自洽检查：25≥26，26=27+28，29≤27，30≥27；触发数只能是 0 或 1，且与“27 是否非零”一致。计数持续到测量窗口结束，包含一次触发用完之后的机会，因此 27、29 可以大于 1，不能当触发次数。错误位1新增 bit4 为控制器等待计数错误；任意错误位非零都不算有效测量。

有触发时，实际 D 由 3/7 核对，5−4 应为 D+1，6≥5；D0/D128 都经过同一个响应寄存器。62 应等于 `12>2`，63 应等于 `min(12,2)`，各有效插入记录必须身份正确、TR≤选中，选中时间在触发 A 翻译响应与目标 V 选中之间，顺序不倒退。保留旧事件位图、七阶段时间顺序及完整 V 记录检查。所有相对时间还应在 ARM 至冻结范围内。

## 怎么判定有用，而不是只看运行成功

第一层是执行验收：配套版本、数据正确、排空安全、字段和守恒无错误，短验收通过。第二层是触发覆盖：分报 A8 两轮均触发、单轮触发、均不触发数量，结合 25～31 解释门槛。31=0 且队头记录为 A 读，才直接说明本次触发落在旧队头条件覆盖不到的场景；29>0 单独只表示出现过这类候选机会。

第三层才比较延迟。逐对核对映射、A/V 请求身份/序号/方向/IOVA、PTE 地址/层级、V 首次 hit、插入身份/方向/次序/首次 hit，以及 78～93 的前史摘要；分报触发前 V 等待和 A 已服务时间。先看 D0/D0 是否仍有顺序相关差异。无触发、V 首次 miss、前史或身份不同、插入截断单列，不把它们隐藏后补采出一组“成功样本”。即使这些已观测字段相同，也不等于内部状态完全相同。

对能比较的配对，按 **D128−D0** 计算，而不是固定用第二轮减第一轮。四个主要读数为：

| 读数 | e3_words 计算 |
|---|---|
| 触发后 V 剩余等待 | 70−4 |
| V 完整排队 | 70−69 |
| V 自身翻译服务 | 73−71 |
| 触发后 A 剩余服务 | 41−4 |

同时报告触发前 V 已等多久 `4−69`、A 此前服务多久 `4−39`，以及整批硬件/软件时间，避免把前史算作 D 的作用。候选证据是：A 剩余服务随 D 延长，匹配条件下 V 剩余等待也出现可重复增量，且与 D0/D0 的自然波动、V 自身服务和中间请求变化可区分。不要预先规定结果必须严格等于 128 周期；中间请求可能参与传播。六对只是有限诊断，不承诺统计显著性。

若双轮覆盖仍不足或前史/插入次序依旧不可比，则停止解释配对差值，下一步才设计有限请求序列或硬件共同启动。这些控制尚未实现，本轮不自动追加。只有形成可重复的等待位置、可区分的干预证据和可控点，才进入一项缓解方法及其直接基线。
