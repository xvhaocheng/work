## 关键证据

### 1. P 和 N 的真实规则、调用链

**P 规则已证事实**

- 主 TL 给 IOTLB 的 `policy_mask_i` 由稳定主请求 `req_data.did` 决定，不由 fast probe DID 决定：
  - `rv_iommu_tl_wrap.sv:670-673`  
    DID10 → `16'h0003`，其余 → `16'hfffc`。
- IOTLB 分配 mask 与 eligibility：
  - `rv_iommu_iotlb.sv:366` `allocation_mask = PolicyEnable ? policy_mask_i : '1`
  - `rv_iommu_iotlb.sv:367-373` 由 allocation mask 生成 eligible tree。
- 分区局部历史：
  - `rv_iommu_iotlb.sv:353-362` `ProtectedWays=16'h0003`，`ProtectedNodes` / `BackgroundNodes`，`partition_local_active` 仅对 16 条且 mask 为 `0x0003` 或 `0xfffc` 生效。
  - `rv_iommu_iotlb.sv:389-399` touch 归属按常驻 way 选 `ProtectedNodes` 或 `BackgroundNodes`，不使用 `policy_mask_i` 判 touch 归属。
  - `rv_iommu_iotlb.sv:416-422` victim 选择按 eligible tree 跟随 PLRU，全 mask 退化为原 PLRU。

**N 规则已证事实**

- fast 窗口：
  - `rv_iommu_tl_wrap.sv:303-306`  
    `n_window = state_q == PT && e3_ptw_active && en_1S_q && !en_2S_q && !ddt_imp_trans_q && !pdt_imp_trans_q && !req_data.is_debug && trans_req_data_i.bank != req_data.bank && !ats_ddtc_valid_i && !debug_req_valid_i && !ats_trans_req_valid_i`
- fast 模块启动与接受：
  - `rv_iommu_nonblock_hit.sv:47-48` `start`
  - `rv_iommu_nonblock_hit.sv:100-103` `accept_o`
- TL 侧 handshake：
  - `rv_iommu_tl_wrap.sv:284-286`  
    `normal_gate`、`trans_req_ready_o = n_intercept ? n_accept : (normal_trans_ready && normal_gate)`
  - `rv_iommu_tl_wrap.sv:319` `normal_fire_i`
  - `rv_iommu_tl_wrap.sv:322-329` fast 模块端口连接。

**推断**

- 调用链符合设计意图：主 TL 忙时，另一 bank 的 V 命中由 fast path 提前返回；fast 未接受时仍回落 normal，但需等 `normal_gate` 打开。
- 没有发现 fast path 会绕过权限或 DDTC/IOTLB 命中所有权的直接证据。

### 2. N 门控、ready-valid、反压、仲裁、payload 稳定、权限/DDTC/IOTLB/PLRU touch

**已证事实**

- `normal_gate`：
  - `rv_iommu_tl_wrap.sv:284-285`  
    N 使能时，只有 `state_q == IDLE && !req_valid && !n_intercept` 才允许 normal arbiter 接新请求。
- fast 拦截时 ready：
  - `rv_iommu_tl_wrap.sv:286`  
    `n_intercept ? n_accept : ...`
- fast busy/OUT：
  - `rv_iommu_nonblock_hit.sv:49` `busy_o = state_q != IDLE && state_q != REJECT`
  - `rv_iommu_nonblock_hit.sv:50` `intercept_o = start || busy_o`
  - `rv_iommu_nonblock_hit.sv:109` `response_valid_o = state_q == OUT`
  - `rv_iommu_nonblock_hit.sv:171` `OUT: if (response_ready_i) state_q <= IDLE;`
- payload / 上下文稳定检查：
  - `rv_iommu_nonblock_hit.sv:100-103` 同时要求 `candidate_i == req_q`、`ddtp_i == ddtp_q`、`ddtc_dc_i == dc_q`。
- 权限与 S1/Sv39/4KiB 限制：
  - `rv_iommu_nonblock_hit.sv:84-93` `dc_ok`
  - `rv_iommu_nonblock_hit.sv:94-99` `leaf_ok`
  - 检查了 `tc.v`、`!pdtv`、`!sxl`、`!t2gpa`、`!en_ats`、`!en_pri`、`!pid_valid`、`!priv`、`!is_debug`、`UNTRANSLATED_R/W`、canonical、`fsc.mode == Sv39`、`iohgatp.mode == Bare`、iommu_mode、S1 4K、`u`、`r/w`。
- DDTC/IOTLB 命中所有权：
  - `rv_iommu_tl_wrap.sv:249-252` DDTC lookup 端口在 `n_ddtc_lu` 时切给 fast，`ddtc_lu_hit` 对主 TL 强制 0。
  - `rv_iommu_tl_wrap.sv:271-277` IOTLB lookup 端口在 `n_iotlb_lu` 时切给 fast，`iotlb_lu_hit` 对主 TL 强制 0。
  - `rv_iommu_tl_wrap.sv:275-276` fast lookup 固定 `en1=1, en2=0`。
- PLRU touch：
  - `rv_iommu_nonblock_hit.sv:106-107` `ddtc_touch_o = accept_o`、`iotlb_touch_o = accept_o`
  - `rv_iommu_tl_wrap.sv:516` `touch_i(!n_ddtc_lu || n_ddtc_touch)`
  - `rv_iommu_tl_wrap.sv:676` `touch_i(!n_iotlb_lu || n_iotlb_touch)`
  - 结论：fast 只有真正 `accept_o` 才 touch；probe/reject 不 touch。

**推断**

- `normal_gate` 在 N/PN 下比原逻辑严格很多，取消了主 TL 忙时 normal spill 的一拍 lookahead。这是可测的额外气泡来源，但不一定是 0.90M 的主因。
- `OUT` 状态通过 `n_intercept` 阻塞 `normal_gate`。如果 fast 响应长期反压，主 TL 即使 IDLE 也不能接新请求。该路径没有在 `composition_tl_test` 中做持续反压覆盖。
- 响应仲裁 `rv_iommu_tl_wrap.sv:346-353` 使用 `rr`，没有固定优先级。fast/slow 同拍 valid 时，fast 可能让一拍。未发现饥饿证明，也未发现 starvation bug 证据。

### 3. 是否有实际可达性能 bug / 功能 bug / 只是事件顺序

**已证事实**

- P/PN 记录中 A miss 均 2048，V miss 均 0，A fill 均 2048，partition violation 0，replace PSCID 0。
- PN 记录 `raw[21] V_FAST=4096`，`raw[12] V_LOOKUP=12288`；P 记录 `raw[12]=16384`、`raw[21]=0`。
- PN 窗口 W 约 7.93M cycles，P 约 7.04M cycles，差约 0.90M cycles。
- A done `p4m.window[3]=4096` 在 P/PN 均成立，但窗口长度不同，所以 A 窗口平均 rate 在 PN 低约 11.3%。

**推断**

- 从已给 RTL 看，没有单一确定 bug 能直接产生 0.90M cycles。
- 最强候选是共享端口气泡与事件顺序变化：
  1. fast path 抢 IOTLB lookup，主 TL 在 PT 等待完成时可能被延迟；
  2. `normal_gate` 取消 normal spill lookahead，A/V 切换增加气泡；
  3. fast `OUT` 阻塞 normal，fast/slow rr 仲裁可能增加响应延迟；
  4. 这些效应叠加后，可能改变 A PTW 完成、响应返回、V fast 到达的相对时序，从而放大窗口。
- 但按单次事件估算，上述候选单独都远小于 0.90M。要确认，必须做周期级定向 trace，不能靠计数相同或模型共识。

**缺口**

- 没有 `n_iotlb_lu`、`cache_iotlb_hit`、主 TL 自身 hit、PTW active/done、fast accept/reject、fast/slow response valid/ready 的周期级记录。
- 没有实际 DMA 侧每笔 V/A 请求的 issue/done 时间线。
- 没有 `rv_iommu_trans_ctl_wrap` 和 `stream_arbiter` 源码，无法确认 banked response 路由的精确反压行为。

### 4. Linux 任务供给、warmup、mode 清缓存、窗口开关、A 完成数

**已证事实**

- composition 配置在 `stream_prepare` 之前：
  - `idma.c:2436-2447` 调 `idma_composition_configure`
  - `idma_composition_configure` `idma.c:2283-2307` 写 offset2，触发硬件 `clear_o`，并检查 quiet、status、generation、config readback。
- warmup：
  - `idma.c:2502-2507` warmup 提交 A（若存在）并调 `idma_run_window` 跑 V/A。
  - `idma.c:2527-2546` warmup 后 drain A，再 `idma_batch_configure(v, e.victim_transfers)`，A 用 `IDMA_EXPERIMENT_MAX_TRANSFERS`。
- gap、arm、window：
  - `idma.c:2552-2557` gap program readback
  - `idma.c:2579` observation arm
  - `idma.c:2591` batch window
- 窗口开关：
  - `dma_observer.sv:103` `research_open_o` 在 ARMED 且 victim lane issue 时开窗。
  - `dma_observer.sv:402-414` V batch target 达成时 close，冻结窗口。
  - `dma_composition_control.sv:256-274` open 采前状态，close 采 next 状态。
- A 完成数是独立 lane 事件：
  - `dma_observer.sv:311-315` `a_done_evt = done_i[aggressor_q]`，计数到 `p4m_a_done_q`，即 `window[3]`。

**推断**

- mode 清缓存是真实的：配置写触发 `clear_o`，且要求在 quiet 下进行。
- A 完成数不是由 V 推导的，是 aggressor lane 的独立 done 事件。
- n=3 是描述性样本，不足以对 A 吞吐做显著性解释；文档本身也声明不做显著性主张。
- 需要补全缺失的 3 次重复记录和 S/N 对比记录，才能确认平均值和窗口计数守恒。

## 最多 3 个低成本定向验证

1. **IOTLB 端口冲突周期级仿真**
   - 在 `tests/composition_tl_top.sv` 临时暴露 `n_iotlb_lu`、`cache_iotlb_hit`、主 TL `state_q==PT`、`e3_ptw_active`。
   - 在 `composition_tl_test.cpp` 构造：A cold miss 进入 PT 且 PTW active → 连续 V fast 命中 → 释放 A PTW → 观察 A 从 PTW done 到主 TL `COMPLETE` 的周期数。
   - 统计 `n_iotlb_lu` 与主 TL 需要看 hit 的周期重叠次数。
   - 目的：量化 fast 抢 IOTLB lookup 是否产生显著气泡。低成本，纯仿真。

2. **N vs 非 N 的 normal lookahead 气泡仿真**
   - 用同一 cold A 序列，在 N 使能和非 N 下比较：A 完成后主 TL 接下一个 V/A 请求的延迟。
   - 观察 `normal_gate`、`req_valid`、`arb_req_valid`、`normal_trans_ready`、主 TL `state_q`。
   - 目的：确认 `normal_gate` 取消 spill lookahead 是否产生可测的每切换气泡。

3. **窗口内阶段时间定位**
   - 利用已有 `composition_trace` 或已有 record 中的 `victim_elapsed_ns`、`window[1]`、`drain_ns`、`snapshot_*`。
   - 对 P 和 PN 各一条 A8/Vgap0 记录，计算窗口内外时间占比：
     - P：`victim_elapsed_ns=143,418,600`，`window[1]=7,032,355` cycles（50MHz → 140,647,100 ns），窗口外约 2.77M ns。
     - PN：`victim_elapsed_ns=160,239,280`，`window[1]=7,931,945` cycles（158,638,900 ns），窗口外约 1.60M ns。
   - 结论：0.90M cycles 差额在窗口内，不在 drain/snapshot 外。下一步应在窗口内做周期级 trace，而不是加 FPGA 调试规模。

## 若认为有 bug 的最小修复方向

- 当前没有足够证据认定确定 bug，不建议直接改 RTL。
- 若验证 1 证明 IOTLB 端口抢占导致主 TL 显著延迟：最小方向是给主 TL 与 fast path 分离 IOTLB lookup 读端口，或在主 TL 处于 `PT` 且 PTW 已完成时给主 TL lookup 优先。
- 若验证 2 证明 `normal_gate` 取消 lookahead 造成显著气泡：最小方向是在 fast 不 intercept 时允许 normal spill 预取，同时增加重复接受防护。
- 这些都属于架构级改动，超出小批次，应由 Codex 决策和复核。
