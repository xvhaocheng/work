> 后续[实际配置与更弱完成条件审查](innovation-deeper-20261006.md)已闭合当前配置允许早发物理AW的前缀，但没有证实完整更新环；并加入比严格成对预翻译更宽松的普通准入对照。以下是上一阶段结论。

## 1. 裁定：问题更具体，但仍没有确认新机制

取得 ShareMMU 公开 artifact 的 20 个相关源文件，补齐此前 HTTP 503 留下的主要证据缺口。结果收缩了两个候选，而不是提高了“已经创新”的置信度：

| 原候选／想法 | 本轮核实 | 当前结论 |
|---|---|---|
| C1：历史共享保护冷项 | 论文与公开代码的替换计分不同；代码也不是唯一设备数计数 | 上轮公式反例只针对论文伪代码，不能直接当代码反例；普通 aging/加权替换仍是强基线 |
| C2：暂停翻译使读返回无法排空 | 每个已发读预留返回空间，便可排除这一特定环 | 原环不能单独支撑新机制；完整 job 缓冲不是唯一普通解法 |
| 写地址优先以释放缓冲 | 当前平台已经实现 AW 优先于 AR | 不能再把“增加写优先”当新点 |
| 缓冲释放感知的翻译优先级 | 已有关键性调度、MSHR 合并；本轮未给出有效的信息差异反例 | 不提升为第三个已成立的候选 |
| 两端翻译相依时的完成条件 | 存在另一个“已发写等源读翻译”的条件等待环 | 可继续反证，但尚未证明真实目标协议可达，也未证明普通成对预翻译不足 |

当前保留的问题是：**同等权限更新语义下，两端需要翻译的 DMA 能否用更少预留资源维持完成和有效并发？** 这可以是首篇增量论文的研究问题，但不是已发现的新机制。研究目标仍可落在性能与资源代价；正确处理更新是约束，不代表自动转向安全论文。

## 2. ShareMMU：论文、公开代码和我们的平台必须分开

主来源：[作者论文页](https://research.nvidia.com/publication/2026-09_sharemmu-supporting-secure-address-translation-sharing-among-untrusted)、[公开 artifact](https://doi.org/10.5281/zenodo.21543532)。本次概念 DOI 对应记录 22681559，文件为 `sharemmu-micro59-ae-v3.zip`。只提取必要源码，没有运行该模拟器；完整来源和本地文件 SHA256 见[清单](../out/innovation-followup-20261006/artifact-manifest.json)。

以下源文件路径均相对于 `out/innovation-followup-20261006/artifact/sharemmu-micro59-ae-v3/ShareMMU/src/`：

| 核查位置 | 直接观察 | 对创新论证的限制 |
|---|---|---|
| `modules/NetworkInterrupt/NetworkInterrupts.cc:887–939`，`PTrack::findOrEvict` | 淘汰最大 `age − 5.0 × shareCounter`；`age` 是时间差 | 不等于论文 Algorithm 1 的有限 LRU rank 加共享设备数；上轮固定 rank 阈值不能直接移植 |
| 同文件 `943–977` | 非 lender 的访问会增加 `shareCounter`，并不只在新增共享设备时计数 | 比较前先明确实际计数语义；实现偏差或修 bug 本身不构成新的替换算法 |
| 同文件 `401–562`，以及 `595–673` | 在所审路径中通过延迟与事件调度处理验证／回失效代价 | 这条闭合调用链没有提供显式广播、收齐确认、有限 DMA 数据排空的完整协议 FSM；不能据此声称论文所有实现都没有协议 |
| `modules/LCAcc/DMAController.cc:361–368` | 至少一端是 scratchpad，至少一端是本地 scratchpad | 该接口不允许两端都是外部 memory；它不是我们的 memory-to-memory DMA |
| `modules/linked-prefetch-tile/DMAEngine.hh:55–73` | 每个 transfer 取一个 memory 侧虚拟地址及一个翻译物理地址 | 不能假定它已经建模源、目的两端同时翻译 |
| `DMAEngine.cc:183–188,246–251,458–531` | `IsBufferReady` 恒真，`MakeBufferCopy` 为空；另有按在途数与 `issueWidth` 的限额 | 这不等于按真实有限字节 FIFO 预留返回空间；也不能外推成整个内存系统无限缓冲 |

Codex 还核了 `LCAccDevice.cc` 的消息打包／解包、DMAController 的翻译回调、DMAEngine 的内存回调以及 Ruby System 的接口。中间模型答复怀疑的参数顺序问题已排除：外层 wrapper 正确重排了参数。`pendingOpposite` 是同一物理块反向访问的串行等待，单独一条等待边不构成死锁。

**C1 降级的原因是实现语义与强基线需要重建，不是已经证明它无价值。** 如果继续该题，应分别复现论文政策和 artifact 政策，再与普通权重、aging、LRU/RRIP 及 SHARP 的存在信息刷新比较。不要把公开代码与论文不一致直接写成“论文错误”或我们的机制贡献。

## 3. 原读返回循环为何被普通信用规则排除

原条件环（箭头表示等待）：

`更新 U → 在途读 R 排空 → 缓冲腾空 → 目的写 W → 目的翻译 M → U`

设 `O` 是已存数据字节，`R` 是已物理发出但尚未返回的读字节，`B` 是接收容量。普通准入规则维持：

`O + R ≤ B`

停止发新读后，每返回 `k` 字节，`O += k，R -= k`。因此已发读都有预留接收空间，不需要等待目的翻译来腾出空间。前提是内存最终服务、接收端口可用，且 U 等的是这些物理请求排空，而非要求整个 copy 完成。

这是本轮 Codex 的条件推演，不是新实验或新发明。它只排除这一个环，不能证明全系统无死锁、固定时限完成，或涵盖所有排空语义。它也说明：不能只拿全 job 数据缓冲作为昂贵基线，省掉全 job 缓冲未必就是贡献。

## 4. 进一步发现的是另一个条件环：写已发出，数据尚待翻译

考虑目的地址已经翻译，物理写地址 AW 已接受，但写数据来自尚未完成源地址翻译的读。此时若更新 U 暂停源翻译，并等该写的完成响应 B：

`U → 已发写完成 B → 写数据 W → 源读 R → 源翻译 M → U`

读返回空间预留不会凭空生成写数据，所以不能排除这个环。AW 优先也不会解除它。当前事务控制器确实优先选择 AW，并以已接纳写计数参与 W 转发，但**尚未端到端核实当前 iDMA 会把同一写的数据挂在这个尚未翻译的源读上**；更重要的是当前平台没有这里假定的全局撤销锁。不能说已发现当前板卡 bug。

需要同时成立的条件：

1. AW 已物理发出，W 数据确实依赖尚未翻译的源读。
2. 更新暂停范围覆盖该源翻译，排空范围又包含该目的写。
3. 该已发写不能直接取消；数据也没有预存或另一条可完成路径。
4. 更新由合法生命周期事件触发，例如无关页的更新却采用设备级排空，或相关系统的容量回失效；不依赖软件违规提前解除活跃 DMA 映射。

这是对更一般双端 DMA 的**待证协议反例**。ShareMMU 的具体 accelerator/memory↔scratchpad 路径不同，本轮没有证实它违反论文的完成性假设。

## 5. 强普通方案已经能处理多少

| 方案 | 原读返回环 | 新写等待环 | 必须保留的条件 |
|---|---|---|---|
| AW 优先 | 不保证排除 | 不排除 | 仅改变请求选择顺序，当前平台已有 |
| 每个物理读预留返回空间 | 排除上述特定环 | 不排除 | 不能拿任意超额发读的状态做反例 |
| 仅增加缓冲容量 | 容量覆盖已发读时可排除 | 不保证 | 没有源数据时再大缓冲也无用 |
| 按源／目的页边界分块 | 单独不排除 | 单独不排除 | 分块不等于双方翻译完成 |
| 逐块完成两端翻译，并处理更新期间的有效性 | 可以排除 | 可以排除 | 物理发出前完成必要准备；部分预留可取消，避免在预留阶段引入另一个环 |
| 选择性暂停／排空 | 可在不覆盖依赖时破环 | 同左 | 不能假定所有架构都提供相同粒度或免费跟踪 |
| 失败请求记录与重放 | 已有强近邻 | 已有强近邻 | 普通 IOTLB miss 与 fault 不等价；不能重放已经产生不可重复副作用的写 |

[MMU-aware DMA，ICCD 2018](https://arxiv.org/pdf/1808.09751) §IV-C 已讨论传输所需翻译全部预装／锁定的普通办法及其并发代价，也提出按 burst 记录失败和重放。其原对象是 memory↔SPM，不能声称原论文已实现任意双端方案；但把普通预锁与分页分块组合并扩展到两端，显然是必须比较的强基线。

公平的普通基线是：按 `min(源页剩余, 目的页剩余, 剩余长度)` 分块，两端翻译及必要资源准备好后才发物理请求；失效时取消尚未发出的部分预留，或在合法的分块排空边界之后提交更新。**仅仅“过去翻译过”不够；也不能让新方案无限延迟权限撤销来换吞吐。** 这不是完整协议证明，但足以反对把分块／成对预翻译本身包装为新机制。

[Arm AMBA DTI IHI 0088G §4.3.6](https://documentation-service.arm.com/static/668660ca69e89f01e39c40fb) 已约束翻译、失效完成与流控的进度关系；[Understanding Host Interconnect Congestion，HotNets 2022](https://conferences.sigcomm.org/hotnets/2022/papers/hotnets22_sagarwal.pdf) 已分析 IOTLB miss 延长 DMA 延迟、占满有限在途信用并造成反压。因此“翻译影响有限缓冲／信用”不是本轮新发现的研究主题。

## 6. 一篇增量论文还必须补的差异

可检验的命题是：在相同数据缓冲 B、允许预留的翻译／分块数 K、在途上限以及更新完成约束下，某种明确的配对准入或可取消预留办法，比上述普通方案保留更多有效并发，且不给正确性或更新延迟转移成本。

这句话是研究规格，**不是机制设计或创新验收**。真正新增的内容至少要落到一个地方：可证明的资源／完成条件、前作没有覆盖的合法约束，或同等成本下稳定的性能—更新代价改进。小论文可以用旧构件做到这些；不要求每个零件都新，也不要求在概念验证之前已经得到最终性能结果。

优先比较的维度是有效吞吐、任务完成时间、更新完成时间，以及数据／元数据／预留条目开销。固定输入任务与可用资源，不能把会被机制改变的总 PTW 次数、miss 数或实际吞吐也强行固定。不要只用“全 job 预锁”和“无限缓冲”做弱对照。

停止条件明确：如果合法序列不可达，就停止以这个环为依据的主张；如果普通分块＋成对预翻译在同等约束下已没有额外代价，新名字不构成增量。若有代价，还须证明 proposed mechanism 真能降低它，而不是只换一种表述。

## 7. 对当前平台的决定

当前 [事务控制器](../cva6/corev_apu/riscv-iommu/rtl/transaction_controller/rv_iommu_trans_ctl_wrap.sv) `623–647` 已 AW 优先；`674–703` 是单主慢翻译等待路径。只加写优先或泛泛关键性调度不值得立题。[MASK，ASPLOS 2018](https://rausavar.github.io/pubs/mask-asplos18.pdf) §5.4 已有翻译请求优先及依据翻译停顿的应用选择；它不是本题相同接口，但限制了宽泛“关键性”主张。

当前单 lane 单个 4 KiB copy 和对应全量数据缓冲、没有完整私有 TLB/PT 回失效协议，会限制上述实验的可达性。若要研究这条问题，应先用小协议模型确认真实接口与普通基线的差异，再决定需补哪些 RTL；没有理由现在启动昂贵全量编译。已有 172 项功能验收和 method88 限速负结果保持原义，不替代此处证据。

**下一项最小证据**是一份真实双端 DMA 的合法请求序列与暂停／排空作用域，随后是普通逐块成对预翻译的资源账本。它们能决定继续还是停题；本轮没有自动启动模型实现或板测。C2 比此前更具体，但工程跨度仍大，不因问题听起来深就认定适合博一首篇；C1 也不能因实现简单就自动获得创新资格。
