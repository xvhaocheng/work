## 为什么使用 FPGA，什么时候需要仿真

研究使用的实际系统是 CVA6、iDMA、IOMMU、互连/DDR 和 Linux；Victim 任务耗时、实际压力及性能影响应由这套 FPGA 系统提供数据。仿真的可控内存响应不包含全部实际系统行为，不能替代板上性能数据。

仿真适合补充难以在板上精确复现或观察的因果问题，例如受控请求相位与页表响应。E2/E3 也可以在 FPGA 上做，但必须具有对应的状态/请求控制和观测能力；若没有直接证据，就保留“原因尚未确认”，不能从 HPM 和吞吐强行推出 HOL。

上游确有 vsim/类式 VIP 测试、目前只验证了本平台 HPM 的 Verilator 流程，这只是仿真工具现状，不构成搭新仿真环境的理由或 FPGA 实验门槛。

## P0：统一结果和测量含义

负载记录角色/DID、实际翻译上下文、源/目标映射、页大小、访问序列、chunk、总工作量、预热和排空规则。软件任务时间与硬件请求时间分别命名；active cycles 不能替代完整经过时间。

每试次保存元信息、原始计数/时间、试次汇总；有 trace 时用 run_id 关联。unavailable 与 0 分开。工具成功执行、数据/协议错误、超时、实验条件不足分别表示，机制结论另行记录。

元信息包含实际源码/修改、RTL 参数、bitstream/Image/rootfs 标识、工具版本、完整命令、seed、试次顺序。缺失观测不能填写为“没有事件”；无效样本保留原因，不进入正常性能比。

## P1：新双路软件测量

已实现部分涉及 `linux/include/uapi/linux/idma.h`、`linux/drivers/misc/idma.c`、`linux/drivers/iommu/riscv/iommu-hpm.c`，以及新前端 `bench/idma_experiment.c`。新 ABI 采用独立命令、明确版本/长度/能力信息；用户态和内核共享权威定义，不静默改变旧 ioctl 的含义。

状态机表达 prepare、warmup、measure、stop、drain、verify。V 完成固定任务就结束自己的窗口；A 在窗口内循环运行，随后停止补交并排空。记录实际提交间隙和工作量，不把程序持续运行等同于硬件持续竞争。

HPM 配置/快照由明确的驱动所有者管理，避免测量者互相覆盖全局寄存器。所有失败路径检查在途 DMA；无取消/复位能力时不能释放仍可能被访问的缓冲区，需排空或保留并隔离。

旧程序和结果保留在 Git 历史及构建前备份中；旧 0x01～0x05 已退役，新接口为 0x06/0x07。构建/rootfs 使用明确产物列表和内容检查，避免旧 `out/bench` 文件被误打包；已有 HPM RTL 回归保留。

主机桩可以验证 ABI、解析和错误传播，交叉编译验证可构建性；实际 DMA 时序、HPM 和任务时间只能由相应硬件测试确认。

## P2：现有 FPGA 上先建立可信测量

先核对实际连接板卡及软硬件版本，不把历史“无串口”当作现在的事实。完成既有 smoke、时钟/CDC/IO 约束审查和 HPM 端到端校准；构建、约束与上板功能分别留证。

软件可使用已有硬件寄存器先做功能/计数试跑。需要直接请求证据时，再增加每路入口/必要内部边界的 monitor 或 ILA。新增 RTL 必须对应新 bitstream，并检验观测逻辑、时序及其开销。

现有 migration-4dma 的 DS 50/50 只能作为明确标注的配置；正式 DS 0/0 基线尚需构建和验收。不能将两种配置的性能样本混用。

校准单设备冷/热、两设备事件归属、请求/完成量、数据、预热/窗口长度敏感性。能否确认实际请求竞争取决于观测能力；软件计时与 HPM 仍可能不足。

分别记录“功能/HPM 校准”和“实际供给/竞争校准”的状态。前者通过可继续试跑，后者是对应硬件干扰解释的门槛；不因缺少完整 trace 而禁止基本启动/功能检查。当前 S1/S2 事件源与 IOTLB miss 相关，不能作为独立 PTW 访存量；DDTW 相邻事件漏计未修复前不用于冷上下文定量结论。

## P3/P4：FPGA 现象和机制实验

E1 在固定 V 工作量下比较 Solo/Corun，同时记录实际 A 压力。E2 在相同初始化后执行 V 预热、A 有限工作、完全排空和 V 首次探测；只有 miss 变化时先称翻译状态影响，追踪替换/失效后再细分机制。

E2 显式依赖同一映射生命周期内的分阶段执行和相应排空/首次探测观测，当前 v1 连续共跑接口不具备该能力。选定 E2 后补此工作包；若优先研究 E3，可按其既定判据先推进，无需把所有 E2 扩展作为前置。一次 DMA 拷贝含源/目标两侧请求，不能把其累计 miss 自动解释成单页首次探测。

E3 先明确需要的触发与证据：V 请求提出/受理/排队，V 条目驻留和 lookup，A PTW 及其身份，翻译后出口与下游反压。可选 ILA 或专用事件记录；是否需要额外可控请求源或选择性页表延迟，依据待验证的因果条件决定。

若 CPU 无法产生足够/可控的压力，再考虑描述符队列、设备端循环或简易请求源；不把大规模流量发生器重构列为默认首项任务。既有 DS delayer 作用于多类数据结构请求，不能直接充当 PTW 专属干预。

不能精确操纵或观察某因果条件时，可用定向 RTL 仿真辅助，也可将结论保持为未确认。仿真结果与 FPGA 结果分别标注；只有实际触发条件获得对应证据才能建立联系。

## P4M：方法原型与公平基线（待实施）

明确方法可取得的观测、控制位置、参数、触发与退出规则、顺序/失效/异常及公平进度条件。先实现与主张直接相关的一个方法和简单基线；A 完整描述符间隔控制可作为通用准入基线，0 保留旧行为，等待 A 时必须继续服务 V。间隔控制仍是闭环，不称固定到达率。

评价保留 A 有效吞吐与 V 时间的取舍曲线，并在需要交代整体工作/积压时增加双方有限作业、各自独立结束的模式。记录原始就绪、实际提交和完成时刻；政策准入等待计入作业耗时。增加单独运行时的代价、必要消融；改 RTL 时增加资源/时序和功能正确性验证。

开发条件与正式留出条件分开，策略规则在正式验证前冻结。若验证后又改规则，原验证数据成为开发数据。实验工具正确但方法无优势仍是有效实验结果，不能标成新方法贡献成立。表征可以继续用于找设计缺口，不预先保证存在新方法。

## P5：正式矩阵与验收口径

正式采样前固定矩阵、顺序规则、重复数、精度/效应判据、无效样本处理和图表定义。先导试测单独标识。记录 slowdown 分布、每路事件、实际压力及可获得的机制证据。

验收实验能正确控制和测量，不要求一定出现 HOL 或 slowdown。压力成立且未检出影响是有效结果；压力不足是条件不足。页大小/BARE/DS 对照需说明同时改变的条件，不能将性能差简单相减称作纯翻译损失。

P0/P1 的最小软件入口已完成，下一项平台工作仍是设备准备与 P2 校准；依赖新增记录/控制的正式实验前完成相应 v1.1 项。四路全面扩展和复杂措施按 P4M 的具体主张选择，不默认纳入 v1.1，也不要求新建仿真环境。

## 可选辅助支线：定向 RTL 仿真

只有当问题需要精确请求相位、选择性页表响应或内部完整 trace 时启用。候选范围是实际 `rv_iommu_top`、合法 AXI 请求源、编程接口及数据结构/数据内存模型；涉及外部 mux 时才纳入同版 mux，明确与 FPGA 的差异。

可参考上游配置/协议代码，工具与依赖兼容性实施时核对，不默认更新 Bender 依赖。若建设此支线，先验收已知冷/热、请求身份、响应/数据正确性，再加入 E2/E3，且不要求目标机制必须出现。

本轮已修改 benchmark/驱动及构建打包，完成主机控制逻辑检查和完整软件构建；未修改 RTL、重建 FPGA 或升级依赖。当前无 FPGA 连接且 SD 卡尚未准备，未执行板上验收或正式实验。
