# 共享地址翻译：值得验证的创新候选

**最新比较：** [四候选前作—场景—约束—判别矩阵](translation-comparison-20261006.md)已完成。①优先立题验证，③与其共用场景；②条件保留、机制实施暂缓；④暂缓宽泛方案。矩阵补入 ShadowUpdate 的失效传播与 HELM 的指标指导策略证据，明确分层基线、闭环反馈、实际维护成本和停止条件。下方为候选形成过程，不代表已有创新或性能证据。

日期：2026-10-06。依据[123项文献地图](shared-translation-deepening-20261006.md)与[18席审定](innovation-council18-20261006.md)，加本轮定向原文与公开来源核查。以下是Codex提出/收紧的研究假设与优先级，不是已验证的新机制、全领域空白或发表承诺。DeepSeek负责聚合强前作和反证，完整答复保留在[证据包](../out/translation-opportunities-20261006/evidence.md)。

当前优先验证第一项；第二项需要先证明真实负载中共享与频繁更新同时存在；第三项可作为前两项的支撑，也可能形成独立的测量/方法贡献；第四项是结构性探索，研究风险最高。此排序基于问题与证据，不以现有FPGA是否容易实现决定。

**同日缺口审计更新：** [补充清单](shared-translation-gaps-20261006.md)新增20项优先核读前作，其中16项已补存全文、4项为题录/相关作者说明，尚未全部完成全文审阅。BIS/Criticality Stacks/CATS、Coz/MISE/ASM/CounterPoint以及PFM直接提高第一、三、四项的新颖性门槛；下列排序只表示待验证顺序。不能将“依赖感知”“因果观测”或“双视图”本身当作贡献。

## 1. 让翻译服务识别跨设备的计算依赖

**可能的论文主张：** 在存在跨设备生产—消费关系的应用中，仅按发起设备、请求数量或本地等待时间分配翻译资源，会选错对端到端进度最重要的请求；运行时提供少量依赖信息，可能显著改变这一取舍。

具体场景是假设性的：NIC、GPU和加速器组成流水线。一个设备产生大量后台搬运，另一个设备仅剩一个小消费组的数据尚未齐备，而它会解锁下游的大段计算。减少前者的平均翻译延迟，不一定缩短整条流水线的完成时间。是否真的存在这种翻译主导的状态，需要应用轨迹证明，不能用人为排队就当实际需求。

应用路径补核：NVIDIA当前[GPUDirect RDMA文档§3.4](https://docs.nvidia.com/cuda/gpudirect-rdma/index.html#supported-systems)要求所述路径使用1:1映射/直通，不能从NIC–GPU直连推导它们争用共享IOMMU翻译。应分别核GPU MMU、NIC注册翻译、IOMMU及设备缓存的位置和请求路径；不同硬件/互连需单独确认。BaM/GPUrdma可提供真实应用入口，但不是上述翻译瓶颈已存在的证据。另需对照[VIO（OSDI 2025）](https://www.usenix.org/conference/osdi25/presentation/wang-yun)的提交前缓冲区探查/缺页准备机制，区分软件供给与PTW服务。见[第三轮覆盖审计](../out/shared-translation-literature-20261006/gap-audit-03/README.md)。

**机制探索：** 由运行时标记消费组、依赖关系或近似剩余工作；把同一消费组的翻译需求关联起来，在PTW、请求合并、预取和数据搬运提交之间协调。元数据必须廉价、可随阶段变化更新，且有公平性/防饥饿约束。重点是找到现有设备局部状态缺少的必要信息，不能只给请求添一个“高优先级”位。

**必须超过的前作：** [Scheduling Page Table Walks（2018）](../out/shared-translation-literature-20261006/papers/walk_scheduling2018.pdf)已将同一SIMD指令的遍历看成一组，按预计工作量服务；[MASK](../out/shared-translation-literature-20261006/papers/mask2018.pdf)、DWS、SoftWalker/cuPTW已处理并发、优先级与计算资源占用。因此“等待warp多就优先”“同一指令批处理”“小任务先做”均不是新意。还必须补齐一般任务图调度、关键性内存调度和异构流水线研究，不能只在IOMMU论文中检索。

**最小判别：** 同一条真实应用轨迹，比较FIFO、按设备公平、SJF/同组优先、运行时已有优先级，以及知道完整依赖的理想策略。先只求收益上限，再计入依赖暴露与维护开销。如果理想策略也几乎没有额外端到端收益，停止；如果普通任务优先级已经能取得全部收益，也不应再做复杂IOMMU机制。

补充对照：BIS（ASPLOS 2012）和Criticality Stacks（ISCA 2013）已用同步等待识别影响整体进度的工作；CATS（ICS 2015）是运行时任务依赖调度近邻。PAR-BS和ATLAS是资源调度强基线。它们不等于已解决跨设备翻译问题，但要求明确：新增的设备依赖信息为何不能由已有运行时/调度器廉价获得，收益为何来自翻译层的特有约束。

## 2. 按映射生命周期决定翻译共享的范围

**可能的论文主张：** 同样高的翻译复用率，可能对应完全不同的收益：一种映射长期稳定，另一种很快迁移、改权限或回收。共享到更多设备节省查找，却会增加副本维护、失效确认和再次填充；只看命中率或排队压力可能判断错误。

**机制探索：** 将“哪些位置持有翻译副本、什么时候传播或回收副本”变成可控决策，使用可获得的分配/迁移阶段信息、复用间隔和实际维护代价。探索允许设备访问但避免为一次性访问长期保留远端翻译副本的组织方式。这可能需要新的设备—IOMMU协作，不能假定现有ATS设备已经支持任意缓存驻留控制；也不能以过期翻译或放宽权限撤销换性能。

**必须超过的前作：** [Trans-FW](../out/shared-translation-literature-20261006/papers/transfw2023.pdf)已有队列感知的远端转发；MGvm已有动态映射/负载均衡；[CLAP](../out/shared-translation-literature-20261006/papers/clap2025.pdf)已评估结合迁移；[Hydra](../out/shared-translation-literature-20261006/papers/hydra2024.pdf)、[IDYLL](../out/shared-translation-literature-20261006/papers/idyll2023.pdf)、[F&S](../out/shared-translation-literature-20261006/papers/fastsafe2024.pdf)与[ShareMMU](../out/shared-translation-literature-20261006/papers/sharemmu2026.pdf)已覆盖部分过滤、复用和维护。ShadowUpdate仍须取得全文。还要查自适应复制、缓存准入与一致性协议的经典近邻。

**最小判别：** 保持访问次数/地址重叠近似一致，改变真实映射阶段与更新事件，观察最优共享组织是否反转。成本要按实际时间线计，允许等待与工作重叠，不能将所有延迟无条件相加。若高复用与高更新不在真实负载中同时出现，或简单本地/共享阈值已取得全部收益，这项不值得单独立题。

补充对照：Leases、TinyLFU与MIND分别提供有效期、准入和共享内存管理的经典/相邻视角；数据副本的一致性语义不能直接替代翻译撤权语义。SPMC（MICRO 2026已接收）是本轮新核到的翻译共享近邻，目前仅核官方题录，取得全文前不推断其共享范围和协议。

## 3. 找出指导翻译优化所必需的最少观测

**可能的论文主张：** 若两种状态拥有近似相同的现有TLB统计，却需要相反的优化动作，那么仅凭这些统计的策略无法可靠选择。研究目标是找出还缺什么信息，并以足够低的成本及时取得它。

具体假设包括：相似miss率背后，可能是PTW排队阻塞关键消费者，也可能是翻译延迟已被其它工作隐藏；也可能真正拖慢任务的是映射更新或软件供给。先证明这种不可区分现象在限定观测集合下存在，再谈新策略。

**机制探索：** 为请求增加少量归因状态、采样等待阶段，或做短暂有界的资源扰动，分辨“多给翻译资源是否真的推进任务”。扰动本身的代价、非平稳负载、跨资源反馈与准确性都必须计入。最终需要使一个实际控制决策变好，不能只交一个分类器或仪表盘。

**必须超过的前作：** [2010 IOTLB瓶颈研究](../out/shared-translation-literature-20261006/papers/iotlb_bottleneck2010.pdf)已有成本隔离微基准；[ObservUVM](../out/shared-translation-literature-20261006/papers/observuvm2026.pdf)已有GPU访问观测机制；[Soar/Alto](../out/shared-translation-literature-20261006/papers/soaralto2025.pdf)、[PACT](../out/shared-translation-literature-20261006/papers/pact2026.pdf)已有性能关键性分析。还需对照通用内存干扰估计、因果剖析与性能计数器工作，HELM全文未取得，不能把它视作不覆盖。

**最小判别：** 用完整事件记录建立真值，逐步隐藏信息，查出哪些信息丢失会使动作选择出错；再测取得必要信息的代价。若现有计数器/简单模型足够，或观测和反应比应用阶段还慢、开销超过可获收益，则不建立独立课题。

补充对照：Coz（SOSP 2015）的虚拟加速、MISE（HPCA 2013）和ASM（MICRO 2015）的干扰估计已覆盖通用方法。CounterPoint（ASPLOS 2026）更直接以Haswell MMU为案例，用带噪计数器检查和修正微架构假设。新课题须证明现有方法在具体设备翻译条件下缺少什么信息；CounterPoint的模型一致性检查本身不等于在线控制策略。

## 4. 同一底层对象，允许不同设备使用不同的翻译表示

这是更大胆的结构方向：顺序访问者、稀疏访问者和频繁更新的对象，可能不适合相同的页表/覆盖方式。探索在共享物理数据、保留身份与权限语义的前提下，允许设备使用不同的局部翻译表示，并低成本同步更新。

**潜在贡献必须具体：** 证明同一对象上存在不可由单一表示兼顾的真实访问与维护冲突，再设计可共存、可验证、切换有界的表示。不能只提出“加一层中间地址”或“支持大小页”。页级地址转换也不能免费完成任意张量转置；改变页内元素布局往往需要地址生成器或实际数据重排，其代价必须算入。

VBI、Utopia、EMT、DIPTA、DeACT、Barre Chord和CLAP都构成直接威胁。[EMT](../out/shared-translation-literature-20261006/papers/emt2025.pdf)提供多种翻译结构的OS框架，其当前不覆盖IOMMU不代表简单移植有创新；[Utopia](../out/shared-translation-literature-20261006/papers/utopia2023.pdf)已有混合受限/灵活映射。只有在这些强设计加普通页拆分/分组/复制仍不能解决的同一约束下，且收益足以覆盖元数据与更新成本，才值得继续。

补充对照：[PFM / Dual-View Memory](https://arxiv.org/abs/2608.06989)（MICRO 2026已接收）已有一份物理数据面向NPU/PIM的不同逻辑视图；原文§IV-C的ARU做PA到硬件地址重映射，§VIII明确保留基本VA→PA转换，并依赖离线映射、有限MDT与重排缓冲。因此宽泛的“双视图”主张需要撤回；IOMMU页表表示共存及其更新成本是否仍有独立问题，需要精确比较，不能仅因层级不同声称新意。另补RMM与Twizzler；Direct Segments与DVM在原123项中已有全文，不是新增遗漏。

| 拥塞时把翻译换一条路 | CATO作者页面的搜索索引说明已有按层级有效延迟选择本地遍历/CXL卸载，并用哈希叶PTE副本的设计。直接网页当前404，仍为作者说明/索引级，未得全文；该线索足以要求强对照，不足以审定完整协议或性能。它面向CXL分层内存，不应泛称GPU卸载。来源保留于[web-2](../out/translation-opportunities-20261006/web-2.txt)。 |
| 热度换成关键性、等待warp越多越优先 | 关键性、SIMT指令完成组和并发调度都有经典/近年工作。第一项只有跨设备依赖确实提供必要新信息且现有接口无法低成本达到同效果时，才可能形成贡献。 |
| 单独改batch、预取或页排序 | 仍作为强基线；若与消费依赖相结合，归入第一项验证，不拆成多个表面不同的“创新”。 |

## 当前决定与证据边界

优先找一条真实多设备流水线，检验第一项的理想策略收益空间；第三项用于确认收益来自翻译及所需信息。并行保留第二项的真实高复用/高更新轨迹收集；第四项暂列高风险探索。以上是建议顺序，本轮未执行轨迹采集、仿真、RTL修改或板测，既有172/172功能验收不能支持这些创新结论。

本轮DeepSeek一次调用维持thinking/high、393216预算，完整返回。其证据表中的部分行号混合了原论文与worker报告位置，不直接视为精确原文定位；MMU-aware DMA在本轮worker输入中缺席，不代表123项库没有该文。Codex直接重看2018页表遍历调度、MASK、CLAP、ShareMMU与IDYLL相关段落，并核规范和新近邻后作上述取舍。模型意见用于提出与反驳问题，不能替代创新检索或实验。
