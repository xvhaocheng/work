# 行缓冲图像工作流与共享翻译研究假设

本轮将问题固定为：**一条按期限取下一行图像的DMA，与一条持续后台搬运共享IOMMU。** 工作流、三个强对照和可推翻主张可以具体写清；但目前没有证据证明这条工作流相对强简单方法还存在多少性能缺口。因此本轮不批准新RTL方法，也不把旧PN退化当作新方案收益空间。

这是固定目的COPY主线下的一个具体需求实例，作为本对话的补充立题记录；不覆盖同期[研究收敛计划](history/plans/research-convergence-plan-20261010.md)，不恢复晚选目的或共享载荷候选。

**谁搬什么，何时需要结果**

DASH原论文§2.2给出640×480、30fps的Sobel例子：四个行槽，每行640字节；计算使用三行，同时预取下一行；下一行必须在约69.44微秒内就绪。只有一个空槽，因此不能继续提前写入下一行并覆盖仍在使用的数据。这是本轮采用的工作流依据。[DASH原文](https://people.inf.ethz.ch/omutlu/pub/dash_deadline-aware-heterogeneous-memory-scheduler_taco16.pdf)

本项目将其改成如下明确合同。图像源帧在开始前已经存在、运行期间不变；DMA0从源帧依次搬640字节至四个固定目的行槽，消费者完成当前三行计算后释放最旧行槽。DMA1独立做4KiB后台copy，源和目的各有16个4KiB页组成的环，完成后立即提交下一项。两路无共享源、无可任选目的、无取消已发事务；后台流与共享IOMMU是本项目研究适配，不是声称DASH原Sobel例已测过这些条件。

| 项目 | 固定值或规则 |
|---|---|
| 图像格式 | 640×480，1字节/像素，源帧307,200字节 |
| 行缓冲 | 4×640=2,560字节；3行计算、1行预取 |
| 每行期限 | 精确625000/9纳秒；50MHz下31250/9周期 |
| DMA0地址 | 源`0x10000000 + row×640`；目的`0x20000000 + (row mod 4)×640` |
| 后台负载 | 独立上下文，源/目的各64KiB环；每次4KiB，完成驱动持续提交 |
| 元数据何时可知 | 所有行地址、字节数和期限从t0可知，所有方法享有相同信息 |
| 数据写入何时允许 | 对应行槽被消费者释放以后；提前翻译允许，提前覆盖有效数据不允许 |
| 初始化 | 前3行共1,920字节单列；初始化、最终消费和输出成本不能藏进稳态指标 |

因此，约束是载荷槽的寿命，不是下一行地址未知，也不是禁止提前翻译。基线可以使用相同大小的行缓冲、合法预翻译、预读、大页和缓存保护；提前预读使用的暂存也须公平计入。合同检查的是首次写入目的载荷的时刻，不能拿“任务发出不得早于释放”误伤合法准备。完成必须代表数据已可被消费者读取，不能用翻译成功代替。若增加缓冲能解决问题，增加的实际存储与收益也应比较，不能假定四行缓冲对所有实现永远不可改变；本轮只是固定资源预算下的首个实例。

**当前数据到底证明了多大缺口**

现有同BIT、同boot、A8、V64、gap0实验中，P平均窗口109839.3周期，PN为123956.7周期，即PN慢12.85%；后台速率分别29133.55与25815.51 copy/s，PN低11.39%。**这说明PN在该例不如P，不能证明强简单方法仍有12.85%的损失可以回收。** 当前数据是4KiB copy及完成后的固定gap，没有行缓冲消费、固定绝对deadline或逐行延迟证据。[原归约](../out/pn-board-path-20261007/reduction.json)

源码边界也明确：现有前端在copy完成后进入GAP再发下一项；composition ABI固定4KiB及0/1000/4000周期gap，不支持本合同的640字节行、slot-free和deadline。旧gap不能直接改名为重叠计算，旧平均copy时间不能作为每行最坏时延。[前端状态机](../cva6/corev_apu/iDMA/src/frontends/register_64bit/idma_reg64_frontend.sv)、[现有接口](composition-v1-spec-20261004.md)

还存在一个很强的简单对照：307,200字节源帧可放入一个2MiB映射，2,560字节目的环可放入一个4KiB映射。在物理分配和权限允许、S2关闭、静态映射且条目保留的条件下，V只需两个S1叶翻译条目。它可能消除稳态V叶翻译miss，却不保证消除数据争用或所有共享控制等待。现有IOTLB支持2MiB匹配；当前benchmark驱动按PAGE_SIZE映射，不能声称该大页实验已实现或已验证。若大页需独占一个2MiB分配，须报告相对307,200字节的容量成本，不能把更大映射覆盖不应授权的内存。[映射代码](../linux/drivers/misc/idma.c)、[IOTLB大页匹配](../cva6/corev_apu/riscv-iommu/rtl/translation_logic/rv_iommu_iotlb.sv)

所以，本轮对“简单方法为什么不够，以及差多少”的答案是：**目前尚未测到这条新工作流相对强简单方法的剩余缺口，数值应记为未测，不能记成12.85%，也不能反过来断言为零。** 这是进入方法实现前必须解决的唯一性能判别。

**固定三个强对照的规则与权限**

| 对照 | 决策规则及权限 |
|---|---|
| B0 固定配置与后台额度 | 在训练条件选择映射、P或不分区、后台额度；包括合法大页与准备方案。参数固定后验证；逐场景事后最优包络只作解释，不能冒充在线策略。 |
| B1 截止时间调度加入口门控 | 按任务期限和进度调优先级，计入真实在途排空及保守翻译服务；允许根据已知周期提前限制后台、正常提前翻译。使用与候选相同的早期任务信息。 |
| B2 整任务保护窗口 | 关键copy需要保护时停止新增后台copy；已有事务合法完成；关键copy实际完成后恢复后台。允许相同提前准备。 |

B1有明确前作依据：DASH既有动态优先，也计在途请求排空时间，并明确说明source throttling可以与其结合。MASK已有翻译和数据联合优先。因此不能仅增加一个deadline标签、加一项PTW估时或把优先级向前传，就宣布新增机制。[DASH](https://people.inf.ethz.ch/omutlu/pub/dash_deadline-aware-heterogeneous-memory-scheduler_taco16.pdf)、[MASK](https://research.ece.cmu.edu/safari/pubs/MASK-address-space-aware-gpu-memory-hierarchy_asplos18.pdf)

这里冻结的是对照规则和公平权限，尚未把三个策略移植为行工作流的可执行调度器，不能记作基线已跑通。复用已有P/不分区与额度策略，不再搭建完整应用；真正比较前须固定调参输入、服务估计方法和动作时刻。必要差异证据是：在这些普通控制已经合法提前准备后，仍存在可达状态，使候选新增信息改变必要的保护时长。仅让未优化基线盲目保守不满足此条件。

**一句可推翻的贡献主张**

> 在这条固定行预取工作流中，利用当前copy剩余翻译工作和已经承诺的服务量，按需缩短后台保护窗口，可以在满足相同行期限的前提下，比调好的固定配置、DASH式入口门控和整任务保护完成更多后台有效搬运，且增益覆盖新增观测与控制成本。

这是筛选假设，不是已证明收益或新颖性。候选新增信息是绑定真实请求和上下文的源/目的翻译进展、在途义务；新增动作只是在恰当时刻停止接纳新的后台copy及恢复。它不撤销已发布VALID、不跳过权限检查，也不假设当前composition可以忙时切换P/N配置。原始TLB驻留信息不等于成功许可，未来命中也不能凭一次采样保证；若估计不能保守覆盖失效和竞争，就不能宣称有期限保证。

具体正例要求同样字节数和期限下，某些行确实需要更长翻译服务、另一些行无需该服务，而保守保护浪费了可用后台时间；这些状态必须由合法执行产生。不能通过禁止基线预取或人为拖延它来制造差异。邻近反例包括大页且V翻译已保留、无后台流、翻译代价可以忽略或期限足够宽。若B0/B1/B2已经达到相同或更好的期限—后台进度—成本关系，就否定这版方法主张。

评价使用所有方法相同的绝对时间区间，报告每行释放至实际可消费完成的延迟、late行数/最大迟到、后台有效完成字节及额外存储/端口/控制开销。不能通过推迟任务释放、丢帧、跳过困难行或改变统计窗口改善指标。初版只处理静态S1和正常完成；不能把有限轨迹零迟到写成硬实时证明。

DeepSeek负责既有证据与脚本草案；Codex亲自选题、核关键原文/源码、制定合同及可推翻主张，审查代码并执行合同检查。一个关键Codex席核DASH/MASK等近邻。当前只恢复有界立题，生产RTL、Linux、FPGA编译和上板不启动；合同检查结果与实际用量另见本轮执行记录。
